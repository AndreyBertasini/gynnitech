Lo staging non e' il posto dove "fare tutta la trasformazione". E' il posto dove rendere i dati **puliti, leggibili e confrontabili**. Se lo staging diventa un mart travestito, il progetto si opacizza. Se invece resta troppo raw, tutta la complessita' esplode nei layer successivi.

## Cosa deve fare un modello di staging

In un contesto martech un buon `stg_*` di solito fa queste cose:

- rinomina colonne con uno standard coerente
- applica cast espliciti
- normalizza timezone e date
- pulisce valori sentinella o stringhe vuote
- genera flag elementari
- conserva una granularita' vicina alla sorgente

## Esempio: staging per Meta Ads

```sql
with source as (
    select * from {{ source('raw_marketing', 'meta_ads_daily') }}
),
renamed as (
    select
        cast(date as date) as report_date,
        cast(campaign_id as varchar) as campaign_id,
        cast(adset_id as varchar) as adset_id,
        lower(trim(campaign_name)) as campaign_name_raw,
        cast(spend as numeric(12, 2)) as spend,
        cast(clicks as integer) as clicks,
        cast(impressions as integer) as impressions,
        cast(loaded_at as timestamp) as loaded_at
    from source
)
select
    report_date,
    campaign_id,
    adset_id,
    campaign_name_raw,
    spend,
    clicks,
    impressions,
    case when impressions > 0 then clicks * 1.0 / impressions end as ctr,
    loaded_at
from renamed
```

## Esempio: staging per sessioni web

```sql
with source as (
    select * from {{ source('raw_marketing', 'ga4_sessions') }}
)
select
    cast(session_id as varchar) as session_id,
    cast(user_pseudo_id as varchar) as anonymous_user_id,
    cast(session_start_at as timestamp) as session_started_at,
    lower(nullif(source, '')) as session_source,
    lower(nullif(medium, '')) as session_medium,
    lower(nullif(campaign, '')) as session_campaign,
    coalesce(nullif(landing_page, ''), '/unknown') as landing_page,
    case
        when lower(medium) in ('cpc', 'paid_social', 'display') then true
        else false
    end as is_paid_session
from source
```

## Standardizzazione campagne con seed di mapping

```text
seeds/campaign_mapping.csv

campaign_name_raw,channel_group,country,target_funnel
it_bf24_retargeting,paid_social,it,retention
bf24-ret,paid_social,it,retention
black friday retargeting,paid_social,it,retention
```

Poi:

```sql
with ads as (
    select * from {{ ref('stg_meta_ads_daily') }}
),
mapping as (
    select * from {{ ref('campaign_mapping') }}
)
select
    ads.*,
    map.channel_group,
    map.country,
    map.target_funnel
from ads
left join mapping map
    on ads.campaign_name_raw = map.campaign_name_raw
```

## Timezone e calendario

Se:

- Meta Ads chiude il giorno in UTC
- Shopify salva in UTC
- GA4 viene letto in property timezone
- il management legge tutto in Europa/Rome

allora devi fissare una regola presto, non nel dashboard finale.

```sql
select
    order_id,
    order_created_at at time zone 'Europe/Rome' as order_created_at_local,
    cast(order_created_at at time zone 'Europe/Rome' as date) as order_date_local
from {{ source('raw_commerce', 'shopify_orders') }}
```

Se un collega non tecnico apre un modello di staging, dovrebbe poter dire: "capisco che qui stanno pulendo e standardizzando". Se invece vede KPI finali, il layer e' sbagliato.

## Dove si rompe il disordine

Un errore frequente e' costruire staging troppo carichi. Di solito succede perche' qualcuno chiede una metrica urgente e lo sviluppatore "la aggiunge subito nello staging" per risparmiare tempo. Sei mesi dopo lo staging ha 50 colonne, calcoli di business, flag aziendali e logica di attribution.

A quel punto lo staging non e' piu' utile. Diventa confuso. E quando cambia una regola di business, nessuno sa se aggiornare lo staging o il mart.

Ecco perche' una regola pratica utile e': se vedi la parola "final" nel nome di una colonna dello staging, hai un problema.

## Casi martech specifici

### Campagne con nomi incoerenti

Meta Ads potrebbe dare `it_bf24_retargeting`, Google Ads `BF24 Retargeting`, HubSpot `Black Friday 2024 Retargeting`. Lo staging di Meta le pulirebbe tutte allo stesso modo (lowercase, trim, remove special chars). Poi un modello intermedio le mapperebbe tutte alla chiave unificata.

Non nello staging. Lo staging non sa quale sia la "vera" naming aziendale.

### Timestamp di multiple zone

Se ricevi dati da:
- Meta in UTC
- Shopify in UTC
- GA4 letto in timezone property
- CRM in timezone locale

lo staging standardizza ogni sorgente secondo la propria regola interna, ma non li converte yet a una timezone aziendale unica. Questo avviene in una trasformazione successiva, magari intermedia o nel mart, quando sai quale regola di business applica.

## Test che proteggono lo staging

Sui modelli di staging ha senso aggiungere test semplici ma utili:

```yml
models:
  - name: stg_meta_ads_daily
    columns:
      - name: report_date
        data_tests:
          - not_null
      - name: spend
        data_tests:
          - not_null
          - dbt_expectations.expect_column_values_to_be_of_type:
              column_type: numeric
```

Questi test proteggono da errori silenti quando le sorgenti cambiano schema o valori.

## Riepilogo

Lo staging layer esiste per togliere entropia al dato. In martech vuol dire soprattutto rendere confrontabili piattaforme diverse, gestire naming e timestamp, e preparare il terreno per marts e metriche senza anticipare decisioni di business troppo presto. Se lo staging diventa complesso, stai mettendo logica nel posto sbagliato.
