## ClickHouse Mastery


> **Consiglio:**
> ClickHouse è il database analitico open-source più veloce al mondo. In questa lezione imparerai come funziona internamente, come progettare schemi ottimali e come sfruttare le sue feature uniche per ottenere performance impossibili con altri database.


## Cos'è ClickHouse

ClickHouse è un database management system **colonnare** creato da Yandex nel 2016 e rilasciato come open-source. È progettato per una sola cosa: **query analitiche veloci su grandi volumi di dati**. E lo fa meglio di qualsiasi altro database al mondo.

Alcuni numeri per dare contesto:
- Processa **miliardi di righe al secondo** su hardware commodity
- Comprime i dati **10-40x** rispetto alla dimensione originale
- Una singola macchina con 32 core può gestire **petabyte** di dati
- Le query analitiche tipiche terminano in **millisecondi**, non minuti

### Quando Usare ClickHouse

**Perfetto per:**
- Analytics e reporting (dashboard, BI)
- Log analysis (eventi, access log, error log)
- Time-series data (metriche, monitoring, IoT)
- Marketing analytics (eventi utente, attribuzione, funnel)
- Real-time analytics (con Materialized Views)

**Non adatto per:**
- Database transazionale dell'applicazione (usa PostgreSQL)
- Operazioni UPDATE/DELETE frequenti
- Query punto singolo (SELECT per ID specifico)
- Transazioni ACID con rollback
- Sistemi con tantissime scritture piccole (meglio batch)

## L'Architettura Interna

### Il MergeTree Engine

Il **MergeTree** è il motore di storage principale di ClickHouse e la chiave delle sue performance. Capirne il funzionamento è essenziale per progettare schemi efficaci.

Come funziona:

1. **Inserimento**: I dati vengono scritti in **parti** (parts) — blocchi immutabili di dati ordinati. Ogni INSERT crea una nuova parte.

2. **Merge**: In background, ClickHouse **fonde** (merge) le parti piccole in parti più grandi. Questo è il "Merge" di MergeTree.

3. **Ordinamento**: All'interno di ogni parte, i dati sono ordinati secondo la chiave `ORDER BY` della tabella. Questo ordinamento permette la compressione efficace e le ricerche binarie.

4. **Indicizzazione**: ClickHouse crea un **sparse index** — un indice che punta a blocchi di ~8192 righe (granuli), non a singole righe. È sufficiente per le query analitiche e molto più leggero di un B-tree.

```
INSERT batch 1 → Parte 1 (ordinata per ORDER BY)
INSERT batch 2 → Parte 2 (ordinata per ORDER BY)
INSERT batch 3 → Parte 3 (ordinata per ORDER BY)
     ↓ (background merge)
Parte 1+2+3 → Parte Merged (ordinata, compressa, indicizzata)
```

### Implicazioni Pratiche

1. **Batch INSERT è fondamentale**: Inserisci almeno 1000-10000 righe per volta. Inserire riga per riga crea migliaia di parti piccole che rallentano tutto.

2. **L'ORDER BY determina tutto**: La scelta della chiave ORDER BY è la decisione più importante quando crei una tabella.

3. **I dati sono immutabili**: Una volta scritti, i dati in una parte non cambiano. UPDATE e DELETE sono operazioni "pesanti" che riscrivono intere parti.

## Schema Design: L'ORDER BY Perfetto

La scelta dell'ORDER BY è la decisione di design più critica in ClickHouse. Determina:
- Quali query saranno veloci (filtri sulle colonne ORDER BY)
- Quanto i dati si comprimeranno (colonne simili vicine)
- Quanta RAM serve per l'indice sparse

### Regole per l'ORDER BY

1. **Metti per prima la colonna con più filtri equality**. Se il 90% delle query filtra per `event_name`, mettila per prima.
2. **Bassa cardinalità prima, alta cardinalità dopo**. Le colonne con pochi valori unici (es. `country` con ~200 valori) prima delle colonne con molti valori unici (es. `user_id` con milioni).
3. **Le colonne temporali di solito vanno per ultime**. Il timestamp ha alta cardinalità (ogni secondo è diverso) ma è utile per range scan.
4. **Non mettere troppe colonne**. 3-5 colonne nell'ORDER BY è tipico. Più colonne = indice più grande = meno efficiente.

### Esempi Pratici

```sql
-- Tabella eventi: la maggior parte delle query filtra per event_name e timestamp
CREATE TABLE events (
    event_name   LowCardinality(String),
    timestamp    DateTime64(3),
    user_id      String,
    properties   String,
    page_url     String
) ENGINE = MergeTree()
ORDER BY (event_name, timestamp)
PARTITION BY toYYYYMM(timestamp);

-- Tabella log: le query filtrano per service e severity
CREATE TABLE logs (
    service      LowCardinality(String),
    severity     Enum8('debug'=0, 'info'=1, 'warn'=2, 'error'=3),
    timestamp    DateTime,
    message      String,
    trace_id     String
) ENGINE = MergeTree()
ORDER BY (service, severity, timestamp)
PARTITION BY toYYYYMMDD(timestamp);

-- Tabella analytics: le query filtrano per tenant e data
CREATE TABLE analytics_events (
    tenant_id    UInt32,
    event_date   Date,
    event_name   LowCardinality(String),
    user_id      String,
    revenue      Decimal(10, 2)
) ENGINE = MergeTree()
ORDER BY (tenant_id, event_date, event_name)
PARTITION BY (tenant_id, toYYYYMM(event_date));
```

## La Famiglia MergeTree

ClickHouse offre diverse varianti del MergeTree, ognuna ottimizzata per un caso d'uso specifico:

### ReplacingMergeTree

Mantiene solo l'ultima versione di ogni riga (basata sull'ORDER BY). Utile per dimension table che vengono aggiornate.

```sql
CREATE TABLE dim_users (
    user_id      String,
    name         String,
    plan         LowCardinality(String),
    updated_at   DateTime
) ENGINE = ReplacingMergeTree(updated_at)
ORDER BY user_id;

-- Inserisci aggiornamenti come nuove righe
INSERT INTO dim_users VALUES ('u1', 'Mario', 'free', now());
INSERT INTO dim_users VALUES ('u1', 'Mario', 'pro', now());
-- Dopo il merge, rimarrà solo la versione con updated_at più recente
```


> **Attenzione:**
> La deduplicazione nel ReplacingMergeTree avviene durante il background merge, non immediatamente. Per query deterministiche, usa `FINAL` o `argMax()`:
```sql
SELECT user_id, argMax(plan, updated_at) AS current_plan
FROM dim_users GROUP BY user_id;
```


### SummingMergeTree

Somma automaticamente le colonne numeriche per righe con la stessa chiave ORDER BY. Perfetto per aggregazioni incrementali.

```sql
CREATE TABLE daily_stats (
    date         Date,
    event_name   LowCardinality(String),
    event_count  UInt64,
    revenue      Decimal(10, 2)
) ENGINE = SummingMergeTree()
ORDER BY (date, event_name);

-- Inserisci incrementi
INSERT INTO daily_stats VALUES ('2024-01-15', 'purchase', 5, 500.00);
INSERT INTO daily_stats VALUES ('2024-01-15', 'purchase', 3, 300.00);
-- Dopo il merge: ('2024-01-15', 'purchase', 8, 800.00)
```

### AggregatingMergeTree

Versione avanzata del SummingMergeTree che supporta qualsiasi funzione di aggregazione (non solo SUM). Usa tipi di dato speciali `*State` e `*Merge`.

```sql
CREATE MATERIALIZED VIEW mv_user_stats
ENGINE = AggregatingMergeTree()
ORDER BY (user_id, date)
AS SELECT
    user_id,
    toDate(timestamp) AS date,
    countState() AS events_state,
    uniqState(page_url) AS unique_pages_state,
    sumState(toUInt64(revenue)) AS revenue_state
FROM events
GROUP BY user_id, date;

-- Query: usa le funzioni *Merge per ottenere il risultato
SELECT
    user_id,
    countMerge(events_state) AS total_events,
    uniqMerge(unique_pages_state) AS unique_pages,
    sumMerge(revenue_state) AS total_revenue
FROM mv_user_stats
WHERE date >= '2024-01-01'
GROUP BY user_id;
```

### Confronto dei Motori

| Engine | Caso d'uso | Deduplicazione | Aggregazione |
|--------|-----------|---------------|-------------|
| **MergeTree** | General purpose | No | No |
| **ReplacingMergeTree** | Dimension table, dati mutabili | Per ORDER BY key | No |
| **SummingMergeTree** | Contatori, totali incrementali | No | SUM automatico |
| **AggregatingMergeTree** | Pre-aggregazioni complesse | No | Qualsiasi funzione |
| **CollapsingMergeTree** | Stato mutabile con "cancel row" | Per sign column | No |
| **VersionedCollapsingMergeTree** | Come sopra, con versioning | Per version + sign | No |

## Tipi di Dato Ottimali

La scelta dei tipi di dato in ClickHouse ha un impatto enorme su performance e storage:

### LowCardinality

Il tipo più importante da conoscere. Wrappa un altro tipo e usa un **dictionary encoding** per colonne con pochi valori unici (< 10.000).

```sql
-- PRIMA: String normale
country String  -- ~15 byte per riga

-- DOPO: LowCardinality
country LowCardinality(String)  -- ~1-2 byte per riga (dictionary encoded)
```

**Usalo per**: country, plan, status, event_name, browser, device_type, channel — qualsiasi colonna con cardinalità < 10.000.

**Impatto**: 5-15x riduzione in storage, 2-5x più veloce nelle aggregazioni.

### Tipi Numerici Appropriati

Non usare `UInt64` quando `UInt16` basta:

| Tipo | Range | Byte |
|------|-------|------|
| `UInt8` | 0 - 255 | 1 |
| `UInt16` | 0 - 65.535 | 2 |
| `UInt32` | 0 - 4.294.967.295 | 4 |
| `UInt64` | 0 - 18.4 quintilioni | 8 |
| `Float32` | Floating point | 4 |
| `Float64` | Double precision | 8 |
| `Decimal(P, S)` | Precision esatta | Variabile |

```sql
-- Buono: tipi appropriati
CREATE TABLE orders (
    quantity     UInt16,          -- Max 65K (abbastanza per quantità)
    revenue      Decimal(10, 2), -- Precision esatta per i soldi
    discount_pct Float32,        -- Approssimazione OK per percentuali
    user_age     UInt8            -- Max 255 (abbastanza per l'età)
);
```

### Enum per Stati Fissi

```sql
-- Enum usa 1 byte e ha validazione automatica
CREATE TABLE tickets (
    status Enum8(
        'open' = 1,
        'in_progress' = 2,
        'resolved' = 3,
        'closed' = 4
    )
);
```

### DateTime64 per Timestamp Precisi

```sql
timestamp DateTime64(3)  -- Millisecondi (3 decimali)
-- vs
timestamp DateTime       -- Solo secondi
```

## Partitioning

Il **partitioning** divide la tabella in parti fisiche separate basate su un'espressione. Le query che filtrano sulla colonna di partizione possono **saltare intere partizioni** senza leggerle.

### Regole per il Partitioning

```sql
-- BUONO: Partitioning per mese (12-60 partizioni)
PARTITION BY toYYYYMM(timestamp)

-- BUONO: Partitioning per mese + tenant (per multi-tenant)
PARTITION BY (tenant_id, toYYYYMM(timestamp))

-- CATTIVO: Partitioning per giorno su anni di dati (migliaia di partizioni)
PARTITION BY toYYYYMMDD(timestamp)
-- → Troppo granulare, crea troppe parti, rallenta i merge

-- CATTIVO: Partitioning su colonna ad alta cardinalità
PARTITION BY user_id
-- → Milioni di partizioni = disastro
```

**Regola**: Punta a **12-100 partizioni** attive. Troppo poche non aiutano; troppe rallentano il sistema.

### TTL (Time-To-Live)

ClickHouse può cancellare automaticamente i dati vecchi:

```sql
CREATE TABLE events (
    timestamp DateTime,
    event_name String,
    user_id String
) ENGINE = MergeTree()
ORDER BY (event_name, timestamp)
PARTITION BY toYYYYMM(timestamp)
TTL timestamp + INTERVAL 13 MONTH;  -- Cancella dopo 13 mesi

-- TTL differenziato: comprimi prima, cancella dopo
TTL
    timestamp + INTERVAL 3 MONTH TO VOLUME 'cold',   -- Sposta su storage economico
    timestamp + INTERVAL 13 MONTH DELETE;             -- Cancella
```

## Compressione Avanzata

ClickHouse permette di specificare il codec di compressione per ogni colonna:

```sql
CREATE TABLE events (
    -- Timestamp: delta encoding + LZ4 (ottimo per serie temporali)
    timestamp    DateTime64(3) CODEC(Delta, LZ4),

    -- Interi incrementali: DoubleDelta (compressione estrema)
    event_id     UInt64 CODEC(DoubleDelta, LZ4),

    -- Stringhe: ZSTD per miglior ratio
    properties   String CODEC(ZSTD(3)),

    -- Float: Gorilla per valori che cambiano poco
    temperature  Float32 CODEC(Gorilla, LZ4),

    -- Low cardinality: già compresso dal dictionary, LZ4 basta
    country      LowCardinality(String) CODEC(LZ4)
) ENGINE = MergeTree()
ORDER BY (timestamp);
```

### Verificare la Compressione

```sql
-- Vedi quanto spazio usa ogni colonna
SELECT
    column,
    formatReadableSize(sum(data_compressed_bytes)) AS compressed,
    formatReadableSize(sum(data_uncompressed_bytes)) AS uncompressed,
    round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 2) AS ratio
FROM system.columns
WHERE database = 'analytics' AND table = 'events'
GROUP BY column
ORDER BY sum(data_compressed_bytes) DESC;
```

## Materialized Views: Pre-aggregazione Automatica

Le **Materialized Views** in ClickHouse sono trigger che calcolano aggregazioni al momento dell'inserimento. Non sono "viste materializzate" nel senso tradizionale — sono pipeline di trasformazione real-time.

```sql
-- Ogni volta che un evento viene inserito in 'events',
-- questa view aggiorna automaticamente i conteggi giornalieri
CREATE MATERIALIZED VIEW mv_daily_metrics
ENGINE = SummingMergeTree()
ORDER BY (event_name, date)
AS SELECT
    event_name,
    toDate(timestamp) AS date,
    count() AS event_count,
    uniq(user_id) AS unique_users
FROM events
GROUP BY event_name, date;

-- Query sulla Materialized View: istantanea su miliardi di eventi
SELECT event_name, date, event_count, unique_users
FROM mv_daily_metrics
WHERE date >= '2024-01-01'
ORDER BY date, event_count DESC;
```

### Quando Usare le Materialized Views

- **Dashboard real-time**: Pre-calcola le metriche che le dashboard mostrano
- **Aggregazioni costose**: COUNT(DISTINCT), percentili, funnel
- **Downsampling**: Ridurre la granularità (da secondi a minuti/ore)
- **Denormalizzazione incrementale**: JOIN al momento dell'inserimento

## Monitoring e Diagnostica

```sql
-- Query più lente
SELECT
    query,
    query_duration_ms,
    read_rows,
    formatReadableSize(read_bytes) AS data_read,
    formatReadableSize(memory_usage) AS memory
FROM system.query_log
WHERE type = 'QueryFinish'
  AND query_duration_ms > 1000
ORDER BY query_duration_ms DESC
LIMIT 20;

-- Spazio per tabella
SELECT
    database,
    table,
    formatReadableSize(sum(bytes_on_disk)) AS size,
    sum(rows) AS total_rows,
    count() AS parts
FROM system.parts
WHERE active = 1
GROUP BY database, table
ORDER BY sum(bytes_on_disk) DESC;

-- Stato dei merge
SELECT
    database,
    table,
    elapsed,
    progress,
    formatReadableSize(total_size_bytes_compressed) AS size
FROM system.merges;
```

1. Crea una tabella `events` con ORDER BY ottimale per le tue query più frequenti
2. Scegli i tipi di dato appropriati (LowCardinality, Enum, tipi numerici corretti)
3. Configura il partitioning per mese e un TTL di 13 mesi
4. Crea una Materialized View che pre-aggrega i dati giornalieri
5. Inserisci dati di test e verifica la compressione con la query `system.columns`
6. Confronta la velocità di query sulla tabella raw vs sulla Materialized View
