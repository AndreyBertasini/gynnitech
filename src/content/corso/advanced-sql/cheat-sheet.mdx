Questa scheda non sostituisce le lezioni del modulo. Serve come promemoria operativo quando devi scegliere velocemente il pattern SQL giusto per una domanda analitica.

## Quando usare quale pattern

### Window functions

Usale quando vuoi mantenere il dettaglio di riga ma aggiungere contesto.

```sql
sum(revenue) OVER (PARTITION BY channel)
row_number() OVER (PARTITION BY category ORDER BY revenue DESC)
lagInFrame(revenue) OVER (ORDER BY month)
```

Usi tipici:

- ranking
- contribution percent
- running total
- MoM / WoW / YoY

### Date spine

Usala quando hai una metrica temporale e i giorni senza eventi contano.

```sql
WITH start_date AS toDate('2025-01-01')
SELECT start_date + number AS day
FROM numbers(31)
```

Usi tipici:

- line chart corretti
- medie mobili
- alerting temporale

### Cohort retention

Usala quando vuoi confrontare utenti entrati in periodi diversi.

```sql
dateDiff('month', cohort_month, activity_month) AS month_number
countDistinct(user_id) AS active_users
```

Usi tipici:

- retention prodotto
- repeat purchase
- confronto canali acquisition

### Funnel

Usalo quando vuoi misurare il percorso verso una conversione.

```sql
max(if(event_name = 'landing', 1, 0)) AS s1_landing
max(if(event_name = 'purchase', 1, 0)) AS s5_purchase
```

Usi tipici:

- ecommerce checkout funnel
- activation funnel
- onboarding funnel

### Pivot e KPI table

Usali quando il reporting richiede confronto diretto tra dimensioni.

```sql
sum(if(channel = 'google', amount, 0)) AS revenue_google
GROUP BY ROLLUP(country, channel)
```

Usi tipici:

- scorecard management
- export per finance
- subtotali gerarchici

### Pareto e segmentazione

Usali quando vuoi capire cosa pesa davvero sul totale o chi merita attenzione.

```sql
sum(total_revenue) OVER (
    ORDER BY total_revenue DESC
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
ntile(10) OVER (ORDER BY total_revenue DESC)
```

Usi tipici:

- top customers
- assortimento prodotti
- CRM targeting

## Query fragments da ricordare

### Running total

```sql
sum(metric) OVER (
    ORDER BY day
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

### Media mobile a 7 righe

```sql
avg(metric) OVER (
    ORDER BY day
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
)
```

### Contribution sul totale gruppo

```sql
metric / sum(metric) OVER (PARTITION BY dimension)
```

### First e last del gruppo

```sql
first_value(metric) OVER (
    PARTITION BY entity
    ORDER BY ts
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
)
```

### OHLC in ClickHouse

```sql
argMin(price, ts) AS open_price,
max(price) AS high_price,
min(price) AS low_price,
argMax(price, ts) AS close_price
```

## Anti-pattern frequenti

### `SELECT *` su tabelle grandi

Legge piu' colonne del necessario e rende la query piu' costosa.

### Funnel senza ordine temporale

Gonfia la conversione e rovina l'interpretazione.

### Retention senza `DISTINCT`

Conta gli eventi, non gli utenti.

### Medie mobili su serie con buchi

Se manca la date spine, la media mobile e' fuorviante.

### Pareto senza ordinamento decrescente

La cumulata perde senso.

## Checklist pre-dashboard

- La granularita' della riga e' esplicita?
- I `NULL` sono trattati in modo intenzionale?
- I tassi usano `nullIf(..., 0)`?
- I subtotali sono chiaramente distinguibili?
- La query separa bene calcolo e presentazione?
- Il risultato e' leggibile anche senza grafico?

<Aside type="tip">
La domanda giusta da farti prima di ogni query non e' "quale funzione uso?", ma "che decisione deve rendere possibile questa tabella?".
</Aside>

## Riepilogo operativo

- Parti dalla domanda di business, non dalla funzione SQL.
- Scegli il pattern in base al tipo di output: tabella dettagliata, KPI table, funnel, retention o shortlist di anomalie.
- Controlla sempre granularita', `NULL`, divisori a zero e leggibilita' finale.
- Se il risultato non e' interpretabile senza grafico, il layer SQL non e' ancora abbastanza buono.
