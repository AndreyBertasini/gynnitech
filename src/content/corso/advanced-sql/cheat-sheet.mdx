# Test, refactoring e pattern SQL riusabili

Una query di 280 righe scritta mesi fa con cinque subquery annidate produce un fatturato mensile più alto del 12% rispetto al mese precedente, ma nessuno nel team osa toccarla perché non ha commenti sul *grain* (granularità) delle tabelle né test automatici di integrità. Quando un nuovo sviluppatore aggiunge una `LEFT JOIN` verso la tabella delle promozioni per estrarre il codice sconto, duplica silenziosamente gli ordini che hanno usato due coupon nello stesso carrello. La causa non è SQL: è mantenere **query monolitiche prive di CTE con grain dichiarato e prive di test di integrità che restituiscono zero righe quando i dati sono sani**.

## Fatturato gonfiato del 12% per una LEFT JOIN su coupon multipli

Questo è un caso ricostruito con numeri di esempio su quanto accade quando una query SQL complessa non dichiara il proprio livello di granularità e non esegue test automatici di unicità e riconciliazione.

Ogni query di produzione dovrebbe rispettare quattro livelli di controllo e modularità:

| Livello di controllo | Cosa verifica | Regola operativa | Output atteso |
| :--- | :--- | :--- | :--- |
| **Test di unicità e `not_null`** | Nessun duplicato sulla chiave primaria del modello | `GROUP BY pk HAVING count() > 1` | `0` righe restituite |
| **Test di integrità referenziale** | Nessun record orfano verso la tabella padre | `LEFT JOIN` + `WHERE parent.id IS NULL` | `0` righe restituite |
| **Test di quadratura / invarianti** | Conservazione dei totali dopo JOIN o deduplica | `abs(sum_after - sum_before) > 0.01` | `0` righe restituite |
| **Refactoring in CTE con grain** | Ogni CTE dichiara esplicitamente 1 riga = cosa | Commento `-- Grain: 1 row per order_id` | Leggibilità e zero fan-out |

Adottare la convenzione **"zero righe = test superato"** rende ogni controllo SQL immediatamente integrabile in dbt, in CI/CD o in uno script di monitoraggio schedulato.

## Test SQL a zero righe, refactoring in CTE con grain e pattern riusabili

Il primo meccanismo è il **test di integrità a zero righe**. Invece di scrivere query di controllo che stampano `COUNT(*)` costringendo un umano a leggere il numero, si scrive una query che restituisce **solo le righe violate**. Se la query restituisce `0` righe, il test passa; se restituisce `>= 1` righe, la pipeline si ferma e mostra esattamente gli ID incriminati.

Il secondo meccanismo è il **refactoring in CTE sequenziali con grain dichiarato**. Ogni subquery annidata va estratta in una CTE nominata in modo esplicito (`orders_dedup`, `coupons_agg_by_order`, `orders_enriched`), dichiarando in un commento la granularità esatta (`-- Grain: 1 row per order_id`). Prima di fare qualsiasi `LEFT JOIN`, si aggrega sempre la tabella figlia (`coupons_agg_by_order`) allo stesso grain della tabella padre, eliminando matematicamente ogni rischio di duplicazione (fan-out).

Il terzo meccanismo è la **centralizzazione dei pattern riusabili in modelli intermedi dbt**. Se tre dashboard diverse hanno bisogno della deduplica degli ordini o della sessionizzazione degli eventi, copiare e incollare la stessa CTE in tre file crea divergenze inevitabili. Il pattern va estratto una sola volta in un modello `int_orders_dedup` testato, e tutte le query a valle leggono da lì.

**Dichiarate il grain di ogni CTE, aggregate le tabelle figlie prima della JOIN e scrivete test SQL che restituiscono zero righe quando i dati rispettano i vincoli.**

## Tre errori comuni nel refactoring e nei test SQL

Il blocco SQL qui sotto mostra l'errore tipico di una query monolitica che esegue una `LEFT JOIN` diretta verso una tabella `1:N` senza pre-aggregare, generando duplicati silenziosi:

```sql
-- ERRORE 1: LEFT JOIN diretta su order_coupons (1 ordine -> N coupon) duplica o.revenue_eur!
-- ERRORE 2: nessuna CTE nominata né grain dichiarato -> impossibile fare debug!
SELECT
    o.order_id,
    o.revenue_eur,
    c.coupon_code
FROM analytics_prod.fct_orders AS o
LEFT JOIN analytics_prod.fct_order_coupons AS c
    ON o.order_id = c.order_id;
```

### Fare JOIN prima di aggregare le tabelle con relazione 1:N

Unire `fct_orders` (`1` riga per ordine) con `fct_order_coupons` (`N` righe per ordine) moltiplica `o.revenue_eur` per `N`. La regola ferrea è: **prima** aggregate `fct_order_coupons` per `order_id` (es. `groupArray(coupon_code)` o `sum(discount_eur)`), **poi** eseguite la `LEFT JOIN`.

### Scrivere test che controllano solo se la tabella non è vuota

Verificare `COUNT(*) > 0` non intercetta duplicati, valori negativi assurdi né rotture di quadratura. I test utili verificano invarianti specifici di business: `revenue_eur < 0` dove non ammesso, `shipped_at < ordered_at`, o duplicati sulla chiave primaria.

### Copiare e incollare la stessa logica di deduplica o window function in 10 query diverse

Duplicare blocchi SQL identici in più dashboard garantisce che alla prima modifica di regola di business (es. nuovo stato `'partially_refunded'`) almeno metà delle query resti disallineata. Centralizzate la logica una volta sola in un modello intermedio o in una macro dbt.

## Suite di test a zero righe e refactoring sicuro in ClickHouse

Per trasformare una query fragile in un modello robusto e verificato in ClickHouse, applicate questi quattro passi:

1. Dichiarate il grain di partenza (`1 row per order_id`) e pre-aggregate ogni tabella `1:N` in una CTE dedicata prima della `JOIN`.
2. Costruite la CTE finale unendo solo tabelle già portate allo stesso grain.
3. Eseguite una suite di test che restituisce **zero righe** per unicità, integrità e invarianti temporali.
4. Centralizzate il modello pulito come vista o tabella intermedia riusabile.

Ecco l'implementazione SQL completa in ClickHouse:

```sql
-- Refactoring sicuro con pre-aggregazione 1:N e suite di test a zero righe:
WITH coupons_by_order AS (
    -- Grain: 1 row per order_id
    SELECT
        order_id,
        count() AS coupons_applied_count,
        sum(discount_eur) AS total_coupon_discount_eur,
        arrayStringConcat(groupArray(coupon_code), ', ') AS coupon_codes_list
    FROM analytics_prod.fct_order_coupons
    GROUP BY order_id
),
orders_enriched AS (
    -- Grain: 1 row per order_id
    SELECT
        o.order_id,
        o.customer_id,
        o.order_date,
        o.revenue_eur,
        coalesce(c.coupons_applied_count, 0) AS coupons_applied_count,
        coalesce(c.total_coupon_discount_eur, 0.00) AS total_coupon_discount_eur,
        coalesce(c.coupon_codes_list, '') AS coupon_codes_list
    FROM analytics_prod.fct_orders AS o
    LEFT JOIN coupons_by_order AS c
        ON o.order_id = c.order_id
    WHERE o.status = 'paid'
)
-- Test di integrità a zero righe: restituisce solo eventuali violazioni di unicità o importo!
SELECT
    order_id,
    'DUPLICATE_OR_INVALID_REVENUE' AS test_failure_reason,
    count() AS row_count,
    min(revenue_eur) AS min_rev
FROM orders_enriched
GROUP BY order_id
HAVING row_count > 1 OR min_rev < 0;
```

In questa query `coupons_by_order` riduce la cardinalità `1:N` a `1:1` prima della `LEFT JOIN`, rendendo impossibile qualsiasi fan-out su `revenue_eur`, mentre il blocco finale verifica in un colpo solo l'unicità di `order_id` e l'assenza di ricavi negativi restituendo `0` righe su dati sani.

Per rendere questo approccio scalabile su tutto il progetto analytics, organizzate i test a zero righe in tre categorie eseguite a ogni pull request e a ogni run notturno: test di schema (`unique`, `not_null`, `accepted_values`), test di relazione tra tabelle padre e figlie, e test di quadratura finanziaria che confrontano i totali prima e dopo le trasformazioni critiche. Quando un test fallisce e restituisce righe, la query stessa funge da report diagnostico immediato perché espone già gli `order_id` o i `customer_id` anomali da ispezionare.

Infine, ricordate che ogni CTE ben nominata con il proprio *grain* dichiarato funge da documentazione vivente per chi erediterà il codice tra sei mesi: un collega può leggere la sequenza dall'alto verso il basso e capire in trenta secondi dove entra il dato grezzo, dove avviene l'aggregazione `1:N` e dove viene garantita l'unicità finale. Questa disciplina trasforma l'SQL analitico da script fragili in vera ingegneria del software.

## Test SQL a zero righe in dbt vs controlli manuali in BI

Per garantire la qualità dei dati nel tempo, potete **integrare test SQL a zero righe nella pipeline dbt/CI** oppure **controllare i grafici manualmente in BI dopo il rilascio**.

Il criterio di scelta è netto: **automatizzate sempre i test di unicità, integrità referenziale e quadratura in dbt (`dbt test`) o in CI prima che i dati raggiungano le dashboard, perché un errore di fan-out o un duplicato non deve mai essere scoperto dal direttore finanziario durante una riunione.**

La confusione comune consiste nel pensare che i test rallentino lo sviluppo: in realtà, una suite di 5 test a zero righe richiede pochi secondi di esecuzione e risparmia ore di debug quando cambia una tabella sorgente.

## Cinque domande prima di promuovere una query SQL in produzione

1. Ogni CTE della query dichiara esplicitamente il proprio *grain* (`1 row per ...`)?
2. Tutte le tabelle con relazione `1:N` sono state pre-aggregate al grain padre **prima** della `LEFT JOIN`?
3. Esiste un test automatico a zero righe che verifica l'unicità della chiave primaria finale?
4. Esiste un test di quadratura che confronta il totale dei ricavi prima e dopo le `JOIN`?
5. La logica condivisa (deduplica, sessionizzazione, attribuzione) è centralizzata in un solo modello riusabile?

La metrica di controllo della qualità SQL è il **Test Failure Row Count**: ogni test di integrità, unicità e quadratura deve restituire esattamente **`0` righe** ad ogni esecuzione della pipeline.

Integrare questo standard nel flusso di lavoro quotidiano significa che nessuna modifica a una query o a una tabella sorgente può rompere silenziosamente un KPI esposto in dashboard. Ogni volta che introducete una nuova trasformazione o un nuovo join, la prima domanda non è "il risultato sembra plausibile?", ma "quale test a zero righe dimostra matematicamente che il *grain* è preservato e che i totali quadrano?". Quando tutto il team adotta questa disciplina, i numeri aziendali smettono di essere oggetto di discussione in riunione e diventano una base affidabile, verificabile e condivisa per decidere in modo rapido.
