## Esercizio 1: trovare la campagna piu' debole

Scenario: il team performance marketing vuole capire quale campagna ha generato meno ordini confermati nel trimestre. La richiesta e' precisa: niente `LIMIT 1`, serve una soluzione che si estenda facilmente anche a casi "per paese" o "per canale".

Schema minimo:

```sql
campaigns(
    campaign_id    bigint,
    campaign_name  varchar
)

orders(
    order_id       bigint,
    campaign_id    bigint,
    status         varchar,
    country        varchar
)
```

<Tabs>
  <TabItem label="Traccia" icon="pencil">

  Scrivi una query che restituisca:

  - `campaign_name`
  - `confirmed_orders`
  - `rn`

  Dove `rn = 1` identifica la campagna con meno ordini confermati.

  </TabItem>
  <TabItem label="Soluzione" icon="seti:db">

  ```sql
  WITH campaign_orders AS (
      SELECT
          c.campaign_name,
          count(o.order_id) AS confirmed_orders
      FROM campaigns c
      LEFT JOIN orders o
          ON o.campaign_id = c.campaign_id
         AND o.status = 'confirmed'
      GROUP BY c.campaign_name
  ),
  ranked AS (
      SELECT
          campaign_name,
          confirmed_orders,
          row_number() OVER (
              ORDER BY confirmed_orders ASC, campaign_name
          ) AS rn
      FROM campaign_orders
  )
  SELECT
      campaign_name,
      confirmed_orders,
      rn
  FROM ranked
  WHERE rn = 1;
  ```

  Qui il punto chiave e' che il ranking avviene **dopo** l'aggregazione. Se ordinassi le righe raw di `orders`, non staresti classificando le campagne ma le singole occorrenze.

  </TabItem>
</Tabs>

## Esercizio 2: segmentare i prodotti in quartili di vendita

Scenario: il category manager non vuole solo sapere i top seller. Vuole vedere come l'intero catalogo si distribuisce in 4 quartili e quali prodotti definiscono i limiti alto e basso di ogni quartile.

Schema minimo:

```sql
product_sales(
    product_id      bigint,
    product_name    varchar,
    sales_amount    numeric(12, 2)
)
```

<Tabs>
  <TabItem label="Traccia" icon="pencil">

  Dividi i prodotti in 4 quartili per `sales_amount` dal piu' alto al piu' basso e mostra, per ogni quartile:

  - il prodotto con vendite massime
  - il prodotto con vendite minime
  - i relativi importi

  </TabItem>
  <TabItem label="Soluzione" icon="seti:db">

  ```sql
  WITH bucketed AS (
      SELECT
          product_id,
          product_name,
          sales_amount,
          ntile(4) OVER (
              ORDER BY sales_amount DESC, product_name
          ) AS quartile
      FROM product_sales
  ),
  ranked AS (
      SELECT
          quartile,
          product_name,
          sales_amount,
          row_number() OVER (
              PARTITION BY quartile
              ORDER BY sales_amount DESC, product_name
          ) AS rn_top,
          row_number() OVER (
              PARTITION BY quartile
              ORDER BY sales_amount ASC, product_name
          ) AS rn_bottom
      FROM bucketed
  )
  SELECT
      quartile,
      max(CASE WHEN rn_top = 1 THEN product_name END) AS highest_selling_product,
      max(CASE WHEN rn_top = 1 THEN sales_amount END) AS highest_sales_amount,
      max(CASE WHEN rn_bottom = 1 THEN product_name END) AS lowest_selling_product,
      max(CASE WHEN rn_bottom = 1 THEN sales_amount END) AS lowest_sales_amount
  FROM ranked
  GROUP BY quartile
  ORDER BY quartile;
  ```

  Qui usi due idee in cascata:

  - `NTILE(4)` per creare i bucket
  - `ROW_NUMBER()` dentro ogni bucket per trovare estremi alto e basso

  Questo pattern e' molto utile per portfolio analysis, pricing band e merchandising.

  </TabItem>
</Tabs>

## Esercizio 3: trovare il payback day del mese

Scenario: ogni mese il team finance sostiene `85000` euro di costi fissi marketing e operations. Vuole sapere in quale giorno del mese la cumulata dei ricavi supera quella soglia.

Schema minimo:

```sql
daily_sales(
    sold_at        date,
    net_revenue    numeric(12, 2)
)
```

<Tabs>
  <TabItem label="Traccia" icon="pencil">

  Costruisci una query che restituisca:

  - `month`
  - `payback_day`

  per il primo giorno di ogni mese in cui la cumulata dei ricavi supera `85000`.

  </TabItem>
  <TabItem label="Soluzione" icon="seti:db">

  ```sql
  WITH daily_margin AS (
      SELECT
          DATE_TRUNC('month', sold_at) AS month,
          sold_at AS day,
          sum(net_revenue) AS revenue
      FROM daily_sales
      GROUP BY DATE_TRUNC('month', sold_at), sold_at
  ),
  with_running AS (
      SELECT
          month,
          day,
          revenue,
          sum(revenue) OVER (
              PARTITION BY month
              ORDER BY day
              ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
          ) AS cumulative_revenue
      FROM daily_margin
  ),
  crossed AS (
      SELECT
          month,
          day,
          row_number() OVER (
              PARTITION BY month
              ORDER BY day
          ) AS rn
      FROM with_running
      WHERE cumulative_revenue >= 85000
  )
  SELECT
      month,
      day AS payback_day
  FROM crossed
  WHERE rn = 1
  ORDER BY month;
  ```

  La struttura corretta e' sempre la stessa:

  1. tabella giornaliera
  2. cumulata mensile
  3. filtro sulle righe che superano la soglia
  4. ranking della prima riga utile

  </TabItem>
</Tabs>

## Checklist mentale per risolvere bene gli esercizi

- Se devi scegliere "la prima" o "la peggiore" riga: pensa a `ROW_NUMBER()`
- Se devi dividere una distribuzione in gruppi omogenei: pensa a `NTILE()`
- Se devi trovare quando una soglia viene superata: pensa a `SUM() OVER (...)` con cumulata

<Aside type="tip" title="Test manuale rapido">
Prima di fidarti della query, controlla sempre 5-10 righe a mano. Le window functions sono potenti, ma proprio per questo gli errori di logica possono sembrare molto credibili.
</Aside>
