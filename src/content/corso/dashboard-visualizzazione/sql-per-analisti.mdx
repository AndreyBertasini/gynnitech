# SQL per analisti: query per dashboard

Le query SQL per le dashboard vanno lette come un passaggio decisionale, non come definizioni isolate. Una query collega la domanda al dato, il dato al controllo e il controllo all'azione, così il lavoro tecnico resta ancorato a una scelta verificabile sotto incertezza invece di diventare un esercizio fine a sé stesso.

## Il caso che spiega tutto: due dashboard che non concordano

Un team nota discrepanze tra due dashboard executive: una conta le righe ordine, l'altra le righe pagamento. La soluzione parte da SQL. Allineare grain, join e date elimina il conflitto prima ancora di discutere di visualizzazioni o filtri.

Il primo sospetto è il grain: la prima dashboard conta gli ordini, la seconda i pagamenti, e un ordine può avere più pagamenti (o nessuno). Il secondo è il join: se la tabella ordini viene unita alla tabella pagamenti uno-a-molti, ogni ordine con due pagamenti raddoppia le righe. Il terzo è la data: la prima usa la data dell'ordine, la seconda la data del pagamento, e un ordine di dicembre pagato a gennaio compare in due mesi diversi. Nessuno dei tre errori è visibile guardando i grafici: si vede solo che i numeri non tornano.

## Pattern comuni per query dashboard

Una dashboard affidabile nasce da query solide: grain esplicito, filtri controllati, join senza duplicati, denominatori chiari e date coerenti. Alcuni pattern tornano spesso.

L'aggregazione temporale con date spine evita i buchi: usi una tabella di date generata per assicurarti che ogni giorno abbia un valore, anche zero. Per il confronto al periodo precedente sfrutti funzioni di finestra come LAG, che mettono in fila periodi consecutivi e calcolano le variazioni percentuali. Il Top N con categoria "others" classifica i primi N elementi e raggruppa il resto sotto "others", così la visualizzazione resta leggibile.

```sql
-- Confronto settimana su settimana con LAG
WITH weekly AS (
    SELECT
        DATE_TRUNC('week', order_date) AS week,
        COUNT(DISTINCT order_id) AS orders
    FROM orders
    WHERE order_date >= CURRENT_DATE - INTERVAL '90 days'
    GROUP BY 1
)
SELECT
    week,
    orders,
    LAG(orders) OVER (ORDER BY week) AS prev_orders,
    ROUND(
        100.0 * (orders - LAG(orders) OVER (ORDER BY week))
        / NULLIF(LAG(orders) OVER (ORDER BY week), 0),
        1
    ) AS wow_change_pct
FROM weekly
ORDER BY week;
```

Nota il `NULLIF`: quando la settimana precedente ha zero ordini, la divisione produrrebbe un errore o un infinito. Gestire il denominatore è parte del lavoro, non un dettaglio.

## Ottimizzazione per dashboard

Le query pesanti conviene materializzarle con tabelle temporanee o CTAS notturni. La finestra temporale di default va limitata, per esempio agli ultimi 90 giorni, e le date vanno sempre parametrizzate invece di essere scritte a mano nella query. Un timeout impostato evita che query lente frustrino chi usa la dashboard.

La regola pratica: la dashboard deve rispondere in secondi, non in minuti. Se la query impiega più di qualche secondo, il problema non è il grafico ma la query — e la soluzione è materializzare, filtrare prima di aggregare e ridurre il volume che arriva alla vista.

## Verificare che la query risponda alla domanda

Prima di pubblicare una vista, fai tre controlli. Il primo è il conteggio: la somma delle righe della query deve combaciare con un conteggio indipendente sulla sorgente, altrimenti c'è un join che duplica. Il secondo è il bordo: controlla i valori agli estremi della finestra temporale, dove gli errori di timezone e di inclusione si nascondono più facilmente. Il terzo è la definizione: scrivi in una riga cosa conta la query — "ordini pagati, con data di pagamento, esclusi i test" — e verifica che il codice faccia esattamente quello.

```sql
-- Sanity check: il totale della vista deve combaciare con la sorgente
SELECT COUNT(*) AS righe_vista FROM analytics.vista_ordini;
SELECT COUNT(*) AS righe_sorgente
FROM orders
WHERE status <> 'test'
  AND paid_at IS NOT NULL;
```

Se i due numeri non combaciano, non correggere il grafico: correggi la query. La discrepanza è un'informazione, non un fastidio.

## L'errore da evitare

Il rischio più comune è trattare SQL per dashboard come un'etichetta invece che come un processo. Succede quando mostri un grafico senza decisione, una metrica senza baseline o una conclusione che non dichiara quali assunzioni potrebbero invalidarla.

La domanda chiave è: se questo risultato fosse instabile, quale scelta sbaglierei? Se non sai rispondere, manca il collegamento tra analisi e azione. E quando due dashboard non concordano, la risposta non è mai "il dato è sbagliato": è "qual è il grain, il join e la data di ciascuna?".

## Riepilogo

Le query SQL per analisti diventano davvero utili quando aiutano a prendere decisioni più chiare, non quando si limitano a produrre numeri. Il valore nasce dal collegare problema, dati, metrica, segmentazione e azione.

I pattern — date spine, LAG, Top N con others, sanity check — sono strumenti riusabili che risolvono i problemi ricorrenti delle dashboard: buchi temporali, confronti senza baseline, viste illeggibili, numeri che non tornano.

Una buona analisi non si ferma a dire che il numero è salito o sceso, ma risponde a quale decisione prendiamo, con quale confidenza e come misureremo il successo. La query è il punto in cui quella risposta si costruisce — o si perde.
