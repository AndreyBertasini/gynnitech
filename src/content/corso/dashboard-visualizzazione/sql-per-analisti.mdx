# SQL per analisti: query per dashboard
SQL per analisti: query per dashboard va letto come un passaggio decisionale, non come una definizione isolata. La lezione collega domanda, dato, controllo e azione, cosi il lavoro tecnico resta ancorato a una scelta verificabile sotto incertezza.


## Problema reale

Nel contesto delle dashboard e della visualizzazione dati, il vero problema è trasformare dati complessi in strumenti decisionali chiari e affidabili. Le query SQL per analisti non sono semplici esercizi tecnici: sono il cuore di un processo che deve supportare scelte concrete, riducendo l'incertezza.

## Modello concettuale

Per lavorare bene, bisogna partire da quattro punti chiave:

| Fase      | Cosa chiarire                              | Output                  |
|-----------|-------------------------------------------|-------------------------|
| Domanda   | Quale scelta reale deve migliorare?       | Decisione da prendere   |
| Misura    | Quale segnale osservabile rappresenta il problema? | Metrica o dato sorgente |
| Controllo | Quale baseline rende il risultato interpretabile? | Confronto credibile     |
| Azione    | Che cosa cambia dopo l'analisi?            | Prossimo passo operativo|

Questo schema semplice aiuta a non perdere di vista che ogni query deve avere uno scopo: non basta mostrare numeri, bisogna collegarli a una decisione.

## Formalizzazione rigorosa

Prima di scrivere una query, definisci l'unità di lavoro: può essere un grafico, una metrica, una vista o una decisione ricorrente. Associa a questa unità un segnale osservabile, come la frequenza d'uso o la chiarezza del dato. Poi dichiara la decisione che questa analisi dovrebbe supportare, per esempio un alert o una revisione operativa.

| Elemento       | Specifica richiesta                                         |
|----------------|------------------------------------------------------------|
| Unità di analisi| grafico, metrica, vista, stakeholder o decisione ricorrente|
| Segnale principale| leggibilità, frequenza di uso, tempo alla decisione, ambiguità ridotta |
| Baseline       | periodo precedente, gruppo comparabile, benchmark o scenario controfattuale |
| Decisione      | dashboard, vista operativa, alert o narrativa executive     |
| Rischio        | scambiare un numero disponibile per una prova sufficiente   |

La formalizzazione permette di replicare e criticare l'analisi, evitando che sia solo un esercizio di stile.

## Esempio o caso studio

Un team nota discrepanze tra due dashboard executive: una conta righe ordine, l'altra righe pagamento. La soluzione parte da SQL: allineare grain, join e date elimina il conflitto prima di discutere visualizzazioni o filtri.

| Evidenza osservata            | Lettura prudente                         | Azione consigliata                  |
|------------------------------|-----------------------------------------|-----------------------------------|
| Il numero migliora            | Potrebbe essere effetto reale o variazione normale | Cercare confronto e segmentazione |
| Un segmento cambia più degli altri | La media aggregata nasconde differenze | Separare coorti o casi d'uso       |
| Il costo cresce insieme al risultato | L'impatto va letto sul margine          | Stimare trade-off e sostenibilità  |

## Lab / esercizio

### Livello base

Scrivi una scheda sintetica per una query dashboard: decisione da supportare, metrica principale, baseline, rischio e azione prevista.

### Livello intermedio

Costruisci una tabella con tre segmenti o periodi. Per ciascuno indica cosa cambia, una possibile spiegazione alternativa e un controllo da fare prima di agire.

### Livello research-grade

Prepara un memo decisionale con ipotesi, dati richiesti, criteri di esclusione, controlli di qualità, soglia decisionale, rischi residui e piano di monitoraggio.

### Dataset e materiali consigliati

Usa dati reali di dashboard, metriche business, brief stakeholder, mockup e log di utilizzo. Se non disponibili, crea un dataset sintetico con almeno 200 righe, dimensione temporale, segmenti e metrica di outcome.

## Errore tipico da evitare

Il rischio più comune è trattare SQL per dashboard come un'etichetta invece che un processo. Succede quando si mostra un grafico senza decisione, una metrica senza baseline o una conclusione senza indicare quali assunzioni potrebbero invalidarla.

La domanda chiave è: se questo risultato fosse instabile, quale scelta sbaglierei? Se non sai rispondere, manca il collegamento tra analisi e azione.

## Quiz o checkpoint

1. Quale decisione concreta dovrebbe migliorare questa analisi?
2. Quale unità di analisi rende il problema misurabile?
3. Quale baseline useresti per evitare una lettura ingenua?
4. Quale errore tipico potrebbe cambiare la conclusione?
5. Quale output consegneresti a uno stakeholder non tecnico?

## Riepilogo operativo

Le query SQL per analisti diventano davvero utili quando aiutano a prendere decisioni più chiare, non solo a produrre numeri. Il valore nasce dal collegare problema, dati, metrica, segmentazione e azione. Una buona analisi non si limita a dire "il numero è salito" o "è sceso". Deve rispondere: quale decisione prendiamo, con quale confidenza, e come misureremo il successo.

## Pattern comuni per query dashboard

Una dashboard affidabile nasce da query solide: grain esplicito, filtri controllati, join senza duplicati, denominatori chiari e date coerenti. Ecco alcuni pattern utili:

- Aggregazione temporale con date spine per evitare buchi:

  Usa una tabella di date generate per assicurarti che ogni giorno abbia un valore, anche zero.

- Metriche con confronto al periodo precedente:

  Usa funzioni di finestra come LAG per confrontare periodi consecutivi e calcolare variazioni percentuali.

- Top N con categoria "others":

  Classifica i primi N elementi e raggruppa il resto in "others" per semplificare la visualizzazione.

## Ottimizzazione per dashboard

- Materializza query pesanti con tabelle temporanee o CTAS notturni.
- Limita la finestra temporale di default (es. ultimi 90 giorni).
- Parametrizza le date, mai hardcodarle.
- Imposta timeout per evitare query lente che frustrano l'utente.

## Approfondimento operativo

SQL per dashboard non è un esercizio isolato. È parte di un sistema decisionale più ampio, fatto di dati, vincoli tecnici e incentivi organizzativi. Il lavoro professionale richiede di capire il problema, le assunzioni e cosa succede se queste non tengono.

## Caso reale: Netflix e la disciplina delle metriche

Netflix non si limita a misurare click o visualizzazioni immediate. Valuta segnali di qualità come completamento degli episodi, ritorno degli utenti e tempo di ricerca. Questo approccio evita di ottimizzare vanity metric dannose nel lungo periodo.

## Esempio SQL: vista di controllo

Costruisci una vista che aggrega eventi per settimana, segmento e metrica chiave, così da poter confrontare periodi e gruppi senza riscrivere la logica.

## Esempio Python: controllo anomalie

Usa rolling mean e deviazione standard per identificare variazioni anomale nelle metriche settimana su settimana, evitando di reagire a oscillazioni casuali.
