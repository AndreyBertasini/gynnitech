# Fondamenti di ClickHouse


ClickHouse è un database OLAP (Online Analytical Processing) colonnare, progettato per query analitiche su miliardi di righe in millisecondi.


## Perché ClickHouse?


| Caratteristica                | Database Tradizionale (MySQL/Postgres) | ClickHouse             |
| ----------------------------- | -------------------------------------- | ---------------------- |
| **Orientamento**              | Per riga (row-based)                   | Per colonna (columnar) |
| **Caso d'uso**                | OLTP (transazioni)                     | OLAP (analisi)         |
| **INSERT singola riga**       | Veloce                                 | Lento (batch!)         |
| **Query su milioni di righe** | Lento                                  | Estremamente veloce    |
| **Compressione**              | Moderata                               | Eccellente (10-40x)    |


## Architettura Colonnare


In un database row-based, i dati vengono salvati riga per riga:


```plain text
| id | name   | revenue | date       |
| 1  | Google | 5000    | 2025-01-01 |
| 2  | Meta   | 3200    | 2025-01-01 |
```


In ClickHouse, i dati vengono salvati **colonna per colonna**:


```plain text
id:      [1, 2, 3, 4, ...]
name:    [Google, Meta, TikTok, ...]
revenue: [5000, 3200, 1800, ...]
date:    [2025-01-01, 2025-01-01, ...]
```


Questo significa che una query come `SELECT SUM(revenue) FROM campaigns` legge SOLO la colonna `revenue`, ignorando tutto il resto → velocità estrema.


## MergeTree Engine


Il motore di storage più usato:


```sql
CREATE TABLE campaign_events (
    event_date Date,
    campaign_id UInt32,
    source String,
    clicks UInt32,
    impressions UInt32,
    spend Decimal(10,2),
    conversions UInt16
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_date)
ORDER BY (campaign_id, event_date)
SETTINGS index_granularity = 8192;
```


### Elementi chiave:

- **PARTITION BY:** Divide i dati in partizioni (per mese, giorno). Velocizza la cancellazione e le query con filtri temporali.
- **ORDER BY:** L'ordine fisico dei dati su disco. Le query filtrate per queste colonne sono fulminee.
- **index_granularity:** Ogni quante righe ClickHouse crea un'entry nell'indice sparse.

## Query Base


```sql
-- Totale spesa per canale nell'ultimo mese
SELECT
    source,
    SUM(spend) AS total_spend,
    SUM(clicks) AS total_clicks,
    SUM(conversions) AS total_conversions,
    round(SUM(spend) / SUM(conversions), 2) AS cpa
FROM campaign_events
WHERE event_date >= today() - 30
GROUP BY source
ORDER BY total_spend DESC;
```


## Tipi di Dati Importanti


| Tipo                     | Uso                          | Esempio                 |
| ------------------------ | ---------------------------- | ----------------------- |
| `UInt32`                 | Numeri interi positivi       | clicks, impressions     |
| `Float64`                | Numeri decimali              | revenue, CPA            |
| `String`                 | Testo                        | campaign_name           |
| `Date`                   | Solo data                    | 2025-01-15              |
| `DateTime`               | Data + ora                   | 2025-01-15 14:30:00     |
| `LowCardinality(String)` | Testo con pochi valori unici | country, channel        |
| `Nullable(UInt32)`       | Può essere NULL              | Da evitare se possibile |

> 
>
> **Best Practice:** Usa `LowCardinality(String)` per colonne con pochi valori distinti (channel, country, status). Compressione e performance migliorano drasticamente.
