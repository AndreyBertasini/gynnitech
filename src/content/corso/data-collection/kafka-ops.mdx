# Kafka in Produzione: Monitoring e Troubleshooting


## Metriche Critiche di Kafka


### Broker Metrics


| Metrica JMX                      | Significato                                 | Soglia Alert    |
| -------------------------------- | ------------------------------------------- | --------------- |
| `UnderReplicatedPartitions`      | Partizioni con repliche non sincronizzate   | > 0 per > 5 min |
| `ActiveControllerCount`          | Numero di controller attivi (deve essere 1) | != 1            |
| `OfflinePartitionsCount`         | Partizioni senza leader                     | > 0             |
| `RequestHandlerAvgIdlePercent`   | CPU disponibile per request handler         | < 0.3 (30%)     |
| `NetworkProcessorAvgIdlePercent` | CPU disponibile per network I/O             | < 0.3           |
| `LogFlushRateAndTimeMs`          | Tempo di flush su disco                     | p99 > 1000ms    |


### Producer Metrics


| Metrica                  | Significato                   | Soglia Alert                  |
| ------------------------ | ----------------------------- | ----------------------------- |
| `record-send-rate`       | Messaggi inviati/secondo      | -50% dalla baseline           |
| `record-error-rate`      | Errori di invio/secondo       | > 0 prolungato                |
| `request-latency-avg`    | Latenza media delle richieste | > 100ms                       |
| `batch-size-avg`         | Dimensione media del batch    | Troppo piccola = inefficiente |
| `buffer-available-bytes` | Buffer memory disponibile     | < 20% del totale              |


### Consumer Metrics


| Metrica                   | Significato                      | Soglia Alert        |
| ------------------------- | -------------------------------- | ------------------- |
| `records-lag-max`         | Max lag in record per partizione | > 10.000            |
| `records-consumed-rate`   | Record consumati/secondo         | -50% dalla baseline |
| `commit-latency-avg`      | Latenza media del commit         | > 500ms             |
| `rebalance-rate-per-hour` | Rebalance all'ora                | > 2                 |
| `fetch-latency-avg`       | Latenza media del fetch          | > 500ms             |

### Configurazione JMX Exporter


```yaml
# jmx_exporter_config.yml
lowercaseOutputName: true
rules:
  # Broker metrics
  - pattern: kafka.server<type=ReplicaManager, name=UnderReplicatedPartitions><>Value
    name: kafka_server_under_replicated_partitions
    type: GAUGE

  # Topic metrics
  - pattern: kafka.server<type=BrokerTopicMetrics, name=(MessagesInPerSec|BytesInPerSec|BytesOutPerSec), topic=(.+)><>OneMinuteRate
    name: kafka_topic_$1
    type: GAUGE
    labels:
      topic: $2

  # Consumer group lag
  - pattern: kafka.server<type=FetcherLagMetrics, name=ConsumerLag, clientId=(.+), topic=(.+), partition=(.+)><>Value
    name: kafka_consumer_lag
    type: GAUGE
    labels:
      client_id: $1
      topic: $2
      partition: $3
```


### Alert Rules per Prometheus


```yaml
# kafka-alerts.yml
groups:
  - name: kafka_alerts
    rules:
      - alert: KafkaUnderReplicatedPartitions
        expr: kafka_server_under_replicated_partitions > 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Kafka ha partizioni sotto-replicate"

      - alert: KafkaConsumerLagHigh
        expr: kafka_consumer_lag > 10000
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "Consumer lag alto per il gruppo {{ $labels.consumer_group }}"

      - alert: KafkaNoActiveController
        expr: kafka_server_active_controller_count != 1
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Nessun controller attivo nel cluster Kafka"

      - alert: KafkaThroughputDrop
        expr: rate(kafka_topic_MessagesInPerSec{topic="marketing.events"}[5m]) < 100
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Throughput in calo sul topic marketing.events"
```

```bash

kcat -b kafka:9092 -t marketing.events -C -c 10 -o end

echo '{"event_type":"test","user_id":1}' | \
  kcat -b kafka:9092 -t marketing.events -P
```

## Troubleshooting: Problemi Comuni


### Consumer Lag in Crescita


```plain text
DIAGNOSI:
  1. Il consumer è più lento del producer?
     → Aumenta kafka_num_consumers in ClickHouse
     → Aumenta le partizioni del topic

  2. Consumer in continuo rebalance?
     → Aumenta session.timeout.ms
     → Verifica che i consumer non crashino

  3. ClickHouse non tiene il passo?
     → Verifica INSERT performance (system.query_log)
     → Ottimizza la target table (batch size, MV)
```


### Partition Skew (Distribuzione Non Uniforme)


```plain text
SINTOMI: Alcune partizioni hanno molto più lag di altre
CAUSA: Key di partitioning mal distribuita

SOLUZIONE:
  - Verifica: kcat -b kafka:9092 -L -t marketing.events
  - Se il traffico è sbilanciato per campaign_id:
    → Usa hash(campaign_id + user_id) come key
    → O usa round-robin per distribuzione uniforme
```


### Broker Out of Memory


```plain text
SINTOMI: Broker lento o non responsivo, OOM nei log
DIAGNOSI:
  - Troppi topic/partizioni (ogni partizione usa memoria)
  - Log segment troppo grandi

SOLUZIONE:
  - Riduci il numero di partizioni dove possibile
  - Configura log.segment.bytes = 1073741824 (1GB)
  - Aumenta la heap: KAFKA_HEAP_OPTS="-Xmx6g -Xms6g"
```


## Topic Cleanup Policies


### Retention (Default)


```bash
# Mantieni i dati per 7 giorni
kafka-configs.sh --bootstrap-server kafka:9092 \
  --alter --entity-type topics --entity-name marketing.events \
  --add-config retention.ms=604800000

# Mantieni max 50GB per partizione
kafka-configs.sh --bootstrap-server kafka:9092 \
  --alter --entity-type topics --entity-name marketing.events \
  --add-config retention.bytes=53687091200
```


### Compaction


Per topic dove serve solo l'ultimo valore per key (es. stato utente):


```bash
kafka-configs.sh --bootstrap-server kafka:9092 \
  --alter --entity-type topics --entity-name user.profiles \
  --add-config cleanup.policy=compact
```


## Capacity Planning


### Formula Base


```plain text
Throughput richiesto = Eventi/secondo × Dimensione media evento
Esempio: 10.000 events/s × 500 bytes = 5 MB/s

Storage per broker = Throughput × Retention × Replication Factor
Esempio: 5 MB/s × 86400s × 7 giorni × 3 repliche = ~9 TB

Partizioni = max(Throughput / Consumer throughput, N. consumers desiderati)
Esempio: 5 MB/s / 1 MB/s per consumer = almeno 5 partizioni
```


### Sizing Raccomandato per Marketing Analytics


| Scala   | Eventi/s       | Broker | Partizioni | RAM/Broker | Disco/Broker |
| ------- | -------------- | ------ | ---------- | ---------- | ------------ |
| Piccola | < 1.000        | 3      | 6-12       | 8 GB       | 500 GB       |
| Media   | 1.000-10.000   | 3-5    | 12-30      | 16 GB      | 2 TB         |
| Grande  | 10.000-100.000 | 5-10   | 30-100     | 32 GB      | 5 TB         |


## Security Basics


### Autenticazione SASL


```plain text
# server.properties
listeners=SASL_SSL://0.0.0.0:9093
security.inter.broker.protocol=SASL_SSL
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-256
sasl.enabled.mechanisms=SCRAM-SHA-256
```


### ACL per Topic


```bash
# Permetti al consumer ClickHouse di leggere dal topic marketing
kafka-acls.sh --bootstrap-server kafka:9092 \
  --add --allow-principal User:clickhouse \
  --operation Read --topic marketing.events \
  --group clickhouse_marketing_consumer
```
