# Materialized Views Incrementali e Dictionaries


Le applicazioni moderne richiedono analytics real-time su scala: personalizzazione, dashboard operative, anomaly detection. Tradizionalmente queste richiedono pipeline ETL complesse con strumenti esterni (Spark, Flink, dbt). ClickHouse offre un'alternativa radicale: **trasformare, arricchire e aggregare i dati al momento dell'ingestione**, direttamente dentro il database.


## 1. Materialized Views: Trasformazioni on Ingest


A differenza delle MV tradizionali (che sono query salvate), le Materialized Views in ClickHouse sono **trigger di INSERT**: ogni volta che un dato viene inserito nella tabella sorgente, la MV lo trasforma e lo scrive nella tabella di destinazione.


```plain text
INSERT → Tabella Sorgente → MV (trasformazione) → Tabella Destinazione
```


### Perche Questo Cambia Tutto


| Approccio Tradizionale                                      | Approccio ClickHouse MV                                        |
| ----------------------------------------------------------- | -------------------------------------------------------------- |
| Ingestisci dati raw → ETL con Spark/dbt → Tabella aggregata | Ingestisci dati raw → MV aggrega on-ingest → Tabella aggregata |
| Latenza: minuti-ore                                         | Latenza: millisecondi                                          |
| Infrastruttura: Kafka + Spark + Scheduler                   | Infrastruttura: solo ClickHouse                                |
| Costo: $$$                                                  | Costo: $                                                       |
| Complessita: alta                                           | Complessita: bassa                                             |


### La Semantica Incrementale


Il concetto chiave e che le MV in ClickHouse sono **incrementali per natura**: processano solo i nuovi dati inseriti, non ricalcolano l'intera tabella.


```sql
-- Tabella sorgente: ogni click viene tracciato
CREATE TABLE raw_clicks (
    event_time DateTime,
    user_id UInt64,
    campaign_id UInt32,
    channel LowCardinality(String),
    page_url String,
    is_conversion UInt8,
    revenue Decimal(10, 2)
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_time)
ORDER BY (campaign_id, user_id, event_time);

-- Tabella destinazione: aggregazione oraria
CREATE TABLE campaign_metrics_hourly (
    hour DateTime,
    campaign_id UInt32,
    channel LowCardinality(String),
    clicks AggregateFunction(count, UInt8),
    unique_users AggregateFunction(uniq, UInt64),
    conversions AggregateFunction(sum, UInt8),
    total_revenue AggregateFunction(sum, Decimal(10, 2))
) ENGINE = AggregatingMergeTree()
PARTITION BY toYYYYMM(hour)
ORDER BY (hour, campaign_id, channel);

-- MV: aggrega automaticamente ogni INSERT
CREATE MATERIALIZED VIEW mv_campaign_hourly
TO campaign_metrics_hourly
AS SELECT
    toStartOfHour(event_time) AS hour,
    campaign_id,
    channel,
    countState() AS clicks,
    uniqState(user_id) AS unique_users,
    sumState(is_conversion) AS conversions,
    sumState(revenue) AS total_revenue
FROM raw_clicks
GROUP BY hour, campaign_id, channel;
```


### Query sulla Tabella Aggregata


```sql
-- Le query usano -Merge() per finalizzare gli stati aggregati
SELECT
    hour,
    campaign_id,
    channel,
    countMerge(clicks) AS total_clicks,
    uniqMerge(unique_users) AS unique_users,
    sumMerge(conversions) AS total_conversions,
    sumMerge(total_revenue) AS total_revenue,
    round(sumMerge(total_revenue) / greatest(sumMerge(conversions), 1), 2) AS revenue_per_conversion
FROM campaign_metrics_hourly
WHERE hour >= now() - INTERVAL 24 HOUR
GROUP BY hour, campaign_id, channel
ORDER BY hour DESC, total_clicks DESC;
```


## 2. Multi-Stage Materialized Views


Il vero potere emerge quando si concatenano piu MV in una pipeline:


```plain text
Raw Events
    │
    ▼
┌──────────────────┐
│  MV Stage 1:     │
│  Pulizia +       │──→ cleaned_events
│  Normalizzazione │
└──────────────────┘
    │
    ▼
┌──────────────────┐
│  MV Stage 2:     │
│  Arricchimento   │──→ enriched_events (con dati da Dictionary)
│  con Dictionaries│
└──────────────────┘
    │
    ▼
┌──────────────────┐     ┌──────────────────┐
│  MV Stage 3a:    │     │  MV Stage 3b:    │
│  Aggregazione    │     │  Anomaly         │
│  per Dashboard   │     │  Detection       │
└──────────────────┘     └──────────────────┘
    │                         │
    ▼                         ▼
campaign_metrics          anomaly_alerts
```


### Stage 1: Pulizia e Normalizzazione


```sql
-- Tabella per dati puliti
CREATE TABLE cleaned_events (
    event_time DateTime,
    user_id UInt64,
    campaign_id UInt32,
    channel LowCardinality(String),
    page_url String,
    utm_source LowCardinality(String),
    utm_medium LowCardinality(String),
    utm_campaign String,
    is_conversion UInt8,
    revenue Decimal(10, 2),
    is_bot UInt8
) ENGINE = MergeTree()
ORDER BY (campaign_id, event_time);

-- MV che filtra bot, normalizza URL e estrae parametri UTM
CREATE MATERIALIZED VIEW mv_clean_events
TO cleaned_events
AS SELECT
    event_time,
    user_id,
    campaign_id,
    lower(channel) AS channel,
    extractURLPath(page_url) AS page_url,
    extractURLParameter(page_url, 'utm_source') AS utm_source,
    extractURLParameter(page_url, 'utm_medium') AS utm_medium,
    extractURLParameter(page_url, 'utm_campaign') AS utm_campaign,
    is_conversion,
    revenue,
    multiMatchAny(page_url, ['bot', 'crawler', 'spider']) AS is_bot
FROM raw_clicks
WHERE user_id > 0
  AND event_time > '2020-01-01';
```


### Stage 2: Arricchimento con Dictionary


```sql
-- MV che arricchisce con dati dalla dimensione campaign
CREATE MATERIALIZED VIEW mv_enrich_events
TO enriched_events
AS SELECT
    event_time,
    user_id,
    campaign_id,
    channel,
    page_url,
    -- Arricchimento da Dictionary
    dictGet('campaign_dict', 'campaign_name', campaign_id) AS campaign_name,
    dictGet('campaign_dict', 'budget', campaign_id) AS campaign_budget,
    dictGet('campaign_dict', 'team', campaign_id) AS team,
    is_conversion,
    revenue
FROM cleaned_events
WHERE is_bot = 0;
```


## 3. Dictionaries: Arricchimento a Velocita di Lookup


I Dictionaries di ClickHouse sono strutture dati in-memory ottimizzate per lookup chiave-valore. Sono il modo ideale per arricchire i dati in streaming senza fare JOIN costosi.


### Perche i Dictionary Invece dei JOIN


| Aspetto           | JOIN su tabella                             | Dictionary Lookup                         |
| ----------------- | ------------------------------------------- | ----------------------------------------- |
| **Latenza**       | Proporzionale alla dimensione della tabella | Costante (hashmap in-memory)              |
| **RAM**           | Usa RAM durante la query                    | Pre-caricato in RAM                       |
| **Aggiornamento** | Sempre aggiornato                           | Aggiornato periodicamente (configurabile) |
| **Use Case**      | Tabelle grandi, analisi ad-hoc              | Dimensioni piccole-medie (< 10M righe)    |


### Creare un Dictionary da una Tabella ClickHouse


```sql
-- Tabella sorgente con i dati delle campagne
CREATE TABLE dim_campaigns (
    campaign_id UInt32,
    campaign_name String,
    team LowCardinality(String),
    budget Decimal(10, 2),
    start_date Date,
    end_date Date,
    status LowCardinality(String),
    updated_at DateTime DEFAULT now()
) ENGINE = ReplacingMergeTree(updated_at)
ORDER BY campaign_id;

-- Dictionary che legge dalla tabella
CREATE DICTIONARY campaign_dict (
    campaign_id UInt32,
    campaign_name String,
    team String,
    budget Decimal(10, 2),
    start_date Date,
    end_date Date,
    status String
)
PRIMARY KEY campaign_id
SOURCE(CLICKHOUSE(
    TABLE 'dim_campaigns'
    DB 'marketing'
))
LAYOUT(FLAT())
LIFETIME(MIN 60 MAX 120);
```


### Tipi di Layout


| Layout                 | Descrizione               | Dimensione Consigliata           | Lookup          |
| ---------------------- | ------------------------- | -------------------------------- | --------------- |
| `FLAT()`               | Array sequenziale         | < 500K chiavi numeriche          | O(1)            |
| `HASHED()`             | Hashmap                   | < 10M chiavi                     | O(1)            |
| `RANGE_HASHED()`       | Hashmap con range di date | Range temporali                  | O(1)            |
| `COMPLEX_KEY_HASHED()` | Chiave composta           | Chiavi multi-colonna             | O(1)            |
| `CACHE()`              | Cache LRU                 | Dataset enormi, accesso parziale | O(1) miss: O(n) |
| `IP_TRIE()`            | Albero per IP/subnet      | Geo-lookup da IP                 | O(log n)        |


### Dictionary da Sorgenti Esterne


```sql
-- Dictionary da PostgreSQL (es. dati CRM)
CREATE DICTIONARY user_segments_dict (
    user_id UInt64,
    segment LowCardinality(String),
    ltv Decimal(10, 2),
    signup_date Date,
    country LowCardinality(String)
)
PRIMARY KEY user_id
SOURCE(POSTGRESQL(
    PORT 5432
    HOST 'crm-db.internal'
    USER 'readonly'
    PASSWORD 'secret'
    DB 'crm'
    TABLE 'user_segments'
))
LAYOUT(HASHED())
LIFETIME(MIN 300 MAX 600);
```


### Usare i Dictionary nelle Query


```sql
-- Arricchire una query con dati da Dictionary
SELECT
    campaign_id,
    dictGet('campaign_dict', 'campaign_name', campaign_id) AS campaign_name,
    dictGet('campaign_dict', 'team', campaign_id) AS team,
    count() AS total_clicks,
    uniq(user_id) AS unique_users,
    sum(revenue) AS total_revenue
FROM raw_clicks
WHERE event_time >= today()
GROUP BY campaign_id
ORDER BY total_revenue DESC
LIMIT 20;

-- Arricchire con dati utente
SELECT
    campaign_id,
    dictGet('user_segments_dict', 'segment', user_id) AS user_segment,
    count() AS clicks,
    sum(revenue) AS revenue
FROM raw_clicks
WHERE event_time >= today()
GROUP BY campaign_id, user_segment
ORDER BY revenue DESC;
```


## 4. Pattern Avanzato: Anomaly Detection on Ingest


Combinando MV e Dictionaries puoi rilevare anomalie in tempo reale:


```sql
-- Tabella per alert di anomalie
CREATE TABLE anomaly_alerts (
    detected_at DateTime DEFAULT now(),
    campaign_id UInt32,
    campaign_name String,
    metric_name LowCardinality(String),
    current_value Float64,
    expected_value Float64,
    deviation_pct Float64,
    severity LowCardinality(String)
) ENGINE = MergeTree()
ORDER BY (detected_at, campaign_id);

-- MV che rileva anomalie basate su deviazione dalla media
CREATE MATERIALIZED VIEW mv_anomaly_detection
TO anomaly_alerts
AS
WITH
    toStartOfHour(event_time) AS hour,
    count() AS current_clicks,
    -- Media delle ultime 4 settimane per la stessa ora e giorno
    (
        SELECT avg(click_count) FROM campaign_metrics_hourly_simple
        WHERE campaign_id = raw_clicks.campaign_id
          AND toHour(hour) = toHour(raw_clicks.event_time)
          AND toDayOfWeek(hour) = toDayOfWeek(raw_clicks.event_time)
          AND hour >= now() - INTERVAL 28 DAY
    ) AS expected_clicks
SELECT
    now() AS detected_at,
    campaign_id,
    dictGet('campaign_dict', 'campaign_name', campaign_id) AS campaign_name,
    'clicks_per_hour' AS metric_name,
    current_clicks AS current_value,
    expected_clicks AS expected_value,
    round(abs(current_clicks - expected_clicks) / greatest(expected_clicks, 1) * 100, 2) AS deviation_pct,
    multiIf(
        deviation_pct > 200, 'critical',
        deviation_pct > 100, 'warning',
        'info'
    ) AS severity
FROM raw_clicks
GROUP BY campaign_id, hour
HAVING deviation_pct > 50;
```


## 5. Pattern: Personalizzazione Real-Time


```sql
-- Aggregazione per profilo utente in tempo reale
CREATE TABLE user_realtime_profile (
    user_id UInt64,
    last_seen SimpleAggregateFunction(max, DateTime),
    total_clicks SimpleAggregateFunction(sum, UInt32),
    total_conversions SimpleAggregateFunction(sum, UInt32),
    total_revenue SimpleAggregateFunction(sum, Decimal(10, 2)),
    favorite_channel AggregateFunction(topK(1), LowCardinality(String)),
    recent_campaigns AggregateFunction(groupUniqArray(10), UInt32)
) ENGINE = AggregatingMergeTree()
ORDER BY user_id;

CREATE MATERIALIZED VIEW mv_user_profile
TO user_realtime_profile
AS SELECT
    user_id,
    maxSimpleState(event_time) AS last_seen,
    sumSimpleState(toUInt32(1)) AS total_clicks,
    sumSimpleState(toUInt32(is_conversion)) AS total_conversions,
    sumSimpleState(revenue) AS total_revenue,
    topKState(1)(channel) AS favorite_channel,
    groupUniqArrayState(10)(campaign_id) AS recent_campaigns
FROM raw_clicks
GROUP BY user_id;
```


```sql
-- Query per personalizzazione: profilo utente in < 10ms
SELECT
    user_id,
    maxSimpleMerge(last_seen) AS last_seen,
    sumSimpleMerge(total_clicks) AS total_clicks,
    sumSimpleMerge(total_conversions) AS total_conversions,
    sumSimpleMerge(total_revenue) AS total_revenue,
    topKMerge(1)(favorite_channel) AS favorite_channel,
    groupUniqArrayMerge(10)(recent_campaigns) AS recent_campaigns
FROM user_realtime_profile
WHERE user_id = 12345
GROUP BY user_id;
```


## 6. Ottimizzazione e Best Practices


### Performance delle MV


| Pratica                                           | Impatto                              | Dettaglio                            |
| ------------------------------------------------- | ------------------------------------ | ------------------------------------ |
| Usa `AggregatingMergeTree`                        | Aggregazioni incrementali efficienti | Evita ricalcolo completo             |
| `SimpleAggregateFunction` per operazioni semplici | Meno overhead di `AggregateFunction` | Usa per sum, max, min, any           |
| Limita le colonne nella MV                        | Meno I/O                             | Seleziona solo le colonne necessarie |
| `PARTITION BY toYYYYMM()` sulla target            | Pruning efficiente                   | Query su range di date               |
| Non creare troppe MV su una tabella               | CPU durante INSERT                   | Max 5-7 MV per tabella sorgente      |


### Monitoring delle MV


```sql
-- Verificare lo stato delle MV
SELECT
    name,
    engine,
    total_rows,
    total_bytes,
    formatReadableSize(total_bytes) AS size
FROM system.tables
WHERE engine LIKE '%Aggregating%'
ORDER BY total_bytes DESC;

-- Verificare la latenza di ingestione
SELECT
    table,
    database,
    event_type,
    event_time,
    duration_ms,
    written_rows,
    written_bytes
FROM system.part_log
WHERE table = 'campaign_metrics_hourly'
ORDER BY event_time DESC
LIMIT 20;
```
