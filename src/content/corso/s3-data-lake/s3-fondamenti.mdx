# S3 fondamenti: storage per l'analisi dati

Nel 2018, Netflix migrò l'intero data warehouse da Teradata a S3 + Presto. La bolletta passò da milioni a centinaia di migliaia di dollari all'anno. Il motivo: lo storage su S3 costa ~$23/TB/mese, mentre un data warehouse tradizionale costa 10-50 volte di più. Oggi S3 (e i suoi equivalenti: GCS, Azure Blob) è il fondamento di ogni architettura dati moderna. Ma S3 non è un database: è un filesystem infinito. Come organizzi i file determina se le query ci mettono secondi o minuti.

## S3 come data lake: disaccoppiare storage e compute

Il data lake separa due cose che i data warehouse tradizionali tenevano insieme:
- **Storage**: file su S3 in formato Parquet/ORC/Avro (economici, scalabili all'infinito)
- **Compute**: motori di query (Athena, Presto, Trino, Spark) che leggono da S3 e paghi solo per query

Questo disaccoppiamento è il superpotere dell'architettura moderna. Puoi avere 50 TB di dati su S3 (costo: ~$1.200/mese) e usare Athena per query ad-hoc (costo: $5 per TB scansionato). Se scaldi e tieni tutto su Snowflake, costerebbe ~$10.000+/mese.

## Organizzazione dei dati: partizionamento

La struttura delle directory su S3 è il tuo indice primario. La convenzione standard:

```
s3://data-lake/
  └── orders/
       ├── year=2024/
       │    ├── month=01/
       │    │    └── data.parquet
       │    └── month=02/
       └── year=2023/
```

Con `year=` e `month=` come prefisso, motori come Athena e Trino applicano automaticamente il **partition pruning**: una query per gennaio 2024 legge SOLO la directory `year=2024/month=01/`, ignorando tutte le altre. Su 5 anni di dati, la scansione si riduce del 95%.

**Regola**: partiziona per la colonna più frequentemente filtrata. Per dati di eventi, è sempre la data. Per dati di clienti, potrebbe essere `country`. Scegli partizioni che producono ~100-500 MB di dati ciascuna — né troppo piccole (overhead di listing) né troppo grandi (scansione eccessiva).

## Formati di file: Parquet è il re

| Formato | Compressione | Schema embedded | Splittabile | Supporto query engine |
|---------|-------------|-----------------|-------------|----------------------|
| **CSV/JSON** | Bassa | No | No | Universale (lento) |
| **Parquet** | Alta (Snappy, Zstd) | Sì | Sì (row groups) | Universale |
| **ORC** | Alta | Sì | Sì | Hive/Spark/Trino |
| **Avro** | Media | Sì | Sì | Kafka, streaming |

**Parquet** è lo standard per i data lake. È colonnare (legge solo le colonne che ti servono), compresso (3-10x più piccolo di JSON), e ha statistiche incorporate (min/max per ogni row group → il query engine salta interi blocchi se non rilevanti).

```sql
-- Athena: crea tabella partizionata
CREATE EXTERNAL TABLE orders (
    order_id STRING, customer_id STRING,
    amount DOUBLE, order_date DATE
) PARTITIONED BY (year INT, month INT)
STORED AS PARQUET
LOCATION 's3://data-lake/orders/';

-- Carica metadata partizioni
MSCK REPAIR TABLE orders;
```

## Controllo di qualità

Prima di usare \"s3 fondamenti: storage per l'analisi dati\ in una decisione, controlla sempre completezza, duplicati, timezone, definizioni cambiate e segmenti esclusi. Molte analisi apparentemente sofisticate falliscono perché il dato di partenza misura un comportamento diverso da quello che il team crede di osservare.


## Interpretazione per segmenti

La media aggregata è solo il punto di partenza. Segmenta per canale, coorte, piano, paese, device e maturità dell'utente. Se due segmenti si muovono in direzioni opposte, la media non rappresenta nessuno dei due e può portare a una decisione sbagliata.


## Decisione operativa

Ogni analisi deve terminare con una scelta possibile: continuare, fermare, iterare, investire, rimuovere o approfondire. Se \"s3 fondamenti: storage per l'analisi dati\ non cambia una decisione, probabilmente manca ancora il collegamento tra metrica e azione.


## Metriche di verifica

Dopo l'intervento, definisci una metrica primaria e due guardrail. La metrica primaria misura il miglioramento atteso; le guardrail impediscono di ottenere quel miglioramento distruggendo retention, fiducia, qualità del dato o sostenibilità operativa.
