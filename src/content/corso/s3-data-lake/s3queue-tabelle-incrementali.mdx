# S3Queue e Tabelle Incrementali


Il problema fondamentale: hai file che arrivano continuamente su S3 (export da API, log, eventi marketing) e vuoi che ClickHouse li processi **automaticamente**, importando solo i file nuovi. La risposta e' **S3Queue** — un engine che trasforma S3 in una coda di messaggi.


## Il Problema: Importazione Manuale vs Automatica


### L'Approccio Manuale (Quello che Facciamo di Solito)


```sql
-- Ogni giorno eseguiamo manualmente:
INSERT INTO events
SELECT * FROM s3(
    'https://s3.eu-west-1.amazonaws.com/lake/events/date=2024-01-15/*.parquet',
    'Parquet'
);

-- Domani cambiamo la data:
INSERT INTO events
SELECT * FROM s3(
    'https://s3.eu-west-1.amazonaws.com/lake/events/date=2024-01-16/*.parquet',
    'Parquet'
);
```


**Problemi:**
- Devi ricordarti di eseguire la query ogni giorno
- Se dimentichi un giorno, perdi i dati
- Se esegui due volte, duplichi i dati
- Non scala con centinaia di file al giorno


### L'Approccio Automatico: S3Queue


```plain text
┌──────────────┐     ┌──────────────┐     ┌────────────────┐
│  File su S3  │────▶│   S3Queue    │────▶│  Materialized  │
│  (continui)  │     │   Engine     │     │  View          │
└──────────────┘     └──────────────┘     └───────┬────────┘
                     Traccia i file                │
                     gia' processati               ▼
                                          ┌────────────────┐
                                          │  MergeTree     │
                                          │  (destinazione)│
                                          └────────────────┘
```


S3Queue:
- Monitora S3 per file nuovi (polling periodico)
- Traccia quali file sono gia' stati processati (via ZooKeeper/Keeper)
- Non riprocessa mai lo stesso file
- Funziona in background, senza intervento manuale


## Creare una Pipeline Incrementale da Zero


Costruiamo passo per passo una pipeline completa per eventi marketing.


### Step 1: La Tabella Sorgente (S3Queue)


```sql
CREATE TABLE events_queue (
    event_id String,
    user_id String,
    event_name String,
    event_timestamp DateTime,
    page_url String,
    campaign_source Nullable(String),
    campaign_medium Nullable(String),
    revenue Nullable(Decimal(10, 2))
) ENGINE = S3Queue(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/raw/events/*.parquet',
    'Parquet'
) SETTINGS
    mode = 'unordered',
    after_processing = 'keep',
    keeper_path = '/clickhouse/s3queue/marketing_events',
    loading_retries = 3,
    polling_min_timeout_ms = 5000,
    polling_max_timeout_ms = 30000;
```


Ogni parametro ha un ruolo preciso:


| Setting                    | Valore      | Significato                                                 |
| -------------------------- | ----------- | ----------------------------------------------------------- |
| `mode`                     | `unordered` | Processa file in qualsiasi ordine di arrivo                 |
| `after_processing`         | `keep`      | Lascia i file su S3 dopo il processing                      |
| `keeper_path`              | (unico)     | Path ZooKeeper per tracciare lo stato — **deve essere unico per tabella** |
| `loading_retries`          | `3`         | Riprova 3 volte se un file fallisce                         |
| `polling_min_timeout_ms`   | `5000`      | Controlla nuovi file ogni 5 secondi (minimo)                |
| `polling_max_timeout_ms`   | `30000`     | Controlla nuovi file ogni 30 secondi (massimo)              |


### Step 2: La Tabella Destinazione (MergeTree)


```sql
CREATE TABLE events (
    event_id String,
    user_id String,
    event_name String,
    event_timestamp DateTime,
    page_url String,
    campaign_source Nullable(String),
    campaign_medium Nullable(String),
    revenue Nullable(Decimal(10, 2)),
    -- Colonne calcolate
    event_date Date DEFAULT toDate(event_timestamp),
    event_hour UInt8 DEFAULT toHour(event_timestamp),
    ingested_at DateTime DEFAULT now()
) ENGINE = MergeTree
PARTITION BY toYYYYMM(event_timestamp)
ORDER BY (event_date, event_name, user_id)
SETTINGS index_granularity = 8192;
```


La tabella MergeTree e' dove i dati vivranno per le query. Nota le colonne calcolate:
- `event_date` e `event_hour`: utili per filtri rapidi
- `ingested_at`: quando il record e' stato importato (debugging)


### Step 3: La Materialized View (Collegamento)


```sql
CREATE MATERIALIZED VIEW events_consumer TO events AS
SELECT
    event_id,
    user_id,
    event_name,
    event_timestamp,
    page_url,
    campaign_source,
    campaign_medium,
    revenue
FROM events_queue;
```


<Aside type="tip">
La Materialized View e' il "collante" tra S3Queue e MergeTree. Quando la crei, S3Queue inizia automaticamente a processare i file e inserire i dati nella tabella destinazione.
</Aside>


### Come Funziona il Flusso


```plain text
1. Un file nuovo appare su S3:
   s3://marketing-lake/raw/events/events_2024_01_15_001.parquet

2. S3Queue lo rileva al prossimo polling (5-30 sec)

3. S3Queue legge il file e passa le righe alla Materialized View

4. La Materialized View inserisce le righe nella tabella 'events'

5. S3Queue registra il file come "processato" in ZooKeeper

6. Il file NON verra' riprocessato (anche se ClickHouse riavvia)
```


## Processing Modes: Ordered vs Unordered


### Unordered Mode


```sql
ENGINE = S3Queue(...) SETTINGS mode = 'unordered'
```


- Processa file in **qualsiasi ordine** di arrivo
- Traccia **ogni file** individualmente in ZooKeeper
- I file possono avere nomi casuali
- Supporta `processing_threads_num` per parallelismo


**Usa quando:** I file arrivano con nomi casuali (UUID, hash), l'ordine non importa.


```plain text
Esempio:
s3://lake/events/
├── abc123.parquet      ← processato 2°
├── xyz789.parquet      ← processato 1°
├── def456.parquet      ← processato 3°
└── new_file.parquet    ← in attesa
```


### Ordered Mode


```sql
ENGINE = S3Queue(...) SETTINGS mode = 'ordered'
```


- Processa file in **ordine lessicografico** (alfabetico)
- Traccia solo il **nome dell'ultimo file processato** in ZooKeeper
- File con nomi "precedenti" all'ultimo processato vengono **ignorati**
- Meno overhead su ZooKeeper


**Usa quando:** I file hanno nomi ordinabili per data/tempo.


```plain text
Esempio (ordinato lessicograficamente):
s3://lake/events/
├── events_2024_01_13.parquet    ← gia' processato
├── events_2024_01_14.parquet    ← gia' processato
├── events_2024_01_15.parquet    ← ultimo processato (registrato in ZK)
├── events_2024_01_16.parquet    ← prossimo da processare
└── events_2024_01_17.parquet    ← in attesa
```


<Aside type="caution">
In ordered mode, se aggiungi un file con nome lessicograficamente inferiore all'ultimo processato (es. `events_2024_01_12.parquet`), viene **ignorato silenziosamente**. Assicurati che i nomi dei file siano sempre crescenti.
</Aside>


### Quale Mode Scegliere?


| Criterio                       | Unordered              | Ordered                 |
| ------------------------------ | ---------------------- | ----------------------- |
| Nomi file                      | Casuali (UUID, hash)   | Ordinabili (date, seq)  |
| ZooKeeper overhead             | Alto (un nodo/file)    | Basso (un solo nodo)    |
| Parallelismo                   | Nativo (multi-thread)  | Limitato                |
| File fuori ordine              | Nessun problema        | Ignorati!               |
| Marketing events (date-based)  | Funziona               | Ideale                  |
| API webhooks (random)          | Ideale                 | Non adatto              |


## After-Processing Actions


Cosa succede ai file su S3 dopo che S3Queue li ha processati?


### Keep (Default)


```sql
SETTINGS after_processing = 'keep'
```


I file restano su S3 invariati. Utile quando:
- Altri sistemi devono accedere agli stessi file
- Vuoi mantenere i raw data come backup
- Policy di retention richiedono di conservare i dati originali


### Delete


```sql
SETTINGS after_processing = 'delete'
```


I file vengono cancellati da S3 dopo il processing. Utile quando:
- I file sono temporanei (staging area)
- Non vuoi pagare storage per file gia' importati
- I dati originali esistono in un'altra posizione


### Move


```sql
-- Spostare in un prefisso nello stesso bucket
SETTINGS
    after_processing = 'move',
    after_processing_move_prefix = 'processed/'

-- Spostare in un bucket diverso
SETTINGS
    after_processing = 'move',
    after_processing_move_uri = 'https://archive-bucket.s3.amazonaws.com/'
```


I file vengono spostati in una directory "processed". La soluzione migliore per la maggior parte dei casi:
- I file raw vengono organizzati automaticamente
- Puoi distinguere file processati da non processati
- Nessun dato perso


### Tag


```sql
SETTINGS
    after_processing = 'tag',
    after_processing_tag_key = 'clickhouse_processed',
    after_processing_tag_value = 'true'
```


Aggiunge un tag S3 al file. Utile con S3 lifecycle rules per archiviazione automatica.


### Strategia Consigliata per Marketing Data


```plain text
                          ┌─────────────────────┐
  File nuovi su S3   ────▶│  /raw/events/       │
  (API export, webhook)   │  *.parquet          │
                          └──────────┬──────────┘
                                     │ S3Queue processa
                                     ▼
                          ┌─────────────────────┐
  File processati    ────▶│  /processed/events/ │  after_processing = 'move'
                          │  *.parquet          │
                          └──────────┬──────────┘
                                     │ S3 Lifecycle Rule (90 giorni)
                                     ▼
                          ┌─────────────────────┐
  Archivio           ────▶│  S3 Glacier         │  Costo ~$0.004/GB/mese
                          └─────────────────────┘
```


## Parallelismo e Performance


### Processing Threads (Unordered Mode)


```sql
CREATE TABLE events_queue (...)
ENGINE = S3Queue(...)
SETTINGS
    mode = 'unordered',
    processing_threads_num = 16;  -- Default: numero CPU
```


Ogni thread processa un file alla volta. Con 16 thread e file da 100 MB, puoi importare ~1.6 GB in parallelo.


### Buckets per Ordered Mode Distribuito


In un cluster con piu' repliche che condividono lo stesso `keeper_path`:


```sql
-- Formula: buckets = num_repliche x processing_threads
-- Esempio: 3 repliche, 16 thread ciascuna
SETTINGS
    mode = 'ordered',
    buckets = 48,
    keeper_path = '/clickhouse/s3queue/shared_events'
```


I file vengono assegnati ai bucket tramite hash del nome, e ogni thread di ogni replica tenta di acquisire il lock su un bucket.


## Monitoring e Debugging


### Cache in Memoria


```sql
-- Vedere lo stato corrente dei file
SELECT
    file_name,
    rows_processed,
    status,
    processing_start_time,
    processing_end_time,
    exception
FROM system.s3queue
WHERE database = 'default' AND table = 'events_queue'
ORDER BY processing_start_time DESC
LIMIT 20;
```


| Status       | Significato                    |
| ------------ | ------------------------------ |
| `Processed`  | File importato con successo    |
| `Processing` | File in corso di importazione  |
| `Failed`     | File fallito (vedi `exception`)|


### Log Persistente


Configura il log persistente per storicizzare lo stato:


```xml
<!-- /etc/clickhouse-server/config.d/s3queue_log.xml -->
<clickhouse>
    <s3queue_log>
        <database>system</database>
        <table>s3queue_log</table>
    </s3queue_log>
</clickhouse>
```


```sql
-- Quanti file processati nell'ultima ora?
SELECT
    status,
    count() AS files,
    sum(rows_processed) AS total_rows
FROM system.s3queue_log
WHERE event_time ≥ now() - INTERVAL 1 HOUR
  AND database = 'default'
  AND table = 'events_queue'
GROUP BY status;

-- File falliti con dettaglio errore
SELECT
    event_time,
    file_name,
    rows_processed,
    exception
FROM system.s3queue_log
WHERE status = 'Failed'
ORDER BY event_time DESC
LIMIT 10;
```


## Gestione degli Errori


### Righe Duplicate

Le righe duplicate possono verificarsi quando:

1. Un file fallisce a meta' lettura e viene riprovato
2. La sessione ZooKeeper scade prima che il file venga marcato come processato
3. Il server si arresta durante il processing

**Mitigazione con ReplacingMergeTree:**

```sql
-- Usare ReplacingMergeTree per deduplicazione automatica
CREATE TABLE events_dedup (
    event_id String,
    user_id String,
    event_name String,
    event_timestamp DateTime,
    revenue Nullable(Decimal(10, 2)),
    -- versione per deduplicazione
    _version UInt64 DEFAULT toUnixTimestamp(now())
) ENGINE = ReplacingMergeTree(_version)
PARTITION BY toYYYYMM(event_timestamp)
ORDER BY (event_id);  -- Deduplicazione per event_id

-- La Materialized View punta alla tabella con deduplicazione
CREATE MATERIALIZED VIEW events_consumer TO events_dedup AS
SELECT * FROM events_queue;

-- Query con deduplicazione forzata
SELECT event_name, count()
FROM events_dedup
FINAL  -- Forza la deduplicazione al momento della query
GROUP BY event_name;
```


<Aside type="caution">
`FINAL` ha un costo di performance. Per query frequenti, preferisci eseguire `OPTIMIZE TABLE events_dedup FINAL` periodicamente e fare query senza `FINAL`.
</Aside>


### Retry Policy


```sql
SETTINGS
    loading_retries = 3,              -- Riprova 3 volte
    after_processing = 'move',        -- Sposta solo se successo
    after_processing_retries = 20     -- Riprova lo spostamento 20 volte
```


## Esempio Completo: Pipeline Marketing Events


Mettiamo tutto insieme per una pipeline di produzione:


```sql
-- 1. Tabella S3Queue (sorgente)
CREATE TABLE marketing_events_queue (
    event_id String,
    user_id String,
    anonymous_id String,
    event_name String,
    event_timestamp DateTime64(3),
    page_url String,
    referrer String,
    utm_source Nullable(String),
    utm_medium Nullable(String),
    utm_campaign Nullable(String),
    utm_content Nullable(String),
    utm_term Nullable(String),
    device_type String,
    country_code String,
    revenue Nullable(Decimal(10, 2))
) ENGINE = S3Queue(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/raw/events/*.parquet',
    'Parquet'
) SETTINGS
    mode = 'ordered',
    after_processing = 'move',
    after_processing_move_prefix = 'processed/events/',
    keeper_path = '/clickhouse/s3queue/prod/marketing_events',
    loading_retries = 3,
    polling_min_timeout_ms = 10000,
    polling_max_timeout_ms = 60000;

-- 2. Tabella destinazione (MergeTree)
CREATE TABLE marketing_events (
    event_id String,
    user_id String,
    anonymous_id String,
    event_name String,
    event_timestamp DateTime64(3),
    event_date Date DEFAULT toDate(event_timestamp),
    page_url String,
    referrer String,
    utm_source Nullable(String),
    utm_medium Nullable(String),
    utm_campaign Nullable(String),
    utm_content Nullable(String),
    utm_term Nullable(String),
    device_type String,
    country_code String,
    revenue Nullable(Decimal(10, 2)),
    ingested_at DateTime DEFAULT now()
) ENGINE = ReplacingMergeTree(ingested_at)
PARTITION BY toYYYYMM(event_timestamp)
ORDER BY (event_date, event_name, user_id, event_id)
TTL event_timestamp + INTERVAL 24 MONTH DELETE
SETTINGS index_granularity = 8192;

-- 3. Materialized View (collegamento)
CREATE MATERIALIZED VIEW marketing_events_consumer TO marketing_events AS
SELECT * FROM marketing_events_queue;

-- 4. Aggregazione incrementale per dashboard real-time
CREATE MATERIALIZED VIEW marketing_events_hourly
ENGINE = SummingMergeTree
PARTITION BY toYYYYMM(event_hour)
ORDER BY (event_hour, event_name, utm_source, device_type, country_code)
AS SELECT
    toStartOfHour(event_timestamp) AS event_hour,
    event_name,
    utm_source,
    device_type,
    country_code,
    count() AS event_count,
    uniqState(user_id) AS unique_users_state,
    sumState(revenue) AS revenue_state
FROM marketing_events
GROUP BY event_hour, event_name, utm_source, device_type, country_code;
```


### Query sulla Pipeline


```sql
-- Dashboard real-time: metriche ultime 24 ore
SELECT
    event_hour,
    event_name,
    sum(event_count) AS events,
    uniqMerge(unique_users_state) AS unique_users,
    sumMerge(revenue_state) AS total_revenue
FROM marketing_events_hourly
WHERE event_hour ≥ now() - INTERVAL 24 HOUR
GROUP BY event_hour, event_name
ORDER BY event_hour DESC, events DESC;

-- Monitoraggio pipeline: ultimi file processati
SELECT
    file_name,
    status,
    rows_processed,
    processing_start_time,
    processing_end_time,
    dateDiff('second', processing_start_time, processing_end_time) AS duration_sec
FROM system.s3queue_log
WHERE table = 'marketing_events_queue'
ORDER BY processing_start_time DESC
LIMIT 20;
```


## Riepilogo


Le tabelle incrementali con S3Queue sono il modo migliore per costruire pipeline dati automatiche:

- **S3Queue** monitora S3 e processa automaticamente i file nuovi
- **Ordered mode** per file con nomi date-based, **unordered** per nomi casuali
- **Materialized View** collega S3Queue alla tabella destinazione MergeTree
- **After-processing actions** (keep/delete/move/tag) gestiscono i file sorgente
- **ReplacingMergeTree** per deduplicazione automatica
- **SummingMergeTree** per aggregazioni incrementali real-time
- **system.s3queue_log** per monitoraggio e debugging

## Failure Recovery e Idempotenza in S3Queue

In un sistema di produzione, i fallimenti sono inevitabili: ClickHouse si riavvia, la sessione ZooKeeper scade, un file e' corrotto. Capire il comportamento di S3Queue in questi scenari e' fondamentale per costruire pipeline affidabili.

### Comportamento al Riavvio

Quando ClickHouse si riavvia, S3Queue recupera il suo stato da ZooKeeper/Keeper e riprende esattamente da dove si era fermato:

```plain text
Scenario: ClickHouse si riavvia mentre processa file_005.parquet

Prima del riavvio:
  file_001.parquet → Processato (registrato in ZK)
  file_002.parquet → Processato (registrato in ZK)
  file_003.parquet → Processato (registrato in ZK)
  file_004.parquet → Processato (registrato in ZK)
  file_005.parquet → In processing... ← CRASH qui

Dopo il riavvio:
  file_001.parquet → Saltato (gia' in ZK)
  file_002.parquet → Saltato (gia' in ZK)
  file_003.parquet → Saltato (gia' in ZK)
  file_004.parquet → Saltato (gia' in ZK)
  file_005.parquet → Riprocessato! ← possibili duplicati
  file_006.parquet → Processato normalmente
```

**Il rischio duplicati:** se il crash avviene dopo che i dati sono stati inseriti nella MergeTree ma prima che ZooKeeper venga aggiornato, `file_005.parquet` viene riprocessato e inserito due volte.

### Soluzione: Idempotenza con ReplacingMergeTree

```sql
-- ReplacingMergeTree garantisce che i duplicati vengano rimossi
-- La colonna version determina quale record "vince" in caso di conflitto
CREATE TABLE events_idempotent (
    -- event_id come chiave di deduplicazione
    event_id String,
    user_id String,
    event_name String,
    event_timestamp DateTime64(3),
    revenue Nullable(Decimal(10, 2)),
    -- La versione e' il timestamp di ingestione
    -- In caso di duplicato, vince il record con version maggiore
    _version UInt64 DEFAULT toUnixTimestamp64Milli(now64())
) ENGINE = ReplacingMergeTree(_version)
PARTITION BY toYYYYMM(event_timestamp)
-- ORDER BY include event_id: e' la chiave di deduplicazione
ORDER BY (event_id);

-- Materialized View con deduplicazione automatica
CREATE MATERIALIZED VIEW events_idempotent_consumer TO events_idempotent AS
SELECT
    event_id,
    user_id,
    event_name,
    event_timestamp,
    revenue,
    toUnixTimestamp64Milli(now64()) AS _version
FROM events_s3queue;

-- Query con FINAL per forzare la deduplicazione
SELECT count() FROM events_idempotent FINAL;

-- OPTIMIZE periodico per eliminare fisicamente i duplicati
-- (senza FINAL, i duplicati esistono su disco ma vengono filtrati a runtime)
OPTIMIZE TABLE events_idempotent FINAL;
```

### Idempotenza per Ordered Mode

In `ordered` mode, il rischio e' diverso: se il server crasha durante il processing, al riavvio ZooKeeper contiene l'ultimo file **completamente processato**. Il file interrotto viene riprovato dall'inizio.

```plain text
Ordered Mode - Scenario crash:

ZooKeeper state: last_processed = "events_2024_01_14.parquet"

File in S3:
  events_2024_01_13.parquet → Saltato (< last_processed)
  events_2024_01_14.parquet → Saltato (= last_processed)
  events_2024_01_15.parquet → IN PROCESSING... CRASH
  events_2024_01_16.parquet → In attesa

Dopo riavvio:
  ZooKeeper state: last_processed = "events_2024_01_14.parquet"  ← invariato
  events_2024_01_15.parquet → Riprovato dall'inizio
  (rischio duplicati solo se il crash avviene tra insert e update ZK)
```

## Monitoring delle Code S3Queue con system.s3queue_log

Il log S3Queue e' la fonte di verita' per il monitoring della pipeline. Configurarlo correttamente e interrogarlo con le query giuste permette di rilevare problemi prima che impattino gli utenti finali.

### Configurazione Completa del Log

```xml
<!-- /etc/clickhouse-server/config.d/s3queue_log.xml -->
<clickhouse>
    <s3queue_log>
        <!-- Database e tabella dove scrivere i log -->
        <database>system</database>
        <table>s3queue_log</table>
        <!-- Flush ogni 7.5 secondi -->
        <flush_interval_milliseconds>7500</flush_interval_milliseconds>
    </s3queue_log>
</clickhouse>
```

### Schema di system.s3queue_log

```sql
DESCRIBE TABLE system.s3queue_log;

-- Colonne principali:
-- event_time:           DateTime   - Quando e' stato processato il file
-- database:             String     - Database della tabella S3Queue
-- table:                String     - Nome della tabella S3Queue
-- file_name:            String     - Nome completo del file S3
-- rows_processed:       UInt64     - Righe importate con successo
-- status:               Enum       - 'Processed', 'Failed', 'Processing'
-- elapsed_ms:           UInt64     - Tempo di processing in millisecondi
-- exception:            String     - Messaggio di errore (se Failed)
-- processing_start_time: DateTime  - Inizio processing
-- processing_end_time:  DateTime   - Fine processing
```

### Query di Monitoring Essenziali

```sql
-- 1. Overview dell'ultima ora
SELECT
    status,
    count() AS files,
    sum(rows_processed) AS total_rows,
    round(avg(elapsed_ms) / 1000, 2) AS avg_duration_sec,
    round(max(elapsed_ms) / 1000, 2) AS max_duration_sec
FROM system.s3queue_log
WHERE event_time >= now() - INTERVAL 1 HOUR
  AND database = 'default'
  AND table = 'marketing_events_queue'
GROUP BY status;

-- 2. Throughput per minuto (per rilevare rallentamenti)
SELECT
    toStartOfMinute(event_time) AS minute,
    count() AS files_processed,
    sum(rows_processed) AS rows_per_minute,
    round(sum(rows_processed) / 60 / 1000, 1) AS K_rows_per_sec
FROM system.s3queue_log
WHERE event_time >= now() - INTERVAL 2 HOUR
  AND status = 'Processed'
GROUP BY minute
ORDER BY minute;

-- 3. File falliti con dettaglio errore (alert)
SELECT
    event_time,
    file_name,
    rows_processed,
    exception,
    -- Estratto del messaggio di errore
    substring(exception, 1, 200) AS error_summary
FROM system.s3queue_log
WHERE status = 'Failed'
  AND event_time >= now() - INTERVAL 24 HOUR
ORDER BY event_time DESC;

-- 4. Lag della pipeline: differenza tra file piu' vecchio non processato e ora
-- Utile per capire se la coda si sta accumulando
SELECT
    min(event_time) AS oldest_unprocessed_time,
    dateDiff('minute', min(event_time), now()) AS lag_minutes
FROM system.s3queue
WHERE database = 'default'
  AND table = 'marketing_events_queue'
  AND status = 'Processing';
```

### Dashboard di Salute della Pipeline

```sql
-- Vista unificata: salute della pipeline nelle ultime 24 ore
WITH stats AS (
    SELECT
        countIf(status = 'Processed') AS files_ok,
        countIf(status = 'Failed') AS files_failed,
        sum(rows_processed) AS total_rows,
        round(countIf(status = 'Failed') / count() * 100, 2) AS error_rate_pct,
        round(avg(elapsed_ms) / 1000, 1) AS avg_duration_sec,
        max(event_time) AS last_activity
    FROM system.s3queue_log
    WHERE event_time >= now() - INTERVAL 24 HOUR
      AND table = 'marketing_events_queue'
)

SELECT
    files_ok,
    files_failed,
    formatReadableQuantity(total_rows) AS total_rows_readable,
    concat(toString(error_rate_pct), '%') AS error_rate,
    avg_duration_sec,
    last_activity,
    CASE
        WHEN error_rate_pct > 5 THEN 'CRITICAL: troppe failure'
        WHEN dateDiff('minute', last_activity, now()) > 60 THEN 'WARNING: pipeline ferma'
        ELSE 'HEALTHY'
    END AS health_status
FROM stats;
```

## S3Queue vs Kafka → ClickHouse: Confronto per Ingestion

Una domanda comune: quando usare S3Queue e quando usare Kafka con ClickHouse come consumer?

### Architettura con Kafka

```plain text
Kafka Architecture:
Producer → Kafka Topic → ClickHouse Kafka Engine → MergeTree

Caratteristiche:
- Latenza: millisecondi (sub-second)
- Throughput: centinaia di migliaia di messaggi/sec
- Ordering garantito per partition
- Replay: si, ma con limitazioni (retention period)
- Stato: gestito da Kafka (consumer group offsets)
- Costo: istanza Kafka (MSK ~$0.21/hr per cluster minimo)
```

### Architettura con S3Queue

```plain text
S3Queue Architecture:
Producer → S3 file → S3Queue Engine → MergeTree

Caratteristiche:
- Latenza: 5-60 secondi (dipende da polling interval)
- Throughput: dipende dalla dimensione dei file
- Ordering: opzionale (ordered mode)
- Replay: si, senza limiti di tempo (i file sono su S3)
- Stato: gestito da ZooKeeper/Keeper
- Costo: solo S3 storage + S3 GET requests
```

### Quando Scegliere S3Queue

```plain text
Usa S3Queue quando:
[+] I dati arrivano gia' su S3 da sistemi esterni (API export, ETL batch)
[+] La latenza di 30-60 secondi e' accettabile
[+] Vuoi semplifita' operativa (nessun Kafka da gestire)
[+] Hai gia' una pipeline che produce file su S3
[+] Budget limitato (S3 e' piu' economico di un cluster Kafka)
[+] Hai bisogno di replay facile di file storici

Usa Kafka → ClickHouse quando:
[+] Hai bisogno di latenza sub-second (real-time vero)
[+] I dati arrivano da piu' produttori diversi
[+] Hai gia' Kafka in produzione per altri scopi
[+] Hai bisogno di fan-out (stesso dato verso piu' consumer)
[+] Il volume supera 100K messaggi/secondo
```

### Scenario Ibrido: il Meglio di Entrambi

```plain text
Architettura ibrida per massima flessibilita':

Produttore → Kafka → S3 Sink Connector → S3 file
                  ↓                           ↓
             ClickHouse                   S3Queue
             (via Kafka Engine)           (via S3Queue Engine)
             Latenza: 1 sec              Latenza: 60 sec
             Hot data: 7 giorni          Cold data: 2 anni
```

## Best Practice: Naming Convention per File S3

Il nome dei file su S3 influenza direttamente le performance di S3Queue in `ordered` mode e la leggibilita' della pipeline.

### Standard Consigliato

```plain text
Formato: {source}_{type}_{date}_{hour}_{sequence}.{format}

Esempi:
  ga4_events_20240115_08_0001.parquet     ← GA4 events, 15 gen 2024, ora 8, file 1
  meta_insights_20240115_00_0001.parquet  ← Meta Ads, daily export
  hubspot_contacts_20240115_12_0001.parquet

Vantaggi:
- Ordinamento lessicografico = ordinamento temporale
- Facile identificare source e tipo dal nome
- La sequenza (0001) garantisce unicita' per la stessa ora
- Compatible con ordered mode di S3Queue
```

### Anti-pattern da Evitare

```plain text
# SBAGLIATO: Timestamp Unix (non leggibile)
1705302000_events.parquet

# SBAGLIATO: UUID random (non ordinabile)
a3f7c9e2-4b8d-11ee-be56-0242ac120002.parquet

# SBAGLIATO: Data in formato europeo (non ordinabile)
events_15-01-2024.parquet

# SBAGLIATO: Senza padded zeros (ordinamento lessicografico errato)
events_2024_1_5.parquet   ← Viene dopo events_2024_10_1!
events_2024_01_05.parquet ← Corretto con zero-padding
```

### Script Python per Generare Nomi Conformi

```python
from datetime import datetime, timezone

def s3_file_name(
    source: str,
    data_type: str,
    sequence: int = 1,
    extension: str = "parquet",
    dt: datetime | None = None
) -> str:
    """
    Genera un nome file S3 conforme alla naming convention.
    Compatible con ordered mode di S3Queue.

    Args:
        source:    Sorgente dei dati ('ga4', 'meta', 'hubspot')
        data_type: Tipo di dato ('events', 'campaigns', 'contacts')
        sequence:  Numero sequenziale per file multipli della stessa ora
        extension: Formato del file ('parquet', 'json', 'csv')
        dt:        Datetime (default: ora corrente UTC)

    Returns:
        str: 'ga4_events_20240115_08_0001.parquet'
    """
    if dt is None:
        dt = datetime.now(timezone.utc)

    return (
        f"{source}_{data_type}_"
        f"{dt.strftime('%Y%m%d')}_{dt.strftime('%H')}_"
        f"{sequence:04d}.{extension}"
    )

# Uso nel pipeline di export:
# Nome file per il primo export GA4 dell'ora corrente
filename = s3_file_name('ga4', 'events', sequence=1)
# → 'ga4_events_20240115_08_0001.parquet'

s3_path = f"s3://marketing-lake/raw/events/{filename}"
# → 's3://marketing-lake/raw/events/ga4_events_20240115_08_0001.parquet'
```
