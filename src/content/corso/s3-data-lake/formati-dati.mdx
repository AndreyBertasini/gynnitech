# Formati Dati: Parquet, Avro, ORC e JSON


La scelta del formato dati nel data lake influenza tutto: dimensione dello storage, velocita' delle query, compatibilita' con i tool e flessibilita' nello schema. In questa lezione analizziamo i formati principali e capiamo perche' **Parquet e' il re dell'analytics**.


## Row-Oriented vs Columnar


La differenza fondamentale tra i formati dati e' come organizzano le informazioni su disco.


### Storage Row-Oriented


I formati row-oriented (CSV, JSON, Avro) salvano tutti i campi di un record uno dopo l'altro. Per leggere un record completo basta leggere un blocco contiguo.


```plain text
Record 1: | user_id=101 | event=page_view | timestamp=2024-01-15 | page=/home    |
Record 2: | user_id=102 | event=click      | timestamp=2024-01-15 | page=/pricing |
Record 3: | user_id=101 | event=purchase   | timestamp=2024-01-15 | page=/checkout|
```


**Ideale per:** inserimenti rapidi, lettura di record completi, streaming.


### Storage Columnar


I formati colonnari (Parquet, ORC) salvano tutti i valori di una colonna insieme. Per leggere una singola colonna basta leggere un blocco contiguo, saltando tutte le altre.


```plain text
Colonna user_id:    | 101 | 102 | 101 | ...
Colonna event:      | page_view | click | purchase | ...
Colonna timestamp:  | 2024-01-15 | 2024-01-15 | 2024-01-15 | ...
Colonna page:       | /home | /pricing | /checkout | ...
```


**Ideale per:** query analitiche che leggono poche colonne su molte righe.


### Impatto sulle Query Analitiche


Consideriamo una tabella con 50 colonne e 100 milioni di righe. La query tipica in analytics:


```sql
SELECT event_name, COUNT(*) AS events
FROM marketing_events
WHERE event_date = '2024-01-15'
GROUP BY event_name
```


| Aspetto                | Row-Oriented (JSON/CSV) | Columnar (Parquet)              |
| ---------------------- | ----------------------- | ------------------------------- |
| Colonne lette          | Tutte e 50              | Solo 2 (event_name, event_date) |
| Dati scansionati       | ~50 GB                  | ~2 GB (4% del totale)           |
| Tempo di lettura da S3 | ~500 secondi            | ~20 secondi                     |
| Compressione           | 2-3x                    | 10-20x                          |
| Costo S3 GET           | Alto (tutto il file)    | Basso (range read)              |


## Confronto Dettagliato dei Formati


### CSV (Comma-Separated Values)


Il formato piu' semplice e universale. Ogni riga e' un record, i campi sono separati da virgola (o altro delimitatore).


```plain text
user_id,event_name,timestamp,page_url,revenue
101,page_view,2024-01-15T08:30:00Z,/home,0
102,click,2024-01-15T08:31:00Z,/pricing,0
101,purchase,2024-01-15T08:45:00Z,/checkout,49.99
```


**Pro:** Universale, leggibile, ogni tool lo supporta.
**Contro:** Nessuno schema, nessun tipo, nessuna compressione nativa, lento per analytics.


### JSON (JavaScript Object Notation)


Formato semi-strutturato con supporto per dati annidati. Usato comunemente dalle API.


```json
{"user_id": 101, "event": "page_view", "ts": "2024-01-15T08:30:00Z", "props": {"page": "/home"}}
{"user_id": 102, "event": "click", "ts": "2024-01-15T08:31:00Z", "props": {"page": "/pricing", "cta": "signup"}}
```


**Pro:** Flessibile, supporta dati annidati, leggibile, standard per API e streaming.
**Contro:** Verboso (nomi campo ripetuti), nessuna compressione nativa, lento per analytics.


### Apache Avro


Formato row-oriented binario con schema integrato. Lo schema e' scritto in JSON nell'header del file, i dati sono codificati in binario.


```json
{
  "type": "record",
  "name": "MarketingEvent",
  "fields": [
    {"name": "user_id", "type": "long"},
    {"name": "event_name", "type": "string"},
    {"name": "timestamp", "type": {"type": "long", "logicalType": "timestamp-millis"}},
    {"name": "properties", "type": {"type": "map", "values": "string"}}
  ]
}
```


**Pro:** Schema integrato, compatto, eccellente per schema evolution, standard in Kafka.
**Contro:** Row-oriented (non ottimale per analytics), meno supportato nei tool di query.


### Apache Parquet


Formato colonnare binario progettato per l'analytics. Organizza i dati in row groups, ognuno contenente column chunks con metadata statistici.


```plain text
File Parquet
├── Magic Number (PAR1)
├── Row Group 0 (es. prime 1M righe)
│   ├── Column Chunk: user_id
│   │   ├── Page 0 (dati compressi)
│   │   └── Page 1 (dati compressi)
│   ├── Column Chunk: event_name
│   │   └── Page 0 (dati compressi + dictionary)
│   └── Column Chunk: timestamp
│       └── Page 0 (dati compressi)
├── Row Group 1 (prossime 1M righe)
│   └── ...
└── Footer
    ├── Schema
    ├── Row Group metadata
    │   ├── min/max per colonna (per pruning)
    │   ├── null count
    │   └── distinct count
    └── Magic Number (PAR1)
```


**Pro:** Colonnare (ottimo per analytics), compressione eccellente, schema integrato, metadata statistici per query pruning, supportato ovunque.
**Contro:** Non adatto per aggiornamenti singoli record, piu' complesso da scrivere.


### Apache ORC (Optimized Row Columnar)


Formato colonnare simile a Parquet, nato nell'ecosistema Hive. Offre un indice integrato piu' sofisticato e supporto nativo per le transazioni ACID in Hive.


**Pro:** Eccellente compressione, indici integrati, ACID in Hive.
**Contro:** Principalmente legato all'ecosistema Hadoop/Hive, meno supportato fuori.

| **Caso d'uso lake**    | Import iniziale | Zona raw       | Streaming/CDC   | Cleaned + Curated    | Alt. a Parquet  |


## Compressione a Confronto


La compressione riduce lo spazio su disco e, nel contesto S3, riduce anche i costi di storage e di trasferimento dati.


| Algoritmo   | Ratio | Velocita' compressione | Velocita' decompressione | Caso d'uso                       |
| ----------- | ----- | ---------------------- | ------------------------ | -------------------------------- |
| **Nessuna** | 1x    | N/A                    | N/A                      | Debug, file piccoli              |
| **LZ4**     | 2-3x  | Molto veloce           | Molto veloce             | Default ClickHouse, real-time    |
| **Snappy**  | 2-3x  | Veloce                 | Molto veloce             | Default Parquet, bilanciato      |
| **ZSTD**    | 4-8x  | Media                  | Veloce                   | Miglior rapporto ratio/velocita' |
| **Gzip**    | 4-7x  | Lenta                  | Media                    | Compatibilita', file di testo    |
| **Brotli**  | 5-10x | Molto lenta            | Media                    | Archivio, compressione massima   |


### Impatto della Compressione su Dati Reali


Esempio: 10 milioni di eventi marketing (50 colonne, dati tipici GA4-like):


```plain text
Formato              Dimensione    Ratio vs CSV
─────────────────────────────────────────────────
CSV non compresso      8.2 GB       1.0x
CSV + Gzip             1.4 GB       5.9x
JSON non compresso    12.1 GB       0.7x (piu' grande!)
JSON + Gzip            1.8 GB       4.6x
Avro + Snappy          1.1 GB       7.5x
Parquet + Snappy       0.6 GB      13.7x
Parquet + ZSTD         0.4 GB      20.5x
ORC + ZLIB             0.5 GB      16.4x
```


## Schema Evolution


Lo schema dei dati cambia nel tempo: nuovi campi vengono aggiunti, vecchi campi rimossi, tipi modificati. Come gestiscono questa evoluzione i diversi formati?


### Avro: Il Migliore per Schema Evolution


Avro supporta nativamente:

- Aggiungere campi con valore default
- Rimuovere campi con valore default
- Rinominare campi tramite alias
- Promuovere tipi (int → long, float → double)

### Parquet: Schema Evolution Pragmatica


Parquet supporta:

- Aggiungere nuove colonne (appaiono come NULL nei file vecchi)
- Rimuovere colonne (i file vecchi mantengono i dati, le query le ignorano)

Non supporta nativamente:

- Rinominare colonne
- Cambiare tipo di una colonna

```python
# Esempio: schema evolution in Parquet con PyArrow
# Il file v1 ha 3 colonne
# Il file v2 aggiunge una colonna "campaign_source"
# Quando leggi entrambi insieme, la colonna mancante sara' NULL

import pyarrow.parquet as pq

# Leggere file con schema diversi (merge automatico)
dataset = pq.ParquetDataset(
    's3://marketing-lake/cleaned/events/',
    use_legacy_dataset=False
)
table = dataset.read()
# La colonna campaign_source sara' NULL per i record del file v1
```


## Lavorare con Parquet in Python


### Scrivere File Parquet con PyArrow


```python
import pyarrow as pa
import pyarrow.parquet as pq
from datetime import datetime

# Definire lo schema esplicitamente (best practice)
schema = pa.schema([
    ('event_id', pa.string()),
    ('user_id', pa.string()),
    ('event_name', pa.string()),
    ('event_timestamp', pa.timestamp('ms', tz='UTC')),
    ('page_url', pa.string()),
    ('campaign_source', pa.string()),
    ('campaign_medium', pa.string()),
    ('revenue', pa.decimal128(10, 2)),
])

# Creare i dati
data = {
    'event_id': ['e001', 'e002', 'e003'],
    'user_id': ['u101', 'u102', 'u101'],
    'event_name': ['page_view', 'click', 'purchase'],
    'event_timestamp': [
        datetime(2024, 1, 15, 8, 30),
        datetime(2024, 1, 15, 8, 31),
        datetime(2024, 1, 15, 8, 45),
    ],
    'page_url': ['/home', '/pricing', '/checkout'],
    'campaign_source': ['google', 'google', 'google'],
    'campaign_medium': ['cpc', 'cpc', 'cpc'],
    'revenue': [None, None, 49.99],
}

table = pa.table(data, schema=schema)

# Scrivere con compressione ZSTD
pq.write_table(
    table,
    'marketing_events.parquet',
    compression='zstd',
    compression_level=3,       # 1-22, default 3
    row_group_size=1_000_000,  # 1M righe per row group
    use_dictionary=True,       # Dictionary encoding per stringhe
)
```


### Scrivere Parquet Partizionato su S3


```python
import pyarrow as pa
import pyarrow.parquet as pq
import pyarrow.fs as fs

# Configurare il filesystem S3
s3 = fs.S3FileSystem(region='eu-west-1')

# Scrivere con Hive-style partitioning
pq.write_to_dataset(
    table,
    root_path='marketing-lake/cleaned/events/',
    partition_cols=['year', 'month', 'day'],
    filesystem=s3,
    compression='zstd',
    existing_data_behavior='overwrite_or_ignore',
)

# Risultato su S3:
# cleaned/events/year=2024/month=01/day=15/part-0.parquet
```


### Leggere Parquet da S3


```python
import pyarrow.parquet as pq
import pyarrow.fs as fs

s3 = fs.S3FileSystem(region='eu-west-1')

# Leggere solo colonne specifiche (column pruning)
table = pq.read_table(
    'marketing-lake/cleaned/events/',
    filesystem=s3,
    columns=['event_name', 'user_id', 'revenue'],  # Solo 3 colonne su 8
    filters=[
        ('year', '=', '2024'),
        ('month', '=', '01'),
    ],  # Predicate pushdown: legge solo le partizioni necessarie
)

# Convertire in Pandas per analisi
df = table.to_pandas()
print(f"Righe: {len(df):,}")
print(f"Memoria: {df.memory_usage(deep=True).sum() / 1024**2:.1f} MB")
```


## Leggere Parquet da ClickHouse


ClickHouse puo' leggere file Parquet direttamente da S3, rendendo il data lake interrogabile senza caricamento:


```sql
-- Leggere un singolo file Parquet da S3
SELECT
    event_name,
    count() AS events,
    uniq(user_id) AS unique_users,
    sum(revenue) AS total_revenue
FROM s3(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/cleaned/events/year=2024/month=01/day=15/*.parquet',
    'Parquet'
)
GROUP BY event_name
ORDER BY events DESC
LIMIT 20;

-- Leggere con credenziali esplicite
SELECT *
FROM s3(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/cleaned/events/year=2024/month=01/**/*.parquet',
    'ACCESS_KEY_ID',
    'SECRET_ACCESS_KEY',
    'Parquet'

WHERE event_name = 'purchase'
LIMIT 100;

-- Importare dati da S3 in una tabella ClickHouse
INSERT INTO events
SELECT *

    'Parquet'

```


## Quando Usare Quale Formato


| Scenario                     | Formato Consigliato       | Motivazione                                      |
| ---------------------------- | ------------------------- | ------------------------------------------------ |
| Zona raw (API export)        | JSON compresso (.json.gz) | Formato nativo delle API, preserva struttura     |
| Zona raw (database export)   | CSV compresso o Avro      | Semplice per dump tabellari                      |
| Streaming (Kafka)            | Avro                      | Schema registry, evolution, compatto             |
| Zona cleaned                 | Parquet + ZSTD            | Colonnare, compresso, partizionato               |
| Zona curated                 | Parquet + ZSTD            | Standard per analytics                           |
| ClickHouse import            | Parquet                   | Lettura nativa, column pruning                   |
| Data exchange (team esterni) | Parquet o CSV             | Dipende dalla capacita' tecnica del destinatario |
| Machine Learning             | Parquet                   | Pandas/PyArrow leggono nativamente               |


## Riepilogo


La scelta del formato dati e' una delle decisioni piu' impattanti nel design del data lake:

- **Parquet** e' il formato standard per l'analytics: colonnare, compresso, con metadata statistici
- **ZSTD** e' la compressione consigliata: miglior rapporto compressione/velocita'
- **JSON** va bene nella zona raw per preservare i dati originali
- **Avro** eccelle nello streaming e nella schema evolution
- Il **column pruning** di Parquet riduce i costi di query S3 del 90%+
- ClickHouse legge Parquet da S3 nativamente con la funzione `s3()`

## Apache Iceberg: Il Table Format per il Data Lake Moderno

Apache Iceberg e' un **table format open** progettato per gestire tabelle analitiche enormi su object storage. Non e' un format di file (come Parquet): e' uno strato di metadati che aggiunge transazioni ACID, time travel e schema evolution sopra i file Parquet su S3.

### Perche' Iceberg? Il Problema che Risolve

```plain text
Parquet puro su S3 (problema):
  - Vuoi aggiornare 1.000 righe in una tabella da 10 TB?
    → Devi riscrivere TUTTO il file Parquet
  - Vuoi leggere i dati "come erano ieri"?
    → Impossibile: i file sono stati sovrascritti
  - Due job scrivono contemporaneamente?
    → Race condition: dati corrotti

Apache Iceberg (soluzione):
  - Update: scrive solo i delta, i file originali restano
  - Time travel: ogni versione della tabella e' accessibile
  - Concorrenza: snapshot isolation garantisce consistenza
```

### Architettura Iceberg su S3

```plain text
Iceberg Table su S3:

s3://marketing-lake/iceberg/events/
├── metadata/
│   ├── v1.metadata.json          ← Snapshot 1 (stato iniziale)
│   ├── v2.metadata.json          ← Snapshot 2 (dopo primo aggiornamento)
│   ├── v3.metadata.json          ← Snapshot 3 (snapshot corrente)
│   └── snap-123.avro             ← Manifest file (lista di data files)
└── data/
    ├── part-00000-a1b2c3.parquet ← Data file (Parquet)
    ├── part-00001-d4e5f6.parquet ← Data file aggiunto nell'update
    └── part-00002-g7h8i9.parquet
         ↑ I file Parquet sono immutabili
         ↑ Iceberg traccia QUALI file sono "attivi" in ogni snapshot
```

### Lettura Iceberg con PyIceberg

```python
# Installa: pip install pyiceberg[s3,glue]
from pyiceberg.catalog import load_catalog
import pandas as pd

# --- CONFIGURAZIONE CATALOG ---
# PyIceberg usa AWS Glue come registry dei metadati
catalog = load_catalog('glue', **{
    'type': 'glue',
    'warehouse': 's3://marketing-lake/iceberg/',
    'region_name': 'eu-west-1',
})

# --- OPERAZIONI BASE ---

# Aprire una tabella Iceberg esistente
table = catalog.load_table('marketing_lake.events')

# Vedere il schema
print(table.schema())
# Schema: {
#   1: event_id (string, required),
#   2: user_id (string, required),
#   3: event_name (string, required),
#   4: event_timestamp (timestamptz, required),
#   5: revenue (decimal(10, 2), optional)
# }

# Leggere i dati correnti (snapshot piu' recente)
df = table.scan(
    # Filtro pushdown: legge solo le partizioni necessarie
    row_filter="event_date >= '2024-01-01' AND event_name = 'purchase'",
    # Column pruning: legge solo queste colonne
    selected_fields=('event_id', 'event_date', 'user_id', 'revenue'),
    # Limite per test
    limit=10000,
).to_pandas()

print(f"Righe lette: {len(df):,}")
print(f"Revenue totale: ${df['revenue'].sum():,.2f}")

# --- TIME TRAVEL ---

# Listare tutti gli snapshot disponibili
for snapshot in table.snapshots():
    print(f"Snapshot {snapshot.snapshot_id}: {snapshot.timestamp_ms} ms")

# Leggere la versione di ieri (per confronto)
yesterday = table.scan(
    snapshot_id=table.snapshot_by_name('yesterday_snapshot').snapshot_id
).to_pandas()

# Oppure con timestamp diretto
import datetime
yesterday_dt = datetime.datetime.now() - datetime.timedelta(days=1)
df_yesterday = table.scan(
    as_of_time=int(yesterday_dt.timestamp() * 1000)
).to_pandas()

# --- SCHEMA EVOLUTION ---

# Aggiungere una nuova colonna (senza riscrivere i file esistenti!)
with table.update_schema() as update:
    update.add_column(
        path='device_brand',
        field_type='string',
        doc='Brand del dispositivo (Apple, Samsung, ...)'
    )

# I file Parquet vecchi non cambiano.
# Quando vengono letti, la colonna 'device_brand' sara' NULL.
# Solo i nuovi file scritti dopo l'evoluzione avranno il valore.

print("Schema aggiornato:", table.schema())

# --- CREA TABELLA ICEBERG ---

from pyiceberg.schema import Schema
from pyiceberg.types import (
    NestedField, StringType, TimestamptzType, DecimalType, LongType
)
from pyiceberg.partitioning import PartitionSpec, PartitionField
from pyiceberg.transforms import DayTransform

# Definizione schema
schema = Schema(
    NestedField(1, "event_id",        StringType(),       required=True),
    NestedField(2, "user_id",         StringType(),       required=True),
    NestedField(3, "event_name",      StringType(),       required=True),
    NestedField(4, "event_timestamp", TimestamptzType(),  required=True),
    NestedField(5, "utm_source",      StringType(),       required=False),
    NestedField(6, "revenue",         DecimalType(10, 2), required=False),
)

# Partition spec: hidden partitioning per giorno
# Il giorno viene estratto automaticamente da event_timestamp
partition_spec = PartitionSpec(
    PartitionField(
        source_id=4,           # event_timestamp
        field_id=1000,
        transform=DayTransform(),
        name='event_day'       # nome della partizione (nascosta)
    )
)

# Crea la tabella nel catalog
table = catalog.create_table(
    'marketing_lake.events_iceberg',
    schema=schema,
    partition_spec=partition_spec,
    location='s3://marketing-lake/iceberg/events/',
    properties={
        'write.format.default': 'parquet',
        'write.parquet.compression-codec': 'zstd',
        'write.metadata.delete-after-commit.enabled': 'true',
        'write.metadata.previous-versions-max': '10',
    }
)
```

## Delta Lake vs Iceberg vs Hudi: Confronto Operativo

### Quando Passare da Parquet Raw a Table Format?

```plain text
Segnali che e' il momento di adottare un table format:

1. Hai bisogno di GDPR right-to-erasure efficiente
   → Iceberg row-level deletes senza riscrivere tutto

2. Hai aggiornamenti frequenti (CRM sync, ordini)
   → Hudi o Iceberg MERGE per upsert efficienti

3. Hai bisogno di debug "come erano i dati ieri"
   → Time travel di Delta Lake o Iceberg

4. Piu' job scrivono contemporaneamente sulla stessa tabella
   → Snapshot isolation di Iceberg o Delta Lake

5. Lo schema cambia frequentemente
   → Schema evolution di Iceberg (il migliore)

NON serve un table format quando:
- I file Parquet sono write-once (dati storici immutabili)
- ClickHouse e' il solo consumer (ha le sue ottimizzazioni)
- Il team e' piccolo e la complessita' aggiuntiva non vale
```

### Matrice di Compatibilita' con i Tool

| Tool          | Delta Lake | Iceberg (native) | Hudi   |
| ------------- | ---------- | ---------------- | ------ |
| **Spark**     | Nativo     | Nativo           | Nativo |
| **Athena**    | Si (v2)    | Si (v3)          | Si     |
| **ClickHouse**| Limitato   | In sviluppo      | No     |
| **DuckDB**    | Si         | Si               | No     |
| **Flink**     | Si         | Si               | Si     |
| **Trino**     | Si         | Si               | Si     |
| **Pandas**    | delta-rs   | PyIceberg        | No     |

<Aside type="caution">
Se ClickHouse e' il tuo query engine principale e i dati non cambiano frequentemente, resta su Parquet puro + Hive partitioning. La semplicita' supera i benefici dei table format in questo contesto.
</Aside>

### Caso Reale: Netflix e Iceberg

Netflix ha creato Apache Iceberg nel 2017 per risolvere i problemi delle sue tabelle Hive da petabyte. Prima di Iceberg, il loro team di data engineering perdeva ore ogni settimana in operazioni di gestione tabelle che rompevano la consistenza dei dati.

**Il problema specifico:** Netflix aveva una tabella di eventi da 500+ TB. Ogni notte un job Spark riscriveva le partizioni del giorno precedente per correggere i dati ritardatari. Durante questa operazione (che durava ore), le query degli analisti potevano leggere stati parzialmente aggiornati — una partizione sovrascritta a meta'.

**La soluzione con Iceberg:** grazie allo snapshot isolation, le query degli analisti leggono sempre uno snapshot consistente. Il job di riscrittura crea uno nuovo snapshot completo prima di renderlo visibile. Il "flip" da vecchio a nuovo snapshot e' atomico (una singola operazione di aggiornamento del puntatore nel catalog).

Oggi Netflix gestisce oltre 10.000 tabelle Iceberg, con alcune da decine di petabyte. L'adozione di Iceberg ha ridotto il tempo di risoluzione dei problemi di consistenza dei dati del 90% e ha eliminato completamente la categoria di bug legata alle race condition in scrittura.
