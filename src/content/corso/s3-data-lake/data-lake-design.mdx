# Data Lake Design Patterns


Un data lake senza design e' un data swamp. In questa lezione vedremo come progettare un'architettura solida per il data lake di marketing, con pattern collaudati che bilanciano flessibilita', governance e performance.


## Data Lake vs Data Warehouse vs Data Lakehouse


Prima di progettare, chiariamo le differenze tra i tre paradigmi principali di architettura dati.


| Aspetto              | Data Lake                     | Data Warehouse                 | Data Lakehouse                   |
| -------------------- | ----------------------------- | ------------------------------ | -------------------------------- |
| **Storage**          | Object storage (S3)           | Storage proprietario           | Object storage + table format    |
| **Formato dati**     | Qualsiasi (raw + structured)  | Strutturato (tabelle)          | Strutturato (Parquet + metadata) |
| **Schema**           | Schema-on-read                | Schema-on-write                | Schema-on-read con enforcement   |
| **Utenti**           | Data engineer, data scientist | Analisti, BI                   | Tutti                            |
| **Query engine**     | Spark, Athena, Presto         | Engine integrato               | Engine integrato + esterno       |
| **Transazioni ACID** | No                            | Si                             | Si (Delta Lake, Iceberg)         |
| **Costo storage**    | Basso ($0.023/GB)             | Alto ($5-25/TB/mese compressi) | Basso ($0.023/GB)                |
| **Governance**       | Manuale, metadata catalog     | Built-in                       | Table format + catalog           |
| **Esempi**           | S3 + Spark/Athena             | Snowflake, BigQuery, Redshift  | Delta Lake, Apache Iceberg, Hudi |


### Il Nostro Approccio: Pragmatico


Per una piattaforma di marketing analytics, l'approccio piu' efficace e':


```plain text
S3 (Data Lake)  +  ClickHouse (Query Engine)  =  Lakehouse pratico
     │                      │
     │  Dati grezzi e       │  Query veloci,
     │  archivio             │  dashboard real-time
     │  (costo basso)        │  (hot data locale)
```


I dati vivono in S3 in formato Parquet. ClickHouse mantiene i dati "caldi" (ultimi mesi) nel suo storage locale ad alte prestazioni. I dati "freddi" restano in S3 e vengono interrogati on-demand tramite la table function `s3()`.


## Architettura a Zone (Medallion Architecture)


Il pattern piu' collaudato per organizzare un data lake e' l'**architettura a zone**, anche detta Medallion Architecture (terminologia Databricks: Bronze, Silver, Gold).


```plain text
┌─────────────────────────────────────────────────────────────────────┐
│                         DATA LAKE (S3)                              │
│                                                                     │
│  ┌─────────────┐    ┌──────────────┐    ┌────────────────┐         │
│  │   RAW        │    │   CLEANED     │    │   CURATED       │        │
│  │  (Bronze)    │───→│   (Silver)    │───→│   (Gold)        │        │
│  │              │    │               │    │                 │        │
│  │ Dati grezzi  │    │ Dati puliti   │    │ Dati pronti     │        │
│  │ come arrivano│    │ validati      │    │ per analisi     │        │
│  │ dalla sorgente│   │ normalizzati  │    │ aggregati       │        │
│  │              │    │ deduplicati   │    │ business-ready  │        │
│  └─────────────┘    └──────────────┘    └────────────────┘         │
│                                                                     │
│  Qualita': BASSA        MEDIA              ALTA                     │
│  Schema:   Nessuno      Validato           Enforced                 │
│  Accesso:  Solo ETL     Data engineer      Analisti, BI, ClickHouse │
│  Formato:  JSON/CSV     Parquet            Parquet                  │
└─────────────────────────────────────────────────────────────────────┘
```


### Zona Raw (Bronze)


La zona raw contiene i dati esattamente come arrivano dalla sorgente. Nessuna trasformazione, nessuna pulizia. E' il "backup operativo" dei dati originali.


**Regole:**

- I dati non vengono mai modificati dopo l'inserimento
- Il formato originale viene preservato (JSON, CSV, XML)
- Ogni file include un timestamp o un batch ID nel nome
- I dati restano per un periodo definito (es. 12-24 mesi), poi migrano a Glacier

```plain text
raw/
├── ga4/
│   ├── 2024/01/15/
│   │   ├── events_20240115_080000_000.json.gz
│   │   ├── events_20240115_080000_001.json.gz
│   │   └── events_20240115_120000_000.json.gz
│   └── 2024/01/16/
│       └── events_20240116_080000_000.json.gz
├── hubspot/
│   ├── contacts/
│   │   └── 2024/01/15/
│   │       └── contacts_full_20240115.json.gz
│   └── deals/
│       └── 2024/01/15/
│           └── deals_incremental_20240115.json.gz
├── meta_ads/
│   └── 2024/01/15/
│       ├── campaigns_20240115.json
│       └── ad_insights_20240115.json
└── google_ads/
    └── 2024/01/15/
        └── campaign_report_20240115.csv
```


### Zona Cleaned (Silver)


La zona cleaned contiene i dati dopo la prima trasformazione: validazione dello schema, deduplicazione, normalizzazione dei tipi, conversione in formato colonnare (Parquet).


**Trasformazioni tipiche:**

- Conversione da JSON/CSV a Parquet
- Validazione e casting dei tipi di dato
- Deduplicazione (rimozione eventi doppi)
- Normalizzazione timestamp (tutti in UTC)
- Rimozione o mascheramento PII (GDPR)
- Aggiunta di campi calcolati base (data, ora, giorno della settimana)

```plain text
cleaned/
├── ga4/
│   ├── events/
│   │   ├── year=2024/month=01/day=15/
│   │   │   ├── part-00000.parquet
│   │   │   └── part-00001.parquet
│   │   └── year=2024/month=01/day=16/
│   │       └── part-00000.parquet
│   └── sessions/
│       └── year=2024/month=01/day=15/
│           └── part-00000.parquet
├── crm/
│   ├── contacts/
│   │   └── year=2024/month=01/day=15/
│   │       └── part-00000.parquet
│   └── deals/
│       └── year=2024/month=01/day=15/
│           └── part-00000.parquet
└── campaigns/
    └── unified/
        └── year=2024/month=01/day=15/
            └── part-00000.parquet
```


### Zona Curated (Gold)


La zona curated contiene i dati pronti per il consumo: aggregazioni, metriche, tabelle denormalizzate, modelli pronti per le dashboard.


**Caratteristiche:**

- Schema ben definito e documentato
- Dati aggregati al livello di granularita' utile per l'analisi
- JOIN pre-calcolati tra diverse sorgenti
- Naming convention chiara e business-friendly

```plain text
curated/
├── funnel/
│   ├── daily_funnel_metrics/
│   │   └── year=2024/month=01/
│   │       └── part-00000.parquet
│   └── conversion_by_channel/
│       └── year=2024/month=01/
│           └── part-00000.parquet
├── attribution/
│   ├── multi_touch_attribution/
│   │   └── year=2024/month=01/
│   │       └── part-00000.parquet
│   └── channel_contribution/
│       └── latest.parquet
├── segments/
│   ├── rfm_segments/
│   │   └── latest.parquet
│   └── cohort_analysis/
│       └── year=2024/month=01/
│           └── part-00000.parquet
└── kpi/
    └── marketing_kpi_daily/
        └── year=2024/month=01/
            └── part-00000.parquet
```


## Schema-on-Read vs Schema-on-Write


Questa e' una delle differenze filosofiche piu' importanti tra Data Lake e Data Warehouse.


### Schema-on-Write (Data Warehouse)


Lo schema viene definito **prima** di caricare i dati. Se i dati non rispettano lo schema, il caricamento fallisce.


```sql
-- Prima definisco lo schema
CREATE TABLE campaign_metrics (
    date Date,
    campaign_id UInt32,
    impressions UInt64,
    clicks UInt32,
    spend Decimal(10,2)
);

-- Poi carico i dati (devono rispettare lo schema)
INSERT INTO campaign_metrics VALUES ('2024-01-15', 1001, 50000, 1200, 450.00);
-- Se un campo e' del tipo sbagliato → ERRORE
```


**Vantaggi:** Dati sempre consistenti, query prevedibili.
**Svantaggi:** Rigido, lento ad adattarsi a nuove sorgenti.


### Schema-on-Read (Data Lake)


I dati vengono salvati senza schema. Lo schema viene applicato **al momento della lettura**.


```sql
-- I dati sono gia' in S3 come file Parquet o JSON
-- Lo schema viene definito al momento della query
SELECT
    event_date,
    campaign_id,
    toUInt64(impressions) AS impressions,
    toUInt32(clicks) AS clicks,
    toDecimal64(spend, 2) AS spend
FROM s3(
    'https://s3.amazonaws.com/marketing-lake/raw/gads/2024/01/*.json',
    'JSONEachRow'
);
```


**Vantaggi:** Flessibile, ingestione veloce, nessun vincolo iniziale.
**Svantaggi:** Nessuna garanzia sulla qualita', possibili errori a runtime.


### L'Approccio Ibrido


La pratica migliore e' un approccio ibrido:


| Zona        | Strategia Schema                                        |
| ----------- | ------------------------------------------------------- |
| **Raw**     | Nessuno schema (schema-on-read puro)                    |
| **Cleaned** | Schema validato dalla pipeline ETL, salvato nel catalog |
| **Curated** | Schema rigoroso, documentato, con test di qualita'      |


## Metadata Catalog


Il metadata catalog e' il "dizionario" del data lake: registra quali dati esistono, dove si trovano, qual e' il loro schema, chi li ha creati e quando.


### Informazioni da Tracciare


Per ogni dataset nel data lake, il catalog dovrebbe contenere:


```yaml
# Esempio: schema di un dataset nel catalog
dataset:
  name: ga4_events_cleaned
  description: "Eventi GA4 puliti e normalizzati"
  zone: cleaned
  location: s3://marketing-lake/cleaned/ga4/events/
  format: parquet
  partitioning: "year/month/day (Hive-style)"
  schema:
    - name: event_timestamp
      type: DateTime64(3)
      description: "Timestamp dell'evento in UTC"
    - name: event_name
      type: String
      description: "Nome dell'evento GA4"
    - name: user_pseudo_id
      type: String
      description: "ID anonimo dell'utente"
    - name: session_id
      type: UInt64
      description: "ID della sessione"
  owner: data-engineering-team
  pipeline: ga4_daily_etl
  freshness: daily (08:00 UTC)
  retention: 24 mesi
  pii_fields: ["user_pseudo_id"]
  quality_checks:
    - "row_count > 0"
    - "null_rate(event_timestamp) < 0.01"
    - "unique(event_name) between 50 and 200"
```


### Strumenti per il Catalog


| Strumento                 | Tipo        | Complessita' | Caso d'uso                    |
| ------------------------- | ----------- | ------------ | ----------------------------- |
| **File YAML/JSON in S3**  | Manuale     | Bassa        | Piccoli team, inizio progetto |
| **AWS Glue Data Catalog** | Managed     | Media        | Ecosistema AWS, Athena        |
| **Apache Hive Metastore** | Open source | Alta         | Ecosistema Hadoop/Spark       |
| **DataHub**               | Open source | Alta         | Governance enterprise         |
| **dbt docs**              | Open source | Bassa        | Se usi gia' dbt               |

## Anti-pattern: Il Data Swamp


Un data lake senza governance diventa un **data swamp** (palude di dati): un accumulo disorganizzato di file che nessuno riesce a usare.


### Segnali di un Data Swamp


| Segnale                        | Descrizione                                  |
| ------------------------------ | -------------------------------------------- |
| Nessuno sa quali dati ci sono  | Manca un catalog, bisogna "esplorare" l'S3   |
| File senza naming convention   | `export_final_v2_FIXED_newcopy.csv`          |
| Schema non documentati         | Bisogna aprire il file per capire le colonne |
| Dati duplicati                 | Stessi dati in 3 prefissi diversi            |
| Nessun owner                   | Nessuno e' responsabile di un dataset        |
| Dati mai cancellati            | 5 anni di dati raw senza lifecycle rules     |
| Pipeline rotte silenziosamente | ETL che fallisce ma nessuno se ne accorge    |


### Come Prevenire il Data Swamp

1. **Metadata catalog** anche se semplice (YAML in Git). Ogni dataset ha un owner e una descrizione.
2. **Lifecycle rules** su S3: i dati hanno una data di scadenza definita.
3. **Quality checks** automatici nella pipeline: se la qualita' scende sotto soglia, la pipeline si ferma e notifica.
4. **Access control per zona**: solo le pipeline scrivono nella zona raw; solo i data engineer accedono alla zona cleaned; analisti e BI accedono solo alla zona curated.
5. **Documentazione as code**: lo schema dei dati vive nel repository, versionato e reviewed come il codice.

## Governance del Data Lake


La governance e' l'insieme di regole, processi e responsabilita' che mantengono il data lake utilizzabile nel tempo.


### Matrice di Responsabilita'


| Ruolo                   | Raw        | Cleaned    | Curated   | Catalog       |
| ----------------------- | ---------- | ---------- | --------- | ------------- |
| **Data Engineer**       | Scrittura  | Scrittura  | Scrittura | Aggiornamento |
| **Analytics Engineer**  | Lettura    | Lettura    | Scrittura | Aggiornamento |
| **Data Analyst**        | No accesso | Lettura    | Lettura   | Lettura       |
| **BI/Dashboard**        | No accesso | No accesso | Lettura   | Lettura       |
| **Pipeline (servizio)** | Scrittura  | Scrittura  | Scrittura | Automatico    |


### Checklist di Governance


```plain text
[ ] Naming convention documentata e applicata
[ ] Ogni dataset ha un owner nel catalog
[ ] Lifecycle rules configurate su tutti i bucket
[ ] Access control per zona (IAM policies)
[ ] Quality checks automatici in ogni pipeline
[ ] Schema versionati nel repository Git
[ ] Alerting su pipeline failure
[ ] Procedura documentata per aggiungere nuove sorgenti
[ ] Revisione trimestrale dei dataset inutilizzati
[ ] Compliance GDPR: procedura di data deletion testata
```
