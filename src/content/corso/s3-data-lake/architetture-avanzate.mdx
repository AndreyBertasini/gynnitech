# Architetture Avanzate: Lambda, CDC e Aggregazioni


In questa lezione esploriamo i pattern architetturali avanzati per costruire un data lake di produzione. Ogni pattern risolve un problema specifico: latenza, costi, consistenza o scalabilita'.


## Lambda Architecture con S3 + ClickHouse


La Lambda Architecture separa i dati in due percorsi paralleli: **speed layer** (bassa latenza) e **batch layer** (alta accuratezza). Entrambi vengono uniti al momento della query.


### Perche' Serve


```plain text
Problema: vuoi sia query real-time (ultimi 5 minuti) che query storiche accurate (ultimi 2 anni).

- Solo S3Queue: latenza di secondi-minuti, OK per real-time
  Ma i dati raw possono essere sporchi (duplicati, schema drift)

- Solo batch ETL: dati puliti e validati
  Ma latenza di ore (job schedulato ogni N ore)

- Lambda: hai entrambi!
```


### Architettura


```plain text
┌─────────────────────────────────────────────────────────┐
│                  Lambda Architecture                     │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  ┌────────────┐                                          │
│  │ Raw Events │                                          │
│  │ (S3)       │                                          │
│  └──────┬─────┘                                          │
│         │                                                │
│    ┌────┴────┐                                           │
│    ▼         ▼                                           │
│  ┌───────┐ ┌──────────┐                                  │
│  │ Speed │ │  Batch   │                                  │
│  │ Layer │ │  Layer   │                                  │
│  │       │ │          │                                  │
│  │S3Queue│ │ETL job   │                                  │
│  │→ MV   │ │(orario/  │                                  │
│  │→ MT   │ │giornaliero)│                                │
│  └───┬───┘ └────┬─────┘                                  │
│      │          │                                        │
│      ▼          ▼                                        │
│  ┌──────────────────┐                                    │
│  │  Serving Layer   │  Vista unificata                   │
│  │  (UNION ALL)     │                                    │
│  └──────────────────┘                                    │
└─────────────────────────────────────────────────────────┘
```


### Implementazione


```sql
-- SPEED LAYER: dati recenti (ultimi 7 giorni), bassa latenza
-- Alimentato da S3Queue (lezione precedente)
CREATE TABLE events_speed (
    event_id String,
    user_id String,
    event_name String,
    event_timestamp DateTime64(3),
    utm_source Nullable(String),
    revenue Nullable(Decimal(10, 2))
) ENGINE = ReplacingMergeTree()
PARTITION BY toDate(event_timestamp)
ORDER BY (event_id)
TTL toDate(event_timestamp) + INTERVAL 7 DAY DELETE;

-- BATCH LAYER: dati storici, puliti e validati
-- Alimentato da ETL job schedulato (cleaned Parquet su S3)
CREATE TABLE events_batch (
    event_id String,
    user_id String,
    event_name String,
    event_timestamp DateTime64(3),
    utm_source Nullable(String),
    revenue Nullable(Decimal(10, 2)),
    is_valid UInt8 DEFAULT 1,
    dedup_key String DEFAULT event_id
) ENGINE = ReplacingMergeTree()
PARTITION BY toYYYYMM(event_timestamp)
ORDER BY (event_id);

-- SERVING LAYER: vista unificata
CREATE VIEW events_lambda AS
-- Batch layer: dati fino a 7 giorni fa (puliti)
SELECT
    event_id, user_id, event_name, event_timestamp,
    utm_source, revenue,
    'batch' AS source
FROM events_batch
WHERE toDate(event_timestamp) < today() - 7

UNION ALL

-- Speed layer: ultimi 7 giorni (near real-time)
SELECT
    event_id, user_id, event_name, event_timestamp,
    utm_source, revenue,
    'speed' AS source
FROM events_speed;
```


### Job ETL Batch (Schedulato Giornalmente)


```sql
-- ETL batch: importa da S3 Cleaned, pulisce e valida
INSERT INTO events_batch
SELECT
    event_id,
    user_id,
    event_name,
    event_timestamp,
    utm_source,
    revenue,
    1 AS is_valid,
    event_id AS dedup_key
FROM s3(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/cleaned/events/year=2024/month=01/**/*.parquet',
    'Parquet'
)
WHERE event_timestamp IS NOT NULL
  AND user_id != ''
  AND event_name IN ('page_view', 'click', 'add_to_cart', 'purchase');
```


<Aside type="tip">
La Lambda Architecture e' complessa. Usala solo quando hai bisogno sia di bassa latenza che di alta accuratezza. Per la maggior parte dei casi marketing, S3Queue + MergeTree e' sufficiente.
</Aside>


## Change Data Capture (CDC) da S3


Il CDC cattura le **modifiche** ai dati (INSERT, UPDATE, DELETE) invece di riscrivere tutto. Utile quando i dati sorgente cambiano frequentemente (CRM, ordini, profili utente).


### Il Problema


```plain text
Scenario: il CRM esporta su S3 uno snapshot completo dei contatti ogni ora.
- 500.000 contatti totali
- Solo 200-500 cambiano ogni ora
- Riscrivere 500K record ogni ora e' inefficiente

Soluzione CDC: esporta solo i record modificati + un campo 'operation' (INSERT/UPDATE/DELETE)
```


### Schema CDC su S3


```plain text
s3://marketing-lake/cdc/contacts/
├── 2024-01-15_08-00_full.parquet        ← Snapshot iniziale (500K record)
├── 2024-01-15_09-00_delta.parquet       ← Solo modifiche (200 record)
├── 2024-01-15_10-00_delta.parquet       ← Solo modifiche (350 record)
└── 2024-01-15_11-00_delta.parquet       ← Solo modifiche (180 record)
```


### Struttura del Delta File


```sql
-- Ogni file delta contiene:
-- _op: 'I' (insert), 'U' (update), 'D' (delete)
-- _ts: timestamp della modifica
-- + tutti i campi del record

CREATE TABLE contacts_cdc_queue (
    _op String,            -- I, U, D
    _ts DateTime64(3),     -- timestamp modifica
    contact_id String,
    email String,
    first_name String,
    last_name String,
    company String,
    lifecycle_stage String,
    lead_score UInt32,
    last_activity DateTime
) ENGINE = S3Queue(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/cdc/contacts/*.parquet',
    'Parquet'
) SETTINGS
    mode = 'ordered',
    after_processing = 'keep',
    keeper_path = '/clickhouse/s3queue/contacts_cdc';
```


### Tabella Destinazione con CollapsingMergeTree


```sql
-- CollapsingMergeTree gestisce insert/update/delete con un campo sign
CREATE TABLE contacts (
    contact_id String,
    email String,
    first_name String,
    last_name String,
    company String,
    lifecycle_stage String,
    lead_score UInt32,
    last_activity DateTime,
    updated_at DateTime64(3),
    sign Int8  -- 1 = record attivo, -1 = record cancellato/sostituito
) ENGINE = CollapsingMergeTree(sign)
ORDER BY (contact_id);
```


### Materialized View per Applicare il CDC


```sql
CREATE MATERIALIZED VIEW contacts_cdc_consumer TO contacts AS
SELECT
    contact_id,
    email,
    first_name,
    last_name,
    company,
    lifecycle_stage,
    lead_score,
    last_activity,
    _ts AS updated_at,
    CASE
        WHEN _op = 'D' THEN -1  -- Delete: segno negativo
        ELSE 1                    -- Insert/Update: segno positivo
    END AS sign
FROM contacts_cdc_queue;
```


### Query sulla Tabella CDC


```sql
-- Con FINAL per avere la vista corretta (deduplica collapsed records)
SELECT
    contact_id,
    email,
    first_name,
    last_name,
    lifecycle_stage,
    lead_score
FROM contacts
FINAL
WHERE sign = 1  -- Solo record attivi
ORDER BY lead_score DESC
LIMIT 100;

-- Aggregazione per lifecycle stage (con collapsing corretto)
SELECT
    lifecycle_stage,
    sum(sign) AS active_contacts,
    avg(lead_score * sign) AS avg_lead_score
FROM contacts
GROUP BY lifecycle_stage
HAVING active_contacts > 0
ORDER BY active_contacts DESC;
```


<Aside type="caution">
`CollapsingMergeTree` richiede che per ogni UPDATE si inseriscano **due righe**: una con `sign = -1` (cancella il vecchio) e una con `sign = 1` (inserisci il nuovo). Se il CDC source esporta solo la nuova versione, modifica la Materialized View per emettere entrambe le righe.
</Aside>


### CDC Completo con Cancellazione del Vecchio Record


```sql
-- Versione avanzata: emette la riga di cancellazione e la nuova
CREATE MATERIALIZED VIEW contacts_cdc_consumer_v2 TO contacts AS
-- Per UPDATE: cancella il vecchio record
SELECT
    contact_id, email, first_name, last_name,
    company, lifecycle_stage, lead_score, last_activity,
    _ts AS updated_at,
    -1 AS sign
FROM contacts_cdc_queue
WHERE _op = 'U'

UNION ALL

-- Per INSERT e UPDATE: inserisci il nuovo record
SELECT
    contact_id, email, first_name, last_name,
    company, lifecycle_stage, lead_score, last_activity,
    _ts AS updated_at,
    1 AS sign
FROM contacts_cdc_queue
WHERE _op IN ('I', 'U')

UNION ALL

-- Per DELETE: cancella il record
SELECT
    contact_id, email, first_name, last_name,
    company, lifecycle_stage, lead_score, last_activity,
    _ts AS updated_at,
    -1 AS sign
FROM contacts_cdc_queue
WHERE _op = 'D';
```


## State Tracking per Import Incrementale


Quando non usi S3Queue ma vuoi comunque importare solo file nuovi:


```sql
-- Tabella di stato: traccia l'ultimo file processato
CREATE TABLE import_state (
    source_name String,
    last_file String,
    last_import_time DateTime,
    rows_imported UInt64
) ENGINE = ReplacingMergeTree(last_import_time)
ORDER BY source_name;

-- Importare solo file nuovi
INSERT INTO events
SELECT *
FROM s3(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/raw/events/*.parquet',
    'Parquet'
)
WHERE _file > (
    SELECT last_file
    FROM import_state FINAL
    WHERE source_name = 'marketing_events'
);

-- Aggiornare lo stato
INSERT INTO import_state
SELECT
    'marketing_events' AS source_name,
    max(_file) AS last_file,
    now() AS last_import_time,
    count() AS rows_imported
FROM s3(
    'https://s3.eu-west-1.amazonaws.com/marketing-lake/raw/events/*.parquet',
    'Parquet'
)
WHERE _file > (
    SELECT last_file
    FROM import_state FINAL
    WHERE source_name = 'marketing_events'
);
```


<Aside type="tip">
Lo state tracking manuale funziona ma e' fragile. Preferisci S3Queue quando possibile — gestisce lo stato automaticamente via ZooKeeper.
</Aside>


## Ottimizzazione dei Costi S3


### Costi S3 nel Contesto Analytics


```plain text
Operazione          Costo (S3 Standard)        Nota
──────────────────────────────────────────────────────
Storage             $0.023/GB/mese             Parquet + ZSTD riduce 10-20x
PUT (upload)        $0.005 per 1000 richieste  Upload file
GET (download)      $0.0004 per 1000 richieste Ogni query s3() fa GET
LIST               $0.005 per 1000 richieste  Risoluzione glob pattern
Data transfer       $0.09/GB (fuori regione)   $0 nella stessa regione
```


### Strategie di Ottimizzazione


**1. Glob pattern specifici** (riduce LIST + GET)

```sql
-- COSTOSO: scansiona tutti i file
SELECT count() FROM s3('.../events/**/*.parquet', 'Parquet')
WHERE event_date = '2024-01-15';

-- ECONOMICO: scansiona solo un giorno
SELECT count() FROM s3('.../events/year=2024/month=01/day=15/*.parquet', 'Parquet');
```


**2. Formati colonnari + compressione** (riduce storage + transfer)

```plain text
100M eventi marketing (50 colonne):
- CSV:           8.2 GB  → $0.19/mese storage
- JSON:         12.1 GB  → $0.28/mese storage
- Parquet+ZSTD:  0.4 GB  → $0.01/mese storage   (20x risparmio!)
```


**3. S3 Lifecycle Rules** (riduce costi storage a lungo termine)

```plain text
Regola                          Azione
────────────────────────────────────────────────────────────
File raw > 30 giorni            → S3 Infrequent Access ($0.0125/GB)
File raw > 90 giorni            → S3 Glacier Instant ($0.004/GB)
File raw > 365 giorni           → S3 Glacier Deep ($0.00099/GB)
File processed > 180 giorni     → Cancella
```


**4. ClickHouse nella stessa regione** (elimina costi di transfer)

```plain text
S3 bucket: eu-west-1
ClickHouse: eu-west-1 ← stessa regione = $0 data transfer
ClickHouse: us-east-1 ← altra regione = $0.02/GB data transfer
```


### Calcolo Costi per un Caso Reale


```plain text
Scenario: E-commerce marketing analytics
- 50M eventi/giorno
- 50 colonne per evento
- Retention: 24 mesi
- Query: ~100/giorno

Storage (Parquet + ZSTD):
  50M eventi × 50 col × ~20 bytes/col = ~50 GB/giorno raw
  Parquet + ZSTD: ~2.5 GB/giorno compresso
  24 mesi: ~2.5 GB × 730 giorni = 1.825 TB

Costi mensili:
  S3 Storage (1.825 TB):            $41.98
  S3 GET (100 query × ~50 file):    $0.002
  S3 LIST (100 query × 1 list):     $0.0005
  ClickHouse (tiered, stesso region): $0 transfer
  ─────────────────────────────────────
  Totale S3:                         ~$42/mese

Con lifecycle (Glacier per > 6 mesi):
  Hot (6 mesi, ~450 GB):            $10.35
  Glacier Instant (18 mesi, 1.375 TB): $5.50
  ─────────────────────────────────────
  Totale ottimizzato:                ~$16/mese  (62% risparmio)
```


## Pattern Decisionale: Quale Architettura Scegliere


```plain text
                    ┌─────────────────────────────┐
                    │ Hai bisogno di real-time?    │
                    └──────────┬──────────────────┘
                         │                  │
                    SI   │                  │ NO
                         ▼                  ▼
              ┌──────────────────┐  ┌──────────────────┐
              │ I file arrivano  │  │ Query periodiche │
              │ continuamente?   │  │ su S3 bastano    │
              └──────┬───────────┘  └──────────────────┘
                │          │              │
           SI   │          │ NO           │
                ▼          ▼              ▼
         ┌───────────┐ ┌──────────┐ ┌──────────────────┐
         │ S3Queue + │ │ Refresh  │ │ s3() diretta     │
         │ MV chain  │ │ MV       │ │ o INSERT batch   │
         └─────┬─────┘ └──────────┘ └──────────────────┘
               │
               │ Hai bisogno anche di
               │ dati storici accurati?
               │
          ┌────┴────┐
     SI   │         │ NO
          ▼         ▼
   ┌────────────┐ ┌──────────────┐
   │ Lambda     │ │ S3Queue +    │
   │ Arch.      │ │ MergeTree    │
   └────────────┘ │ (sufficiente)│
                  └──────────────┘
```


| Scenario                           | Architettura Consigliata      | Complessita' |
| ---------------------------------- | ----------------------------- | ------------ |
| Report settimanali                 | `s3()` diretta                | Bassa        |
| Dashboard aggiornata ogni ora      | Refreshable MV                | Bassa        |
| Dashboard real-time (< 1 min lag)  | S3Queue + MV chain            | Media        |
| Real-time + storico accurato       | Lambda Architecture           | Alta         |
| Dati CRM che cambiano             | CDC + CollapsingMergeTree     | Alta         |
| Multi-sorgente con deduplicazione  | ReplacingMergeTree + S3Queue  | Media        |


## Riepilogo


I pattern avanzati ti permettono di costruire architetture data lake sofisticate:

- **Lambda Architecture** combina speed layer (S3Queue) e batch layer (ETL) per bassa latenza e alta accuratezza
- **Change Data Capture** con CollapsingMergeTree gestisce INSERT, UPDATE e DELETE incrementali
- **State tracking** per import incrementali senza S3Queue
- **Ottimizzazione costi** con glob specifici, Parquet+ZSTD, lifecycle rules e co-locazione regionale
- **Pattern decisionale** per scegliere l'architettura giusta in base ai requisiti

Il principio guida: **inizia semplice** (S3Queue + MergeTree) e **aggiungi complessita'** solo quando i requisiti lo richiedono.
