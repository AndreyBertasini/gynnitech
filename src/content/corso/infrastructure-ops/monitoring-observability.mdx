# Monitoring e Observability per Data Pipeline


A differenza del software applicativo dove un errore genera un codice HTTP 500 visibile, le pipeline dati possono fallire silenziosamente: i dati arrivano in ritardo, mancano righe, i valori sono corrotti, ma la dashboard continua a mostrare numeri -- semplicemente numeri sbagliati. Questa lezione affronta il problema del "data downtime" con strumenti, metriche e pratiche operative.


## 1. I Tre Pilastri dell'Observability


L'observability per i sistemi dati si basa sugli stessi tre pilastri del software engineering, ma con un'attenzione specifica alla qualita dei dati:


### Metriche (Metrics)


Valori numerici aggregati nel tempo. Rispondono a "quanto?" e "quanti?".


```plain text
Esempi per data pipeline:
  - Righe processate al minuto
  - Latenza media di ingestione (secondi)
  - Percentuale di record con valori NULL
  - Spazio disco utilizzato da ClickHouse
  - Numero di query lente (> 5 secondi)
```


### Log


Registrazioni testuali di eventi specifici. Rispondono a "cosa e successo?".


```plain text
Esempi per data pipeline:
  - "Pipeline dbt completata in 45 secondi, 23 modelli processati"
  - "ERRORE: colonna 'revenue' contiene 15% di NULL (soglia: 5%)"
  - "WARNING: tabella fact_orders non aggiornata da 3 ore"
  - "Snapshot Debezium completato: 1.2M righe processate"
```


### Tracce (Traces)


Il percorso di un dato attraverso i sistemi. Rispondono a "dove si e bloccato?".


```plain text
Trace di un evento marketing:
  [App] click event generato          → 0ms
  [Kafka] messaggio pubblicato        → 15ms
  [ClickHouse] Kafka engine ingerisce → 45ms
  [MV] Materialized View processa     → 52ms
  [Dashboard] dato disponibile        → 55ms
  Totale: 55ms end-to-end
```


## 2. Metriche Specifiche per Data Pipeline


Le metriche standard dell'infrastruttura (CPU, RAM, disco) non sono sufficienti per il mondo dati. Servono metriche specifiche:


### Le Cinque Dimensioni della Qualita dei Dati


| Dimensione       | Descrizione                  | Metrica                         | Soglia tipica                 |
| ---------------- | ---------------------------- | ------------------------------- | ----------------------------- |
| **Freshness**    | Quanto sono recenti i dati   | Tempo dall'ultimo aggiornamento | < 2 ore                       |
| **Volume**       | Quanti dati arrivano         | Righe inserite per intervallo   | +/- 30% dalla media           |
| **Schema**       | La struttura e quella attesa | Colonne aggiunte/rimosse        | 0 cambiamenti non pianificati |
| **Completeness** | I dati sono completi         | % di valori NULL per colonna    | < 5% per colonne critiche     |
| **Distribution** | I valori sono plausibili     | Media, deviazione std, outlier  | < 2 std dalla media storica   |

## 3. SLI e SLO per i Dati


### Service Level Indicators (SLI)


Gli SLI sono le metriche specifiche che misurano la qualita del servizio dati:


```plain text
SLI per un data warehouse di marketing:

1. Data Freshness SLI
   Definizione: % di tabelle con dati aggiornati nelle ultime 2 ore
   Formula: tabelle_fresche / tabelle_totali * 100

2. Data Completeness SLI
   Definizione: % di righe senza NULL nelle colonne obbligatorie
   Formula: righe_complete / righe_totali * 100

3. Query Performance SLI
   Definizione: % di query dashboard completate in < 5 secondi
   Formula: query_veloci / query_totali * 100

4. Pipeline Reliability SLI
   Definizione: % di esecuzioni dbt riuscite
   Formula: run_successo / run_totali * 100
```


### Service Level Objectives (SLO)


Gli SLO sono gli obiettivi che ci si pone sugli SLI:


| SLI                  | SLO                      | Conseguenza Violazione                     |
| -------------------- | ------------------------ | ------------------------------------------ |
| Data Freshness       | ≥ 99.5% tabelle fresche | Alert PagerDuty, incidente P2              |
| Data Completeness    | ≥ 99.9% righe complete  | Alert Slack, ticket automatico             |
| Query Performance    | ≥ 95% query < 5s        | Ottimizzazione query nella prossima sprint |
| Pipeline Reliability | ≥ 99% run riusciti      | Post-mortem se < 95% nel mese              |

## 5. Regole di Alerting


### Alert per Data Freshness


```yaml
# rules/data_quality_alerts.yml
groups:
  - name: data_freshness
    interval: 60s
    rules:
      - alert: DataStaleFactCampaign
        expr: >
          (time() - dbt_model_last_success_timestamp{model="fact_campaign_performance"})
          > 7200
        for: 10m
        labels:
          severity: critical
          team: data-engineering
        annotations:
          summary: "Tabella fact_campaign_performance non aggiornata"
          description: >
            La tabella fact_campaign_performance non viene aggiornata
            da {{ $value | humanizeDuration }}.
            Ultimo aggiornamento: {{ $value }}.
          runbook: "https://wiki.internal/runbooks/stale-data"

      - alert: DataFreshnessViolation
        expr: >
          (count(time() - dbt_model_last_success_timestamp > 7200))
          / count(dbt_model_last_success_timestamp) > 0.005
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "SLO Data Freshness a rischio (> 0.5% tabelle stale)"
```


### Alert per Volume Anomalie


```yaml
- name: data_volume
    rules:
      - alert: InsertVolumeAnomaly
        expr: >
          abs(
            rate(clickhouse_inserted_rows_total{table="fact_events"}[1h])
            - avg_over_time(rate(clickhouse_inserted_rows_total{table="fact_events"}[1h])[7d:1h])
          ) / stddev_over_time(rate(clickhouse_inserted_rows_total{table="fact_events"}[1h])[7d:1h])
          > 3
        for: 30m
        labels:
          severity: warning
        annotations:
          summary: "Volume inserimento anomalo per fact_events"
          description: >
            Il volume di inserimento per fact_events devia di piu di
            3 deviazioni standard dalla media settimanale.

      - alert: ClickHouseTooManyParts
        expr: clickhouse_table_parts > 300
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "Troppe parti in tabella ClickHouse"
          description: >
            La tabella {{ $labels.table }} ha {{ $value }} parti attive.
            Questo indica problemi di ingestione o merge.
```


### Alert per Pipeline Failures


```yaml
- name: pipeline_health
    rules:
      - alert: DbtRunFailed
        expr: dbt_run_errors_total > 0
        for: 5m
        labels:
          severity: critical
          team: data-engineering
        annotations:
          summary: "Esecuzione dbt fallita"
          description: >
            Il run dbt ha {{ $value }} errori.
            Controlla i log per i dettagli.

      - alert: KafkaConsumerLag
        expr: kafka_consumer_group_lag{group="clickhouse_cdc_consumer"} > 10000
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Consumer lag Kafka elevato per CDC"
          description: >
            Il consumer {{ $labels.group }} ha un lag di {{ $value }} messaggi
            sul topic {{ $labels.topic }}.
```


## 6. Data Quality Checks con SQL


Oltre al monitoring dell'infrastruttura, servono controlli diretti sulla qualita dei dati:


### Check di Completezza


```sql
-- Percentuale di NULL per ogni colonna critica
SELECT
    'campaign_id' AS column_name,
    countIf(campaign_id = 0) * 100.0 / COUNT(*) AS null_pct
FROM fact_campaign_performance
WHERE event_date = today() - 1

UNION ALL

SELECT
    'spend',
    countIf(spend = 0) * 100.0 / COUNT(*)
FROM fact_campaign_performance
WHERE event_date = today() - 1

UNION ALL

SELECT
    'impressions',
    countIf(impressions = 0) * 100.0 / COUNT(*)
FROM fact_campaign_performance
WHERE event_date = today() - 1;
```


### Check di Volume


```sql
-- Confronto volume giornaliero con media mobile 7 giorni
WITH daily_counts AS (
    SELECT
        event_date,
        COUNT(*) AS row_count
    FROM fact_campaign_performance
    WHERE event_date ≥ today() - 14
    GROUP BY event_date
),
stats AS (
    SELECT
        AVG(row_count) AS avg_7d,
        stddevPop(row_count) AS stddev_7d
    FROM daily_counts
    WHERE event_date BETWEEN today() - 8 AND today() - 1
)
SELECT
    dc.event_date,
    dc.row_count,
    s.avg_7d,
    ROUND(ABS(dc.row_count - s.avg_7d) / NULLIF(s.stddev_7d, 0), 2) AS z_score,
    if(z_score > 3, 'ANOMALIA', 'OK') AS status
FROM daily_counts dc, stats s
WHERE dc.event_date = today() - 1;
```


### Check di Distribuzione


```sql
-- Verifica che la distribuzione dei canali sia plausibile
SELECT
    channel_id,
    COUNT(*) AS events,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS pct_total,
    -- Confronta con la media storica
    ROUND(AVG(COUNT(*)) OVER (
        PARTITION BY channel_id
        ORDER BY event_date
        ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING
    ), 0) AS avg_7d
FROM fact_campaign_performance
WHERE event_date = today() - 1
GROUP BY channel_id, event_date
ORDER BY events DESC;
```

## 10. OpenTelemetry per Data Pipeline

**OpenTelemetry (OTel)** è lo standard open source per l'instrumentazione di applicazioni distribuite. Nato dalla fusione di OpenCensus e OpenTracing, è ora il progetto CNCF più adottato dopo Kubernetes. Per le pipeline dati, OTel offre un'instrumentazione uniforme per i tre segnali: tracce, metriche e log — con un singolo SDK e un protocollo standard (OTLP).

### Perché OTel per le Pipeline Dati

Senza OpenTelemetry, il monitoring di una pipeline Kafka → ClickHouse → dbt richiede:
- JMX Exporter per Kafka (Java)
- Un exporter custom per ClickHouse
- Un plugin dbt per le metriche
- Tre sistemi di log distinti

Con OpenTelemetry, ogni componente emette dati nel formato OTLP che un OpenTelemetry Collector riceve, processa e instrada verso Prometheus/Grafana o altri backend.

### Instrumentazione di un Pipeline dbt con OTel

```python
# data_pipeline_otel.py
from opentelemetry import trace, metrics
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.trace.export import BatchSpanProcessor
import time

# Configura il provider con esportatore OTLP verso il collector
provider = TracerProvider()
exporter = OTLPSpanExporter(endpoint="http://otel-collector:4317", insecure=True)
provider.add_span_processor(BatchSpanProcessor(exporter))
trace.set_tracer_provider(provider)

tracer = trace.get_tracer("dbt-pipeline")

def run_dbt_model(model_name: str):
    """Esegue un modello dbt con tracing OTel completo."""
    with tracer.start_as_current_span(f"dbt.run.{model_name}") as span:
        span.set_attribute("dbt.model_name", model_name)
        span.set_attribute("dbt.target", "production")

        start = time.time()
        try:
            # Esegui il modello dbt...
            result = execute_dbt_model(model_name)
            duration_ms = (time.time() - start) * 1000

            span.set_attribute("dbt.rows_affected", result.rows_affected)
            span.set_attribute("dbt.duration_ms", duration_ms)
            span.set_attribute("dbt.status", "success")
            return result

        except Exception as e:
            span.record_exception(e)
            span.set_attribute("dbt.status", "error")
            span.set_attribute("dbt.error_message", str(e))
            raise
```

Il vantaggio principale di OTel per le pipeline: ogni esecuzione dbt diventa una **traccia distribuita** che mostra il tempo speso in ogni modello, le dipendenze tra modelli e i colli di bottiglia. Invece di guardare log testuali, vedi un grafico a cascata che rivela immediatamente dove la pipeline ha rallentato.

### OpenTelemetry Collector per Pipeline Dati

```yaml
# otel-collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

    config:
      scrape_configs:

          static_configs:
            - targets: ['clickhouse:9363']
        - job_name: 'kafka'
          static_configs:
            - targets: ['kafka-exporter:9308']

processors:
  # Arricchisci le tracce con attributi del team
  attributes:
    actions:
      - key: team
        value: data-engineering
        action: insert
      - key: environment
        value: production
        action: insert

  # Filtra le tracce a bassa latenza (< 100ms) per ridurre il volume
  filter:
    spans:

        match_type: regexp

          - key: dbt.duration_ms
            value: "^[1-9][0-9]{2,}.*"  # solo span > 100ms

exporters:
  # Metriche a Prometheus/Grafana

    endpoint: http://prometheus:9090/api/v1/write

      exporters: [prometheusremotewrite]
```

### SLI/SLO per Data Engineering: Definizioni Pratiche

La differenza tra SLI, SLO e SLA applicata alle pipeline dati:

- **SLI (Service Level Indicator)**: La metrica misurata. "La percentuale di tabelle aggiornate nelle ultime 2 ore."
- **SLO (Service Level Objective)**: Il target interno. "Il 99.5% delle tabelle deve essere aggiornato nelle ultime 2 ore."
- **SLA (Service Level Agreement)**: L'accordo contrattuale con l'esterno. "Garantiamo ai team consumer dati aggiornati entro 4 ore, altrimenti escalation."

Per il data engineering, gli SLO più importanti da definire e monitorare:

**Freshness SLO**: La tabella `fact_campaign_performance` deve essere aggiornata entro 2 ore dal termine del job dbt. Violazione → alert PagerDuty P2.

```promql
# Query PromQL per calcolare il Freshness SLO
# Tabelle con dati aggiornati nelle ultime 2 ore / tabelle totali
(
  count(time() - dbt_model_last_success_timestamp < 7200)
  /
  count(dbt_model_last_success_timestamp)
) * 100
```

**Volume Anomaly SLO**: Il volume giornaliero di `fact_events` non deve deviare più del 30% dalla media mobile degli ultimi 7 giorni. Violazione → alert Slack + analisi automatica della causa.

**Query Performance SLO**: Il 95% delle query sulla dashboard executive deve completarsi in meno di 5 secondi. Violazione → ottimizzazione nella prossima sprint, valutare nuove Materialized Views.

**Panel 5 — Query Latency Distribution (Heatmap)**:
Distribuzione della latenza delle query per ora del giorno, permette di identificare picchi di carico e ottimizzare la pianificazione degli ETL.

La configurazione completa della dashboard Grafana si esporta come JSON e viene versionata in Git insieme al resto dell'infrastruttura — così ogni modifica alla dashboard passa da code review esattamente come ogni modifica al codice.

### Alerting Budget e Error Budget

Il concetto di **error budget** (budget di errore) viene dal Site Reliability Engineering (SRE) di Google. Se il tuo SLO di freshness è 99.5%, significa che puoi permetterti 0.5% di violazioni — cioè circa 3.6 ore di dati stale al mese.

Tracciare il consumo dell'error budget nel tempo è fondamentale per decidere quando investire in affidabilità vs nuove feature. Se a metà mese hai già consumato il 70% del tuo error budget mensile, devi rallentare le modifiche alla pipeline e investire in stabilità prima di procedere con sviluppi.

In Grafana, l'error budget si visualizza come pannello "burn rate": quante volte più velocemente del normale stai consumando il budget. Un burn rate > 1 significa che sei on track per violare il SLO entro la fine del mese; un burn rate > 6 significa che violerai il SLO entro la settimana — trigger per un alert immediato.

_Il monitoring non e un progetto da completare una volta: e una disciplina continua. Ogni incidente rivela una lacuna nel monitoring. Ogni post-mortem genera un nuovo alert, un nuovo check, un nuovo pannello nella dashboard. Il team dati che investe nel monitoring investe nella fiducia che l'organizzazione ripone nei propri dati._

## Riepilogo Operativo

- Monitoring e observability servono a rendere i problemi visibili prima che diventino crisi per il business.
- SLI, SLO ed error budget aiutano a dare priorita' operative invece di accumulare alert senza criterio.
- Dashboard, alert e post-mortem devono formare un sistema unico di apprendimento operativo.
- La fiducia nei dati cresce quando il team sa rilevare, spiegare e correggere i problemi in tempi prevedibili.
