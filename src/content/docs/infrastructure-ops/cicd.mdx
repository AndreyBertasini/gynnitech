"Ieri i dati erano giusti, oggi sono sbagliati". Se lavori con i dati, questa è la frase che temi di più. Solitamente accade perché qualcuno, da qualche parte, ha modificato una riga di codice SQL, o uno sviluppatore ha rinominato una colonna nel database senza avvisare nessuno.

Per decenni, il mondo del software engineering ha risolto questo problema inventando la **CI/CD (Continuous Integration e Continuous Deployment)**. Nel mondo del Data Engineering, questo concetto è arrivato solo di recente, diventando però lo standard aureo per i team data-driven di alto livello. In questa lezione impareremo a trattare "i dati come codice".

## Il Problema dello Sviluppo Dati Tradizionale

Nel tipico workflow (ormai obsoleto), un analista che voleva aggiungere una colonna "LTV" a una tabella procedeva così:
1. Apriva l'interfaccia web del database (es. BigQuery Console).
2. Scriveva la query `ALTER TABLE` o ricreava la vista.
3. Premeva "Run".
4. Sperava che i cruscotti di Looker o Tableau, collegati a quella tabella, non si rompessero.

Questo approccio si chiama "Programmare in Produzione". È l'equivalente digitale del guidare bendati. Se fai un errore (es. un `JOIN` che duplica le righe), l'errore si propaga istantaneamente a tutti i report direzionali, generando sfiducia totale nei dati da parte del management.

## Cos'è la CI/CD applicata ai Dati?

La CI/CD per i dati (DataOps) impone che **nessuna modifica strutturale** possa essere fatta direttamente in produzione. Ogni modifica deve passare attraverso un rigoroso processo di controllo, testing automatizzato e approvazione. 

<Steps>
1. **Branching (Sviluppo Isolato)**
   Invece di modificare la tabella `fct_orders`, l'analista crea un "ramo" separato del codice (Branch) su Git (es. `feature/add-ltv-column`). Lavora in un ambiente isolato (un database di sviluppo) che è una copia dell'ambiente di produzione.
2. **Continuous Integration (CI - Test e Validazione)**
   Quando l'analista ha finito, apre una "Pull Request" (PR) per unire il suo codice. A questo punto, una macchina (es. GitHub Actions o GitLab CI) si sveglia e testa automaticamente il codice: 
   - Compila il nuovo SQL.
   - Lo esegue su un sottoinsieme di dati finti (Dry Run).
   - Verifica che la nuova colonna non contenga valori nulli.
   - Verifica che i numeri totali di fatturato combacino ancora (Data Quality Tests).
3. **Code Review (Revisione Umana)**
   Se e solo se tutti i test automatici passano (luce verde), un Data Engineer Senior guarda il codice SQL per assicurarsi che sia ottimizzato (es. non ci siano cross-join costose).
4. **Continuous Deployment (CD - Rilascio Automatico)**
   Una volta approvata, il codice viene fuso nel ramo principale (`main`). Un altro processo automatico si sveglia, prende quel codice e lo esegue finalmente nel database di Produzione, aggiornando in sicurezza le tabelle finali.
</Steps>

<Aside type="tip" title="Lo Standard di Mercato">
  Oggi, l'implementazione standard di questo flusso avviene combinando **dbt (data build tool)** per la scrittura dei test e della logica, e **GitHub Actions** (o GitLab CI) per l'orchestrazione automatica dei controlli.
</Aside>

## I Tre Ambienti: Dev, Staging, Prod

Un'infrastruttura CI/CD matura si basa sulla segregazione fisica o logica degli ambienti:

<CardGrid>
  <Card title="Ambiente di Sviluppo (Dev)" icon="setting">
    Il "parco giochi" degli analisti. Ogni analista ha il suo schema privato (es. `dbt_andrea`). Qui si testa l'SQL su un campione limitato di dati (es. solo gli ultimi 3 giorni) per scrivere le query velocemente senza spendere troppo in costi di computazione.
  </Card>
  <Card title="Ambiente di Staging / CI" icon="puzzle">
    L'ambiente temporaneo dove le macchine (GitHub Actions) costruiscono tutto il progetto da zero ogni volta che viene aperta una Pull Request. Serve per validare che l'intero "grafo" (DAG) dei modelli funzioni insieme prima della fusione finale.
  </Card>
  <Card title="Ambiente di Produzione (Prod)" icon="rocket">
    L'unica "Single Source of Truth". Solo i processi automatici di CD possono scrivere in questo ambiente. Nessun essere umano, nemmeno il CTO, dovrebbe avere i permessi per eseguire query di modifica (DDL/DML) manuali qui dentro. I cruscotti aziendali leggono SOLO da questo ambiente.
  </Card>
</CardGrid>

## Il "Data Contract" (Contratto sui Dati)

Il livello più avanzato di CI/CD oggi affronta il problema alla radice: le modifiche del team di Ingegneria Software al prodotto. Se un dev cambia il nome della colonna `user_age` in `age` nel database dell'app, le pipeline di dati si romperanno a valle.

La soluzione è il **Data Contract**: un contratto formale stipulato tramite file (es. JSON Schema) che definisce l'esatta struttura dei dati che l'applicazione promette di inviare al Data Warehouse. La CI/CD del prodotto (l'app) include un test: se lo sviluppatore rompe il contratto (rimuove una colonna richiesta), la build dell'app fallisce prima ancora di andare online.

## Takeaway Actionable
Se nel tuo team chiunque può aprire DBeaver, BigQuery Console o Metabase e alterare la struttura di una tabella di produzione, hai un debito tecnico gigantesco pronto ad esplodere. Il primo passo è revocare i permessi di scrittura diretti in produzione. Il secondo è inserire tutto l'SQL in una repository Git (GitHub/GitLab) e iniziare a fare Code Review tra colleghi prima di rilasciare. La fiducia nei dati si costruisce solo eliminando l'errore umano silenzioso.
