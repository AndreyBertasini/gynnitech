You ask the agent: "Which users activated this week?" It answers. Then you find out that "activated" means different things in three tables: in one, users who completed onboarding; in another, those who created a project; in a third, those who invited a colleague.

The problem is not the question but the data model.

## An agent needs clear entities

To analyze properly, you must know what exists in your domain: users, accounts, events, sessions, features, experiments, sources, tasks, outputs, decisions. Each entity must have precise relationships. Does an event belong to a user? To an account? Both? Which task is an output linked to? Who approved a decision?

These seemingly technical questions define what the organization can truly understand.

## Model for the questions you need to answer

A good data model arises from the operational questions the team must ask. To know if an agent improves onboarding, you need to connect exposure, interaction, setup completion, and return visits. To see if it reduces support workload, link tickets, drafts, human edits, reopenings, and satisfaction. To evaluate marketing insights, connect proposals, experiments, results, and decisions.

The data model should reflect decisions, not just source systems.

## Avoid duplication and ambiguity

Inconsistent IDs, duplicate events, conflicting timestamps, and unshared definitions ruin analysis. An AI agent can mask these issues with fluent answers, but fluency is not reliability.

You need a data glossary listing metric name, definition, source, owner, update frequency, and limits.

## How to apply data modeling without complicating work

Don't start with the newest tool. Start where the team wastes time, argues without data, or makes decisions with incomplete information. That reveals if the topic has operational value or is just a nice slide idea.

An agent is not a clever chat: it needs clear inputs, limited tools, controlled memory, and an explicit rule to hand off decisions to a human when risk rises.

A useful sequence:

1. Define which data the agent can read and which it cannot.
2. Write the expected result in a verifiable form, not as a vague intention.
3. Decide when human review is needed before sending or saving output.
4. Measure time saved, errors avoided, and cases where the agent stops.

## What to measure to know if it works

The question is not "Did we use AI?" or "Did we add a new dashboard?" The question is: which decision became faster, clearer, or safer? If no decision changes, the project risks being mere technical decoration.

Measure at least three levels: operational time saved, result quality, and team trust in the process. Time alone can mislead: a faster flow that's less controllable is not an improvement. Quality alone can mislead: a perfect system that's too slow won't enter daily work.
