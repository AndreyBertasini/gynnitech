You built an agent that answers customer questions using your company's knowledge base. At first, it seems perfect. Then a customer asks about returns, and the agent cites an outdated policy. It didn't make it up - it retrieved the wrong source.

This is the paradox of Retrieval-Augmented Generation (RAG): it reduces hallucinations but does not solve the problem of source quality.

## Retrieval is a decision

When an agent retrieves a source, it's already making a decision. It decides which documents matter and which don't. It decides if an updated policy beats an old manual. It decides if a short FAQ is more useful than a long procedure.

If you don't measure this step, you only measure the final output. That's too late.

You need to track at least:

- the agent's query;
- candidate documents;
- the chosen document;
- the source version;
- retrieval confidence;
- the final answer;
- human or user feedback.

This telemetry helps identify whether the problem lies in the model, the documents, or the index structure.

## The knowledge base is not neutral

A RAG agent reflects the state of your archive. If documentation is duplicated, outdated, or poorly written, the agent amplifies that disorder.

Before asking AI to "answer better," clean up:

1. remove outdated documents;
2. assign an owner to each source;
3. add dates and versions;
4. separate official policies from internal notes;
5. create real question examples.

RAG is not just semantic technology. It's knowledge governance.

## Measure usefulness, not just correctness

An answer can be correct but not useful. For example, the agent cites the right policy but doesn't explain the next step. Or it uses a valid source but too technical for a customer.

That's why you need different metrics:

- source accuracy;
- answer completeness;
- time saved;
- escalation rate;
- ticket reopenings;
- customer or team satisfaction.

Growth engineering brings a valuable discipline here: every improvement must link to observable behavior.

## How to apply it without complicating work

To make RAG and Growth Engineering practical, don't start with the newest tool. Start where the team wastes time, debates without data, or makes decisions with incomplete information. That's where you see if the topic has real operational value or is just a nice slide idea.

The rule is simple: treat the agent not as a clever chat but as a tool with clear inputs, limited tools, controlled memory, and an explicit rule to hand off decisions to a person when risk rises.

A useful sequence is:

1. define what data the agent can read and what it must not touch;
2. write the expected result in a verifiable form, not a generic intention;
3. decide when human review is needed before sending or saving output;
4. measure time saved, errors avoided, and cases where the agent stops.

## What to measure to know if it works

The right question is not "Did we use AI?" or "Did we add a new dashboard?" The right question is: which decision became faster, clearer, or safer? If no decision changes, the project risks being technical decoration.

Measure at least three levels: operational time saved, result quality, and team trust in the process. Time alone can mislead: a faster but less controllable flow is not an improvement. Quality alone can mislead: a perfect system that's too slow won't really enter daily work.

## The human factor

An agent that cites reliable sources is not just more accurate. It's more respectful. It doesn't ask users to trust a synthetic voice. It shows them there's a verifiable basis behind the answer.

The real question is not: "Does our agent use RAG?" The question is: "When it retrieves a source, can we trust why it chose it?"
