## Real-world problem

In daily data work with AI, the risk is turning analysis into a series of unverifiable answers. The concrete challenge is to know when AI can suggest code or insights and when human analytical review is needed. Without a rigorous operational design, analysts risk wasting time or delivering fragile explanations.

## Conceptual model

The work unfolds across four levels: task, context, control, and decision. AI accelerates tasks like query drafting or checklist creation, but context defines data, metrics, and constraints. Control is needed to detect errors or inconsistencies, while decision determines the subsequent action. This model helps avoid two opposite mistakes: using AI merely as a text autocomplete or entrusting it with business decisions without oversight.

| Level     | What to clarify                          | Example in data work                       |
|-----------|-----------------------------------------|--------------------------------------------|
| Task      | Which part of the work is accelerated?  | Query draft, data profile, AutoML checklist|
| Context   | What information makes the output useful?| Schema, metric, period, segment, policy    |
| Control   | How to detect if the output is wrong?   | Grain tests, baseline, leakage checks, owner review|
| Decision  | What action follows if control passes?  | Pipeline fix, experiment, deployment, recommendation|

## Rigorous formalization

To make the process analyzable, define the unit of work (query, notebook cell, chart, memo, or derived metric) and associate observable signals such as logical correctness, readability, performance, grain tests, and narrative clarity. The expected decision is to determine when AI can propose code and when analytical review is required. Guardrails include privacy, cost, data quality, interpretability, ownership, and operational risk.

| Element         | Required specification                                                             |
|-----------------|------------------------------------------------------------------------------------|
| Unit of analysis| Query, notebook cell, chart, memo, or derived metric                              |
| Main signal     | Logical correctness, readability, performance, grain test, narrative clarity      |
| Baseline        | Manual process, previous period, comparable group, or current model               |
| Decision        | Determine when AI can propose code and when code review is necessary              |
| Guardrail       | Privacy, cost, data quality, interpretability, ownership, operational risk        |
| Main risk       | Accepting plausible SQL that duplicates rows, changes grain, or ignores critical filters|

## Example or case study

An analyst asks AI for a monthly retention query. The first version is syntactically correct, but review reveals it counts reactivated users as new, altering the grain. Correcting this improves output quality. This case shows AI as a tool within the decision cycle: question, data, control, recommendation, and monitoring. Each step remains controllable.

| Observed evidence           | Cautious interpretation                        | Recommended action                        |
|----------------------------|-----------------------------------------------|------------------------------------------|
| Faster output              | Speed is useful only if quality and control hold| Compare with manual baseline and independent review|
| Plausible explanations     | Linguistic plausibility is not empirical proof | Translate explanations into data/process controls|
| Metric improvement         | Possible composition effect or leakage          | Segment, verify guardrails, monitor over time|

## Lab / exercise

### Basic level

Write a one-page sheet for a simple case: decision to support, required inputs, expected output, minimum control, and main risk. For example, conversion variation or delayed pipeline.

### Intermediate level

Build a table with three scenarios: manual workflow, AI-assisted workflow, and advanced automation. For each, indicate estimated time, expected quality, operational risk, necessary control, and final owner.

### Research-grade level

Prepare a reviewable decision memo including hypotheses, required data, exclusion criteria, quality controls, decision threshold, residual risk, and post-decision monitoring plan. Add a section on "what would change the team's mind."

### Recommended datasets and materials

Use data warehouse schemas, existing queries, analysis notebooks, metric definitions, and SQL tests. If unavailable, create a synthetic dataset with at least 200 rows, a time dimension, a segment dimension, a primary metric, and a field representing potential quality errors.

## Common mistake to avoid

The first mistake is treating SQL, notebooks, and data storytelling with AI as a label rather than a process. This happens when teams present generated output without explaining data, controls, and decisions. The second is confusing individual productivity with organizational reliability. The third is failing to decide upfront which actions are allowed, require approval, or are forbidden.

A practical fix is to write three lines before starting:

| Line      | Content                                     |
|-----------|---------------------------------------------|
| Decision  | Which concrete choice do we want to improve?|
| Evidence  | Which data or control supports the choice?  |
| Stop      | What risk would make us stop or ask for review?|

If any of these are missing, the workflow is not ready. AI can still help exploratory support but not as a stable part of the decision process.

## Quiz or checkpoint

1. What concrete decision should this lesson improve?
2. Which part of the workflow can be delegated to AI and which must remain under human ownership?
3. What baseline would you use to measure if the new process truly improves?
4. What failure mode could make an apparently correct output dangerous?
5. What artifact would you deliver to a stakeholder: memo, dashboard, query review, model card, runbook, or checklist?

If you cannot answer specifically, return to the real-world problem before proceeding. A generic answer often signals premature automation.

## Operational summary

SQL, notebooks, and data storytelling with AI become valuable when they produce clearer decisions, not just new terminology. The cycle of decision, context, AI support, verification, and handoff turns the lesson into verifiable practice. The more the workflow uses prompts, controls, metrics, and human review, the more it must be observable. An output you cannot reconstruct, review, or stop is not professional automation but uncontrolled speed.
