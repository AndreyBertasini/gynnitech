# Evaluation: leakage, drift, metrics, and limits

In working with data and AI models, the biggest risk is not just having AI "do analysis," but losing control over what we actually know, what we verify, and how we decide. This lesson tackles exactly that: how to build a workflow that makes questions, data, checks, and decisions explicit, avoiding fragile or unverifiable answers.

## Starting point

Imagine a weekly meeting between marketing, product, and data teams. They must decide what to fix first: funnel, tracking, campaign, model, or pipeline. Without AI, analysts risk spending hours on repetitive steps; with AI used without discipline, they risk delivering persuasive but unstable explanations.

The difference lies in operational design: AI should help formulate hypotheses, create checklists, suggest checks, synthesize results, and prepare outputs. It cannot replace data verification, metric ownership, or business choices. Every step must leave a trace readable and contestable by a reviewer.

| Moment | Useful use | Necessary check |
|---|---|---|
| Before analysis | Clarify question, constraints, expected output | Confirm owner, metric, baseline |
| During analysis | Suggest checks, segments, alternative explanations | Verify data, granularity, filters, edge cases |
| After analysis | Prepare memo, trade-offs, next steps | Separate evidence, hypothesis, recommendation |

## Why it matters in data work

The bottleneck is not just writing code but understanding which question deserves an answer, which data is reliable, which metric changes the decision, and what risk remains after recommendation. This process makes those steps explicit.

A good AI workflow has four properties:

1. It starts from a decision, not a tool.
2. It declares inputs, constraints, and expected output.
3. It produces reviewable artifacts, not just final text.
4. It includes a stop criterion when data or model do not hold.

Without these, work looks modern but remains fragile. AI boosts productivity only if it also improves question quality and control discipline.

## Operational framework

Five steps guide the process:

| Step | Guiding question | Minimum output |
|---|---|---|
| Decision | Which choice must improve? | Action verb and owner |
| Context | What do we know about data? | Sources, granularity, period, limits |
| AI support | Which part can be accelerated? | Prompt, tool, or checklist |
| Verification | Which error could change conclusion? | Check, guardrail, baseline |
| Handoff | Who decides and by what criteria? | Memo, ticket, model, or dashboard |

This applies to exploratory analysis, SQL, data engineering, AutoML, and agent workflows. Tools change, but principle remains: no output is evidence until linked to source, check, and decision.

## Real problem

In AI for Data Analysis, Data Engineering, and AutoML, the problem is deciding if a model can enter the process or remain a controlled experiment. This is not isolated theory but improving a concrete choice with data, explicit assumptions, and minimal checks.

The issue arises when a team wants to speed up data work but cannot distinguish delegable tasks from non-delegable responsibilities. AI can generate hypotheses, queries, documentation, tests, candidate features, or summaries. But decisions remain human when impacting budget, roadmap, clients, compliance, access, or production models.

The goal is to produce a reviewable artifact. If you cannot specify which decision changes, which data you observe, and which error you want to avoid, the lesson has not become applied competence.

## Conceptual model

Four levels define the model:

| Level | What to clarify | Example in data work |
|---|---|---|
| Task | Which part of work AI accelerates? | Query draft, data profile, AutoML checklist, memo |
| Context | What info makes output useful? | Schema, metric, period, segment, policy |
| Check | How to detect if output is wrong? | Granularity test, baseline, leakage, owner review |
| Decision | What action follows if check holds? | Fix pipeline, experiment, deploy, recommendation |

This model avoids two opposite errors: using AI only as text autocomplete or giving it autonomy on decisions requiring business judgment. Professional skill lies in drawing the boundary.

## Rigorous formalization

To analyze evaluation, define the unit of work: split, metric, segment, model, decision threshold, or monitoring. Link this unit to observable signals: train-test gap, feature drift, segment performance, calibration, and stability over time. Finally, declare the expected decision: whether a model can enter the process or remain a controlled experiment.

| Element | Required specification |
|---|---|
| Unit of analysis | split, metric, segment, model, decision threshold, or monitoring |
| Main signal | train-test gap, feature drift, segment performance, calibration, stability over time |
| Baseline | manual process, previous period, comparable group, or current model |
| Decision | enter process or remain controlled experiment |
| Guardrail | privacy, cost, data quality, interpretability, ownership, operational risk |
| Main risk | evaluating only average metric ignoring segments where model fails |

Formalization is solid if a reviewer can reproduce logic, critique assumptions, and reach the same decision from the same data. If results depend on untracked conversations, workflow is immature.

## Example or case study

A lead scoring model improves average conversion but worsens on high-value SMEs. The team adjusts threshold and adds segment monitoring.

This shows AI is not the center, but the decision cycle: question, data, check, recommendation, monitoring. AI reduces friction between steps, but each step remains controllable.

| Observed evidence | Cautious reading | Recommended action |
|---|---|---|
| Faster output | Speed is useful only if quality and control remain | Compare with manual baseline and independent review |
| Plausible explanations | Linguistic plausibility is not empirical proof | Translate each explanation into data or process check |
| Metric improves | Could be composition effect, leakage, or seasonality | Segment, verify guardrails, monitor over time |

A good case study does not end with "AI worked" but with a defensible decision: what to automate, what to keep manual, which metric to monitor, and what condition would stop the process.

## Lab / exercise

### Basic level

Write a one-page sheet for Evaluation: leakage, drift, metrics, and limits. Include decision to support, required inputs, expected output, minimum check, and main risk. Use a simple case, e.g., conversion variation, delayed pipeline, or forecast model to evaluate.

### Intermediate level

Build a table with three scenarios: manual workflow, AI-assisted, and heavily automated. For each, indicate estimated time, expected quality, operational risk, necessary check, and final owner.

### Research-grade level

Prepare a reviewable decision memo. Include hypotheses, required data, exclusion criteria, quality checks, decision threshold, residual risk, and monitoring plan after decision. Add a section "what would change the team's mind."

### Recommended datasets and materials

Use evaluation reports, confusion matrices, backtests, drift monitoring, segment metrics, and decision policies. If no real data, create synthetic dataset with at least 200 rows, temporal dimension, segment dimension, primary metric, and a field representing possible quality error.

## Common mistake to avoid

The first mistake is treating Evaluation: leakage, drift, metrics, and limits as a label rather than a process. This happens when output is shown without explaining data, checks, and decision. The second is confusing individual productivity with organizational reliability. The third is not deciding upfront which actions are allowed, require approval, or are forbidden.

The practical fix is to write three lines before starting:

| Line | Content |
|---|---|
| Decision | Which concrete choice we want to improve |
| Evidence | Which data or check supports the choice |
| Stop | Which risk would make us stop or ask for review |

If any is missing, workflow is not ready. AI can still be exploratory support but not stable part of decision process.

## Quiz or checkpoint

1. Which concrete decision should this lesson improve?
2. Which part of the workflow can be delegated to AI and which must remain under human ownership?
3. Which baseline would you use to measure if the new process really improves?
4. Which failure mode could make an apparently correct output dangerous?
5. Which artifact would you deliver to a stakeholder: memo, dashboard, query review, model card, runbook, or checklist?

If you cannot answer specifically, return to the real problem before continuing. Generic answers often signal premature automation.

## Operational summary

Evaluation: leakage, drift, metrics, and limits is useful only if it produces a clear decision, not just new terminology. Use the cycle decision, context, AI support, verification, and handoff to turn the lesson into verifiable practice.

The final rule is simple: the more the workflow uses prompts, checks, metrics, and human review, the more it must be observable. An output you cannot reconstruct, review, or stop is not professional automation; it is just uncontrolled speed.
