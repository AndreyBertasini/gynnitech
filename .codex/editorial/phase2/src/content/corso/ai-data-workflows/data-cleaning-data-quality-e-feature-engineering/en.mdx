# Data cleaning, data quality, and feature engineering

In data work, AI should not turn analysis into a series of unverifiable answers. The real value lies in designing an operational flow where questions, data, checks, and decisions remain transparent and traceable. This approach builds on the previous lesson about SQL, notebooks, and AI-assisted data storytelling, adding a more specific operational layer to maintain ownership over definitions, thresholds, segments, and recommendations while boosting speed and coverage.

## A starting scenario

Imagine a weekly review where marketing, product, and data teams must decide what to fix first: funnel, tracking, campaign, model, or pipeline. Without AI assistance, analysts spend hours on repetitive steps; with poorly used AI, they risk delivering convincing but fragile explanations. The difference lies in operational design: AI should support hypothesis formulation, checklists, controls, synthesis, and output preparation without replacing data verification, metric responsibility, or business decisions. Every step must leave a readable, contestable trace.

| Moment | Useful use | Necessary check |
|---|---|---|
| Before analysis | Clarify question, constraints, expected output | Confirm owner, metric, baseline |
| During analysis | Suggest checks, segments, alternative explanations | Verify data, grain, filters, edge cases |
| After analysis | Prepare memo, trade-offs, next steps | Separate evidence, hypothesis, recommendation |

## Why it matters in data work

The bottleneck is often not coding but understanding which question to answer, which data is reliable, which metric changes the decision, and what risk remains after the recommendation. Data cleaning, data quality, and feature engineering make these steps explicit, enhancing quality and control discipline. A good AI workflow starts from a decision, declares inputs and outputs, produces reviewable artifacts, and includes a stop criterion if data or model fail.

## Operational framework

Five key steps:

| Step | Guiding question | Minimum output |
|---|---|---|
| Decision | Which choice should improve? | Action verb and owner |
| Context | What do we know about the data? | Sources, grain, period, limits |
| AI support | Which part can be accelerated? | Prompt, tool, checklist |
| Verification | What error could change the conclusion? | Control, guardrail, baseline |
| Handoff | Who decides and by what criteria? | Memo, ticket, model, dashboard |

This framework applies to exploratory analysis, SQL, data engineering, AutoML, and agent workflows. No output should be treated as evidence without source, check, and decision.

## Real problem

In AI for Data Analysis, Data Engineering, and AutoML, the challenge is deciding which transformations to automate and which require domain owners. Teams often confuse delegable tasks with non-delegable responsibilities. AI can help generate hypotheses, queries, documentation, tests, candidate features, or summaries, but decisions remain human when impacting budget, roadmap, customers, compliance, or production models. The goal is to produce reviewable artifacts that explicitly state the decision, observed data, and errors to avoid.

## Conceptual model

Four levels:

| Level | What to clarify | Example in data work |
|---|---|---|
| Task | Which part does AI accelerate? | Query draft, data profile, AutoML checklist, memo |
| Context | What information makes output useful? | Schema, metric, period, segment, policy |
| Control | How to detect wrong output? | Grain test, baseline, leakage, owner review |
| Decision | What action follows if control passes? | Pipeline fix, experiment, deploy, recommendation |

This model avoids two opposite errors: using AI only as text autocomplete or granting autonomy on business decisions. Professional skill lies in defining the boundary.

## Rigorous formalization

Define the unit of work: field, cleaning rule, data test, feature, or intermediate transformation. Link it to observable signals: missing rate, duplicates, feature stability, leakage risk, drift, explainability. Declare the expected decision: which transformations to automate and which require domain owners.

| Element | Required specification |
|---|---|
| Unit of analysis | field, cleaning rule, data test, feature, intermediate transformation |
| Main signal | missing rate, duplicates, feature stability, leakage risk, drift, explainability |
| Baseline | manual process, previous period, comparable group, current model |
| Decision | which transformations to automate and which require domain owners |
| Guardrail | privacy, cost, data quality, interpretability, ownership, operational risk |
| Main risk | creating powerful features contaminated by future information or unstable definitions |

Formalization is solid when a reviewer can reproduce the logic, critique assumptions, and reach the same decision with the same data. If results depend on untracked conversations, the workflow is immature.

## Example or case study

A team builds a churn model. AI suggests features from tickets and payments, but one feature includes events after the prediction date. Leakage control prevents a false metric.

This case shows AI is not the center, but the decision cycle: question, data, control, recommendation, monitoring. AI reduces friction between steps, but each remains controllable.

| Observed evidence | Cautious interpretation | Recommended action |
|---|---|---|
| Faster output | Speed is useful only if quality and control are maintained | Compare with manual baseline and independent review |
| Plausible explanations | Linguistic plausibility is not empirical proof | Translate each explanation into data or process control |
| Metric improvement | Could be composition effect, leakage, or seasonality | Segment, verify guardrails, monitor over time |

A good case study ends with a defensible decision: what to automate, what to keep manual, which metric to monitor, and what condition would stop the process.

## Lab / exercise

### Basic level

Write a one-page sheet for data cleaning, data quality, and feature engineering: decision to support, required inputs, expected output, minimum control, main risk. Use a simple case like conversion variation, delayed pipeline, or forecast model evaluation.

### Intermediate level

Build a table with three scenarios: manual workflow, AI-assisted workflow, and advanced automation. For each, indicate estimated time, expected quality, operational risk, necessary control, and final owner.

### Research-grade level

Prepare a reviewable decision memo including hypotheses, required data, exclusion criteria, quality controls, decision threshold, residual risk, and monitoring plan. Add a section "what would change the team's mind."

### Recommended datasets and materials

Use profiling reports, data dictionaries, quality logs, feature examples, and target definitions. If real data is unavailable, create a synthetic dataset with at least 200 rows, temporal dimension, segment dimension, primary metric, and a field representing a possible quality error.

## Common mistake to avoid

First mistake: treating data cleaning, data quality, and feature engineering as a label rather than a process, showing outputs without explaining data, controls, and decisions. Second: confusing individual productivity with organizational reliability. Third: not deciding upfront which actions are allowed, require approval, or are forbidden.

Practical fix: write three lines before starting:

| Line | Content |
|---|---|
| Decision | Which concrete choice to improve |
| Evidence | Which data or control supports the choice |
| Stop | Which risk would stop or require review |

If any are missing, the workflow is not ready. AI can still support exploration but not stable decision-making.

## Quiz or checkpoint

1. Which concrete decision should this lesson improve?
2. Which part of the workflow can be delegated to AI and which must remain under human ownership?
3. Which baseline would you use to measure if the new process truly improves?
4. Which failure mode could make an apparently correct output dangerous?
5. Which artifact would you deliver to a stakeholder: memo, dashboard, query review, model card, runbook, or checklist?

If you cannot answer specifically, return to the real problem. Generic answers often signal premature automation.

## Operational summary

Data cleaning, data quality, and feature engineering become useful when they produce clearer decisions, not just terminology. Use the cycle of decision, context, AI support, verification, and handoff to turn the lesson into verifiable practice. The more the workflow uses prompts, controls, metrics, and human review, the more it must be observable. Outputs that cannot be reconstructed, reviewed, or stopped are not professional automation but uncontrolled speed.
