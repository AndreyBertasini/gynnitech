# Advanced joins, semi-joins, anti-joins, and set logic

When a customer report doubles revenue after a join or a fraud check loses users without matches, the database isn't wrong. The query is mixing relationships, filters, and exclusions as if they were the same. Advanced joins, semi-joins, anti-joins, and set logic clarify these operational boundaries.

## Real problem

In advanced SQL, the challenge is writing correct analytical queries when grain, windows, cohorts, and edge cases complicate results. The key is choosing the right operation for the right question, avoiding duplication or omission that skews metrics.

## Conceptual model

Before joining, clarify:

- What relationship between tables do you want to represent?
- What cardinality checks do you perform before and after the join?
- When should you use semi-joins or anti-joins instead of traditional joins?

Each join answers a precise question about combining two sets of rows. The table below maps each operation to its decision question and behavior:

| Operation | Decision question | Behavior | Syntax |
|-----------|-------------------|----------|--------|
| INNER JOIN | Which rows appear in *both* sets? | Returns only the intersection | `FROM A JOIN B ON ...` |
| LEFT JOIN | Which rows of A have (or don't have) matches in B? | All rows of A plus matches from B (NULL if absent) | `FROM A LEFT JOIN B ON ...` |
| SEMI-JOIN | Which rows of A have *at least one* match in B? | Only rows of A, no columns from B, no duplicates | `WHERE EXISTS (SELECT 1 FROM B WHERE ...)` |
| ANTI-JOIN | Which rows of A have *no* matches in B? | Only rows of A without matches in B | `WHERE NOT EXISTS (SELECT 1 FROM B WHERE ...)` |
| LATERAL JOIN | For *each* row of A, run a subquery depending on that row | Iterates row-by-row with a correlated subquery | `FROM A CROSS JOIN LATERAL (SELECT ...) AS b` |
| AS-OF JOIN | What was the state of B *at the time* of the event in A? | Approximate temporal match (closest ≤ timestamp) | `FROM A ASOF JOIN B ON A.ts >= B.ts` |
| UNION ALL | Which rows belong to A *plus* those of B? | Union of sets (keeps duplicates) | `SELECT ... UNION ALL SELECT ...` |
| EXCEPT | Which rows of A are *not* in B? | Set difference | `SELECT ... EXCEPT SELECT ...` |
| INTERSECT | Which rows are in *both* A and B? | Set intersection | `SELECT ... INTERSECT SELECT ...` |

## Rigorous formalization

Define the unit of work (row, partition, window, join, cohort, or temporal metric) and link it to an observable metric (correctness, performance, duplicates, grain, stability). Declare the expected decision (query, intermediate model, test, or reusable pattern) and identify the main risk (confusing available data with sufficient proof).

| Element | Specification |
|---------|---------------|
| Unit of analysis | row, partition, window, join, cohort, or temporal metric |
| Main signal | correctness, performance, duplicates, grain, stability |
| Baseline | prior period, comparable group, benchmark |
| Decision | query, model, SQL test, reusable pattern |
| Risk | interpreting data as definitive proof |

## Example or case study

### Semi-join: DoorDash and active restaurants

DoorDash needed the average revenue per restaurant active in the last 90 days, defined as having at least one order in that period. The naive INNER JOIN query multiplied restaurants by order count, inflating the average. The correct solution uses a semi-join with EXISTS, filtering without duplication:

```sql
SELECT AVG(r.revenue)
FROM restaurants r
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.restaurant_id = r.id
    AND o.order_date >= CURRENT_DATE - INTERVAL '90 days'
);
```

This query is semantically correct and much more efficient.

### Anti-join: Netflix and inactive catalog

Netflix needed to find titles with zero views in the last 12 months. The LEFT JOIN query was inefficient, materializing a huge join. The anti-join version (NOT EXISTS) drastically reduced runtime:

```sql
SELECT t.title_id, t.title_name
FROM titles t
WHERE NOT EXISTS (
  SELECT 1 FROM views v
  WHERE v.title_id = t.title_id
    AND v.view_date >= '2022-01-01'
);
```

### Lateral join: Uber and ETA

Uber calculates estimated time of arrival (ETA) per ride using a function depending on each row's data. The lateral join runs a correlated subquery for each row:

```sql
SELECT
  r.request_id,
  r.pickup_lat, r.pickup_lon,
  eta.predicted_minutes,
  eta.confidence_interval
FROM ride_requests r
CROSS JOIN LATERAL (
  SELECT predicted_minutes, confidence_interval
  FROM eta_model(r.pickup_lat, r.pickup_lon, r.hour, r.traffic_level)
) AS eta
WHERE r.request_date = CURRENT_DATE;
```

### Set logic: Airbnb and listings

Airbnb consolidates listings from three systems using UNION, INTERSECT, and EXCEPT to identify missing or duplicate data:

```sql
-- Listings in all systems
SELECT listing_id FROM host_db
INTERSECT
SELECT listing_id FROM quality_system
INTERSECT
SELECT listing_id FROM pricing_engine;

-- Listings missing from quality system
SELECT listing_id FROM host_db
EXCEPT
SELECT listing_id FROM quality_system;

-- Unified catalog
SELECT listing_id, 'host' AS source FROM host_db
UNION
SELECT listing_id, 'quality' FROM quality_system
UNION ALL
SELECT listing_id, 'pricing' FROM pricing_engine;
```

## Common mistake to avoid

Using advanced joins and set logic as mere labels without process: showing charts without decisions, metrics without baselines, conclusions without explicit assumptions. The key question is: if this result were unstable, which choice would I be making wrong?

## Operational summary

Advanced joins, semi-joins, anti-joins, and set logic are not just syntax but semantic choices that determine correctness and performance. The difference between "it works" and "it works well" lies in choosing the right operation for the right question, turning analysis into concrete decisions.

## Quality control

Before using advanced joins, semi-joins, anti-joins, and set logic in decisions, always check completeness, duplicates, time zones, changed definitions, and excluded segments. Many sophisticated analyses fail because the source data measures a different behavior than the team believes to observe.
