# Date-time pitfalls and timezone correctness

Handling dates and times in data analysis is not just a technical challenge but a decision-making discipline under uncertainty. When a daily dashboard shows a drop at midnight UTC, but European and American teams see different data, it's not a rounding error but an unspoken temporal decision. For reliable decisions, calendar, timestamps, and business days must speak the same language.

## Real-world problem

In advanced SQL, the challenge is writing accurate analytical queries despite complex grains, windows, cohorts, and edge cases. Without clear rules on handling dates and timezones, metrics can mislead. The goal is to turn this complexity into conscious choices, making assumptions and checks explicit.

## Temporal data types: a minimal map

To orient yourself, distinguish three fundamental temporal data types:

| Type | Contains | When to use |
|------|----------|---------------|
| TIMESTAMP / DATETIME | Date + time + (optionally) timezone | Point events with known timezone |
| DATE | Date only, no time | Daily aggregations, birthdays, deadlines |
| INTERVAL | Duration between two timestamps | Delta calculations, deadlines, SLAs |

Tom Kyte's golden rule is simple: always store in UTC and convert to local only at presentation. Ignoring this leads to hard-to-diagnose errors.

## The timezone problem: three classic pitfalls

1. **Assuming the server is in your timezone**

Servers may run in UTC or another timezone. Using `CURRENT_DATE` without specifying timezone can yield wrong dates. Always use `AT TIME ZONE` to specify explicitly.

2. **Comparing dates from different timezones**

If timestamps in different columns have different timezones, their difference does not reflect actual duration. Normalize all to UTC before calculating differences.

3. **DATE_TRUNC at the wrong midnight**

`DATE_TRUNC('day', timestamp)` truncates at UTC midnight, not local. Events on the same local day can fall into different days. Convert to local timezone first, then truncate.

## Generating time series: the date spine

A fundamental practice is creating a **date spine**: a table or CTE with every date in a range. It ensures every period appears in results even if no data exists, avoiding gaps in charts that confuse interpretation.

PostgreSQL example:

```sql
WITH date_spine AS (
  SELECT generate_series('2024-01-01'::date, '2024-12-31'::date, '1 day'::interval)::date AS dt
)
SELECT ds.dt, COALESCE(SUM(o.amount), 0) AS daily_revenue
FROM date_spine ds
LEFT JOIN orders o ON ds.dt = o.order_date::date
GROUP BY ds.dt
ORDER BY ds.dt;
```

Glovo used the date spine to uncover supply issues invisible without it, demonstrating the method's decision-making value.

## Rolling metrics: sliding time windows

Rolling metrics like moving averages and cumulative sums reveal trends and anomalies. Window functions with `RANGE` are essential when there are gaps in the time series.

Rolling 7-day average example:

```sql
SELECT dt, daily_revenue,
  AVG(daily_revenue) OVER (
    ORDER BY dt
    RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW
  ) AS rolling_7day_avg
FROM daily_revenue;
```

Using `ROWS` instead of `RANGE` calculates averages over rows, not days, distorting results when data is missing.

Dataset: `sensor_readings` with timestamps and temperature from 50 sensors over 6 months, many missing timestamps.

**Level 1**: create an hourly date spine per sensor and compute average temperature per hour.

**Level 2**: compute 24-hour rolling average and flag as `alert` hours where temperature exceeds rolling average by 3 standard deviations.

**Level 3**: each sensor has a `timezone` column. Convert timestamps to local timezone before daily aggregation.

## Common mistake to avoid

The biggest risk is treating "date-time pitfalls and timezone correctness" as a label rather than a process: showing charts without decisions, metrics without baselines, or conclusions without assumptions. If you cannot say which choice you'd get wrong if data were unstable, the link between analysis and action is missing.
