# Ranking, lag/lead, cumulative logic and frames

Weekly revenue may rise while margins fall and some customers slow their purchases. A simple aggregate sum is not enough: you need to compare each row with its previous, next, and cumulative values. Ranking, lag/lead, cumulative logic and frames turn SQL into a language for reading sequences and trajectories.

## Real-world problem

In advanced SQL analytics, the challenge is writing correct, meaningful queries even as grain, time windows, cohorts and edge cases grow complex. This is not about memorizing functions but about improving concrete decisions with data, explicit assumptions, and checks.

## Conceptual model

| Step | What to clarify | Output |
|---|---|---|
| Question | Which real choice needs improvement? | Decision to make |
| Measurement | Which observable signal represents the problem? | Metric or source data |
| Control | Which baseline makes results interpretable? | Credible comparison |
| Action | What changes after analysis? | Next operational step |

This simple framework guides technical analysis toward practical goals.

## Rigorous formalization

To analyze with ranking, lag/lead, cumulative logic and frames, first define the unit of work (row, partition, window, cohort), then the main signal (accuracy, performance, duplicates, stability), the baseline for comparison, and the expected decision. Without this formalization, results risk being useless or misleading.

| Element | Required specification |
|---|---|
| Unit of analysis | row, partition, window, join, cohort or temporal metric |
| Main signal | accuracy, performance, duplicates, grain and stability |
| Baseline | previous period, comparable group, benchmark or counterfactual |
| Decision | query, intermediate model, SQL test or reusable pattern |
| Risk | Mistaking an available number for sufficient proof |

## LAG and LEAD: time as an explicit variable

LAG and LEAD let you compare each row with the previous or next within an ordered partition. This reveals temporal dynamics: elapsed time, first or last event, or state changes.

For example, Intercom accurately calculated "Time to First Response" only after using LAG to link each agent message to the preceding user message, avoiding errors from out-of-sequence replies.

## Cumulative logic: sums, counts and averages over windows

Cumulative functions compute running totals, moving averages and rolling windows. The difference between ROWS and RANGE framing is critical: ROWS counts physical rows, RANGE considers logical values (e.g., time intervals).

Robinhood found that using ROWS 29 PRECEDING for a rolling 30-day ARPU caused false spikes because it counted rows, not days with comparable volume. Switching to RANGE with a time interval made the metric stable and meaningful.

## Sequential patterns: sessionization and paths

Beyond LAG/LEAD and cumulative, window functions enable complex sequential patterns like sessionization, grouping events close in time into distinct sessions. The process has two steps: identify rows starting new sessions (gaps over a threshold), then assign session_id by cumulatively summing these flags.

Spotify uses this pattern to process billions of daily events, producing efficient, accurate session metrics.

## Example or case study

A team wants to understand the effect of a plan upgrade: comparing previous and next values, event ranking, and cumulative over time. LAG, LEAD and explicit frames turn isolated data into an analytic narrative.

| Observed evidence | Cautious interpretation | Recommended action |
|---|---|---|
| Number improves | Could be real effect or normal variation | Seek comparison and segmentation |
| One segment changes more | Aggregate mean hides differences | Separate cohorts or use cases |
| Cost rises with result | Read impact on margin | Estimate trade-offs and sustainability |

## Common mistake to avoid

The most frequent error is treating Ranking, lag/lead, cumulative logic and frames as a label rather than a process: charts without decisions, metrics without baselines, conclusions without assumptions. The key question is: if this result were unstable, which choice would I get wrong? Without a concrete answer, the link between analysis and action is missing.

## Practical lab: sequential analysis

Consider a user event dataset for an e-commerce app:

| user_id | event_time          | page          | action   |
|---------|---------------------|---------------|----------|
| 1       | 2024-02-01 09:00:00 | homepage      | view     |
| 1       | 2024-02-01 09:02:30 | product_page  | view     |
| 1       | 2024-02-01 09:05:00 | cart          | add      |
| 1       | 2024-02-01 09:15:00 | checkout      | start    |
| 1       | 2024-02-01 09:20:00 | checkout      | complete |
| 1       | 2024-02-01 14:30:00 | homepage      | view     |
| 2       | 2024-02-01 10:00:00 | homepage      | view     |
| 2       | 2024-02-01 10:01:00 | product_page  | view     |
| 2       | 2024-02-01 12:00:00 | homepage      | view     |

Goal: for each event calculate

1. Time since previous event
2. Whether the event starts a new session (gap > 30 minutes)
3. A unique session_id per session

The solution uses LAG to compute the gap, a CASE to flag new sessions, and a cumulative SUM to assign session_id.

## Quality control

Before applying these techniques, check completeness, duplicates, timezones, definitions and excluded segments. Many analyses fail because source data does not represent the expected behavior.

## Interpretation by segments

Aggregate averages are only a starting point. Segment by channel, cohort, plan, country or device. If segments move in opposite directions, the average can mislead and cause wrong decisions.
