# Window functions: a mental framework

A table of orders may contain multiple rows for the same customer, with nearly identical timestamps and delayed status updates. The question is not which row to see first, but which row truly represents the fact you want to defend. The mental framework for window functions starts here: partition, order, and frame become the way to define the scope of comparison before writing the function.

## Real-world problem

In advanced SQL analytics, writing correct queries becomes challenging when grain, windows, cohorts, and edge cases intertwine. Window functions are often used without clear awareness of what is being compared, in which order, and over which data slice. This leads to results that seem correct but are fragile and misleading. The real challenge is turning complexity into a clear, reproducible decision.

## Conceptual model

To tackle this problem, a simple but effective model is needed:

| Phase | What to clarify | Output |
|---|---|---|
| Question | Which real choice needs improvement? | Decision to make |
| Measure | Which observable signal represents the problem? | Metric or source data |
| Control | Which baseline makes the result interpretable? | Credible comparison |
| Action | What changes after the analysis? | Next operational step |

Every technical deep dive should strengthen at least one of these points, avoiding losing focus on the decision to support.

## Rigorous formalization

To make the mental framework of window functions analyzable, first define the unit of work: row, partition, window, join, cohort, or time metric. Link this unit to an observable metric such as correctness, performance, duplicates, grain, or result stability. Finally, declare the expected decision: query, intermediate model, SQL test, or reusable pattern.

| Element | Required specification |
|---|---|
| Unit of analysis | row, partition, window, join, cohort, or time metric |
| Main signal | correctness, performance, duplicates, grain, and stability |
| Baseline | previous period, comparable group, benchmark, or counterfactual scenario |
| Decision | query, intermediate model, SQL test, or reusable pattern |
| Risk | Mistaking an available number for sufficient proof |

This formalization allows another analyst to reproduce the logic, critique assumptions, and reach the same decision from the same data.

## Example or case study

Consider an orders table with multiple rows per customer. The question is: which row represents the fact to defend? Every window function has four components:

- PARTITION BY: segments data into independent groups
- ORDER BY: defines order within each group
- ROWS/RANGE BETWEEN ... AND ...: limits the frame of rows included

This mental framework prevents treating `ROW_NUMBER`, ranking, and cumulative functions as isolated formulas.

| Observed evidence | Prudent interpretation | Recommended action |
|---|---|---|
| The number improves | Could be real effect or normal variation | Seek comparison and segmentation |
| One segment changes more than others | Aggregate average hides difference | Separate cohorts or use cases |
| Cost grows with result | Impact must be read on margin | Estimate trade-offs and sustainability |

## Window functions: mental framework and ranking

Every window function has a precise structure:

```
FUNCTION_NAME(...) OVER (
  PARTITION BY column_1, column_2
  ORDER BY column_3 [ASC|DESC]
  ROWS/RANGE BETWEEN ... AND ...
)
```

PARTITION BY segments data into independent groups without collapsing rows. It is like placing a transparent acetate sheet over each group: the function "sees" only that group but all rows remain visible.

ORDER BY inside the window is independent from the query's ORDER BY. You can order by date inside the window but display results ordered by revenue.

The frame (ROWS/RANGE) limits which rows to include in the calculation. If unspecified, the default with ORDER BY is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, enabling cumulative sums.

### The four ranking functions

| Function | What it does | When to use | Behavior on ties |
|----------|--------------|-------------|-----------------|
| `ROW_NUMBER()` | Assigns a unique sequential number to each row | Deduplication, picking the nth row | No ties: order arbitrary but number unique |
| `RANK()` | Assigns the same number to ties, skips subsequent numbers | Ranking with gaps for ties | 1, 2, 2, 4 (skips 3) |
| `DENSE_RANK()` | Assigns the same number to ties, no skips | Ranking without gaps | 1, 2, 2, 3 |
| `NTILE(n)` | Divides partition into n buckets of nearly equal size | Percentiles, quartiles, deciles | Buckets may differ by 1 |

### Real case: LinkedIn recruiter ranking

LinkedIn wanted to show "Top 10 recruiters" by positive responses. They used `ROW_NUMBER()`, but three recruiters with the same score got ranks 10, 11, and 12. Only one made the top 10, others did not, due to arbitrary ordering. After complaints, they switched to `RANK()`, assigning all three rank 10, showing 12 recruiters in the top 10.

Lesson: use `ROW_NUMBER()` for deduplication, `RANK()` for rankings with gaps, `DENSE_RANK()` for rankings without gaps, and `NTILE()` for segmentation.

### Deduplication: the most common pattern

The most common pattern is selecting a single row per group by priority:

```sql
WITH ranked AS (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY customer_id
      ORDER BY created_at DESC
    ) AS rn
  FROM customer_events
)
SELECT * FROM ranked WHERE rn = 1;
```

This picks the most recent event per customer.

### Real case: Wise transaction deduplication

Wise needed to identify the latest identity document uploaded by each user for KYC checks. Previously, the query picked the first document alphabetically, causing false negatives. Deduplication with `ROW_NUMBER()` fixed the issue in one query.

### Level 1

Deduplicate by taking the most recent row per `txn_id` using `ROW_NUMBER()`.

### Level 2

Prioritize `status` as `completed` > `pending` > `failed`, and break ties by most recent `created_at`.

### Level 3

Use `RANK()` to keep all rows with the best status per `txn_id`.

## Quality control and segment interpretation

Before using window functions, always check completeness, duplicates, timezones, changed definitions, and excluded segments. Segment by channel, cohort, plan, country, device, and user maturity. Aggregate averages can hide significant differences among segments, leading to wrong decisions.
