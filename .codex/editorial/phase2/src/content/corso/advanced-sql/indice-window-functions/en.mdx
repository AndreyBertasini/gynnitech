# Execution order, logical plans, and query thinking

SQL queries are not just sequences of commands but chains of logical transformations executed in a precise order. Ignoring this execution order leads to subtle bugs, like filters applied too early or window functions computed on incorrect data.

## Real problem

Many analysts learn SQL in the syntactic order: `SELECT`, `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`. This is how queries are written, but not how they execute. The actual logical execution order, standardized since SQL-92, is:

1. FROM (including JOINs)
2. WHERE
3. GROUP BY
4. HAVING
5. WINDOW FUNCTIONS
6. SELECT
7. DISTINCT
8. ORDER BY
9. LIMIT/OFFSET

This means WHERE filters reduce the dataset before window functions run. A common mistake is thinking window functions "see" all rows and filters apply afterward, but this is false.

For example, Zalando's retention calculation was inflated by 34% due to misunderstanding this order, leading to costly wrong investments.

## Conceptual model

Reading a query as a logical plan involves three key questions:

1. What is the starting grain? (e.g., one row per transaction)
2. Which rows survive the WHERE filter?
3. How do subsequent steps (GROUP BY, window functions, HAVING, SELECT) transform the data?

This mindset treats SQL as a pipeline of set transformations, as Jim Gray emphasized.

## Formalization

Using relational algebra, a generic query follows:

- Join (⋈)
- Filter (σ)
- Aggregate (γ)
- Group filter (σ)
- Window function (ω)
- Projection (π)
- Sort (τ)

Window functions (ω) operate after filtering and aggregation but before projection and sorting.

## Case study

In 2022 Shopify faced a GMV reconciliation gap. The WHERE clause excluded orders canceled after payment recording, and the window function summed already aggregated data, inflating cumulative totals. Redefining the grain and recalculating windows on raw data reduced the gap to acceptable levels.

## Common mistake to avoid

Do not treat "execution order" as an empty label. It must be a concrete process linking analysis to decision: without specifying which choice changes, what data you observe, and which error you avoid, the lesson remains abstract.

## Operational summary

Execution order, logical plans, and query thinking help make clearer, more informed decisions with SQL. They are not just about writing correct queries but about understanding what you measure, how you measure it, and which errors to avoid. Use them as a framework to turn data and assumptions into concrete operational choices.
