# EXPLAIN, optimization, and performance tuning

Monday morning, the dashboard takes twelve minutes to load, the PM asks for an extra filter, and the warehouse costs rise without the query becoming more stable. Before rewriting everything, you need to understand what the database engine is really doing. This lesson starts from the query plan, not from intuition.

## Real-world problem

In complex analytical queries, the challenge is to write correct and performant SQL even when grain, windows, cohorts, and edge cases complicate the logic. Tuning is not an academic exercise but a process to improve real decisions with reliable data and concrete actions.

## Conceptual model

| Phase     | What to clarify                               | Output                  |
|-----------|----------------------------------------------|-------------------------|
| Question  | Which real choice needs improvement?         | Decision to make        |
| Measure   | Which observable signal represents the problem? | Metric or source data   |
| Control   | Which baseline makes the result interpretable? | Credible comparison    |
| Action    | What changes after the analysis?              | Next operational step   |

This simple model guides analysis: every technical intervention must strengthen at least one of these points.

## Rigorous formalization

To approach EXPLAIN and tuning, first define the unit of work (row, partition, window, join, cohort, or time metric), then the main signal (correctness, performance, duplicates, grain, stability), the baseline (previous period, comparable group, benchmark), the expected decision (query, model, test, reusable pattern), and the risk (confusing a number with sufficient proof).

| Element        | Required specification                                         |
|----------------|----------------------------------------------------------------|
| Unit of analysis | row, partition, window, join, cohort, or time metric           |
| Signal          | correctness, performance, duplicates, grain, stability         |
| Baseline        | previous period, comparable group, benchmark, or counterfactual |
| Decision        | query, intermediate model, SQL test, or reusable pattern        |
| Risk            | mistaking an available number for sufficient evidence           |

Formalization is solid when another analyst can reproduce the logic and reach the same decision.

## Reading EXPLAIN: anatomy of a query plan

EXPLAIN reveals what the database actually does with your query, showing scans, joins, aggregations, and filters. Common operations:

| Operation        | Meaning                          | Warning if...                                   |
|------------------|---------------------------------|------------------------------------------------|
| Seq Scan / Full Scan | Reads the entire table          | Only acceptable on small tables or when all rows are needed |
| Index Scan       | Uses an index to find rows       | Good if selective                              |
| Index Only Scan  | Index covers all requested columns | Excellent, no table access needed              |
| Hash Join        | Builds an in-memory hash table   | OK if inner table is small; warning if large  |
| Nested Loop      | For each row in A, searches B    | Warning if B is large and unindexed            |
| Sort             | Sorts data (GROUP BY, ORDER BY)  | Warning if sort spills to disk (insufficient memory) |

### Real case in PostgreSQL

```sql
EXPLAIN ANALYZE
SELECT c.name, COUNT(o.id)
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE c.country = 'IT'
  AND o.order_date >= '2024-01-01'
GROUP BY c.name;
```

Output shows two Seq Scans, a Hash Join, and an in-memory HashAggregate. The bottleneck is the full scan of `orders` (1.2M rows). Adding an index on `orders(customer_id, order_date)` turns the Seq Scan into an Index Only Scan, cutting runtime by 70%.

## Optimization strategies: hierarchy of interventions

1. Reduce data volume read by filtering early (WHERE on indexed or partitioned columns).
2. Reduce JOIN work using anti-join, semi-join, or pre-aggregation.
3. Use composite and partial indexes covering needed columns.
4. Configure memory for sort and hash join (work_mem, join_buffer_size).

## ClickHouse: a different performance model

ClickHouse is column-oriented, storing each column separately. This allows reading only the needed columns, speeding analytical queries on large datasets.

Specific optimizations:
- **Table ORDER BY:** primary index to skip irrelevant data blocks.
- **Compression codecs:** reduce storage and speed decompression.
- **Materialized columns:** computed at INSERT time for expensive expressions.
- **Projections:** mini-tables sorted differently for frequent queries.

### Real case: Cloudflare

Cloudflare reduced a country-level aggregation query from 45 to 0.8 seconds by adding a materialized column computing country from IP at INSERT time, avoiding repeated calculations during queries.

## Practical lab

Datasets: `orders` (5M rows), `customers` (500K rows).

- **Basic level:** run `EXPLAIN ANALYZE` on a join and aggregation query, identify bottlenecks.
- **Intermediate level:** add an index and measure improvement.
- **Advanced level:** rewrite the query using anti-join or pre-aggregation, compare execution plans.

## Common mistake to avoid

Treating EXPLAIN and tuning as mere labels rather than a process: showing charts without decisions, metrics without baselines, or conclusions without assumptions. If you cannot say which wrong choice you'd make if data were unstable, the link between analysis and action is missing.
