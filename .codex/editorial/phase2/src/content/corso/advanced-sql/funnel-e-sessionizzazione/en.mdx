# JSON, arrays, and semi-structured analytics

## Real-world problem

Advanced SQL analytics often deals with data that isn't neatly tabular. JSON, arrays, and nested objects are common. The real challenge is writing reliable queries when formats vary, fields are optional, and granularity is unclear. This is not just a technical task but a discipline of making informed choices about which data to trust, how to interpret it, and what risks to manage.

## Conceptual model

To handle semi-structured data effectively, use a simple but powerful model:

| Phase | What to clarify | Output |
|---|---|---|
| Question | What real decision needs improvement? | Decision to make |
| Measure | What observable signal represents the problem? | Metric or source data |
| Control | What baseline makes the result interpretable? | Credible comparison |
| Action | What changes after the analysis? | Next operational step |

This model guides turning raw data into actionable insight under uncertainty.

## Rigorous formalization

Make semi-structured data analyzable by first defining the unit of analysis: row, partition, time window, join, or cohort. Then pick the main signal to observe: correctness, performance, duplicates, granularity, or stability. Finally, set the baseline and expected decision.

| Element | Required specification |
|---|---|
| Unit of analysis | row, partition, window, join, cohort, or time metric |
| Main signal | correctness, performance, duplicates, granularity, stability |
| Baseline | prior period, comparable group, benchmark, or counterfactual scenario |
| Decision | query, intermediate model, SQL test, or reusable pattern |
| Risk | mistaking available numbers for sufficient proof |

This formalization enables reproducibility and critical evaluation.

## Example or case study

Take a Deliveroo order containing an array of `items`. Each order is one row, but product-level analysis requires exploding the array into separate rows. In PostgreSQL:

```sql
SELECT
  o.order_id,
  o.order_time,
  item->>'name' AS item_name,
  (item->>'quantity')::int AS quantity,
  (item->>'price')::numeric AS price
FROM orders o
CROSS JOIN LATERAL jsonb_array_elements(o.items) AS item;
```

This transformation revealed that 12% of the most ordered items accounted for 56% of restaurant revenue  -  an insight that would have required a complex ETL without unnesting.

## Common mistake to avoid

The most frequent error is treating JSON, arrays, and semi-structured analytics as a buzzword rather than a disciplined process. This happens when a chart is shown without a decision, a metric without a baseline, or a conclusion without stating critical assumptions. The key question is: if this result were unstable, what decision would I get wrong? Without a concrete answer, the link between analysis and action is missing.

## Operational summary

Semi-structured data dominates because it is flexible and widespread, but it demands discipline to turn it into reliable decisions. Extracting JSON fields, unnesting arrays, and navigating nested objects are essential techniques, but without a conceptual model and rigorous formalization, they risk generating noise instead of insight. Always apply the decision, data, control, action cycle to maintain clarity under uncertainty.
