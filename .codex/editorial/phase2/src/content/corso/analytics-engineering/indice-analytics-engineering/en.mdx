# What Analytics Engineering Really Is

Between data engineering and business analytics lies a crucial but often invisible role: turning raw data into reliable, documented, and reusable models. Analytics engineering is not just writing queries or building dashboards; it is about producing technically sound data products that support business decisions with confidence.

## What an Analytics Engineer Does

The analytics engineer bridges data engineers and data analysts. While data engineers build pipelines and infrastructure, and analysts answer business questions, the analytics engineer transforms raw data into clean, tested, and documented analytical datasets. They ensure terms like "revenue" mean the same across marketing, product, and finance.

Formalized by dbt Labs around 2018, the role rests on three pillars:

1. **Software-engineered transformation:** SQL and Jinja code follow engineering best practices - version control, code review, automated testing, CI/CD. It's not just a query but a software module producing data.

2. **Semantic modeling:** building a shared semantic layer with metric definitions, conformed dimensions, and centralized business logic, used company-wide.

3. **Applied governance:** documentation is generated from code (dbt docs), lineage is automatic, and tests block pull requests if data is corrupted.

The modern architecture, called the T-model, replaces siloed approaches:

                │ (Snowflake,     │
                │  BigQuery,      │
                │  Redshift)      │
                └────────┬────────┘
                         │ T: Transform (dbt)
                         ▼
           ┌─────────────────────────┐
           │    Analytics Models     │
           │  ┌───────────────────┐  │
           │  │   Staging Layer   │  │ ← 1:1 with source tables, minimal cleaning
           │  ├───────────────────┤  │
           │  │ Intermediate Layer│  │ ← JOINs, aggregations, business logic
           │  ├───────────────────┤  │
           │  │    Marts Layer    │  │ ← Analysis-ready datasets by team/domain
           │  └───────────────────┘  │
           └────────────┬────────────┘
                        │ SQL, BI tools
                        ▼
           ┌─────────────────────────┐
           │  Analysts, BI, ML       │
           └─────────────────────────┘

This model eliminates duplicated logic, like multiple analysts rewriting revenue calculations. The analytics engineer writes, tests, and maintains a single model used by all.

## Why Analytics Engineering Makes Economic Sense

A 2023 dbt Labs survey of 450 companies showed significant improvements:

| Metric | Before | After | Change |
|--------|--------|-------|--------|
| Time to answer a business question | 3.2 days | 4.1 hours | -87% |
| Duplicate metric definitions | 7.3 | 1.4 | -81% |
| Data errors found by stakeholders | 2.1/week | 0.3/week | -86% |
| Data analysts wanting to leave (burnout) | 34% annually | 12% annually | -65% |

Burnout from constantly fixing dirty data instead of analyzing is a major turnover cause. Analytics engineering shifts repetitive cleaning to automated processes, freeing analysts for high-value work.

## Real Case: Atlassian's Migration to dbt

In 2020, Atlassian moved from Airflow and scattered SQL scripts to dbt. Before:

- 400+ data models maintained by 3 people without tests
- Manual deployments causing downtime
- Inconsistent "Monthly Active Users" definitions across teams

After 6 months:

- 180 dbt models layered (staging, intermediate, marts)
- 1,200 automated tests
- CI/CD with GitHub Actions testing every pull request

Results after 12 months:

- Data incidents dropped from 11/month to 0.5/month
- New analyst onboarding reduced from 6 weeks to 2
- Model contributions from non-data teams increased by 140%

## Analytics Engineering Is a Mindset

You don't need a title to apply these practices. Three defining behaviors:

1. **Write code, not queries:** put SQL logic in versioned, commented, and tested files.
2. **Test before trusting:** every model has `not_null`, `unique`, and `accepted_values` tests on critical columns.
3. **Document from code:** documentation lives in the model's YAML file, always up to date.

## Quality Control

Before making decisions from data, check completeness, duplicates, timezones, definitions, and excluded segments. Many analyses fail because the data doesn't measure the expected behavior.

## Segment Interpretation

Aggregated averages are just a starting point. Segment by channel, cohort, plan, country, device, and user maturity. Opposing segment trends mean the average may mislead and cause wrong decisions.

## Real Problem

Analytics engineering solves turning raw data into tested, documented, reusable models for business. It's not abstract theory but a process to improve concrete decisions with data, explicit assumptions, and checks.

Goal: understand the analytical problem and decision context; apply examples, metrics, and checks to real cases. If you can't identify which decision changes, which data you observe, and which error to avoid, the skill is not yet mastered.

## Conceptual Model

| Phase | What to clarify | Output |
|-------|-----------------|--------|
| Question | Which real choice to improve? | Decision to make |
| Measure | Which observable signal represents the problem? | Metric or source data |
| Control | Which baseline makes the result interpretable? | Credible comparison |
| Action | What changes after analysis? | Next operational step |

The model is simple: decision, data, control, action. Every technical detail should strengthen at least one.

## Rigorous Formalization

To analyze analytics engineering, define the unit of work (source, model, test, mart, metric, exposure), link it to an observable metric (freshness, lineage, coverage, cost, trust), and declare the expected decision (dbt model, semantic layer, contract, test, pipeline).

| Element | Specification |
|---------|---------------|
| Unit of analysis | source, model, test, mart, metric, exposure |
| Main signal | freshness, lineage, test coverage, model cost, stakeholder trust |
| Baseline | previous period, comparable group, benchmark, counterfactual |
| Decision | dbt model, semantic layer, contract, test, release pipeline |
| Risk | mistaking an available number for sufficient proof |

Formalization is solid when another analyst can reproduce the logic, challenge assumptions, and reach the same decision.

## Example or Case Study

A company with data engineers and analysts but no shared quality in transformations. Analytics engineering emerges to create reusable, tested, documented, and stable models.

| Observed Evidence | Cautious Interpretation | Recommended Action |
|-------------------|-------------------------|--------------------|
| The number improves | Could be real effect or normal variation | Seek comparisons and segmentation |
| One segment changes more | The average hides differences | Separate cohorts or use cases |
| Cost grows with result | Impact should be read on margin | Estimate trade-offs and sustainability |

## Lab / Exercise

### Basic Level

Write a one-page brief for analytics engineering: decision supported, primary metric, baseline, main risk, and action if signal confirmed.

### Intermediate Level

Build a table with three segments or scenarios, indicating what changes, plausible alternative explanations, and controls before recommending action.

### Research-Grade Level

Prepare a decision memo: hypotheses, required data, exclusion criteria, quality checks, decision threshold, residual risk, and monitoring plan.

### Recommended Datasets and Materials

Use dbt, warehouse, CRM sources, events, marts, semantic layer, and lineage. If no real data, create a synthetic dataset with at least 200 rows, a time dimension, a segment dimension, and an outcome metric.

## Common Mistake to Avoid

Using analytics engineering as a label instead of a process. This happens when teams present a chart without a decision, a metric without a baseline, or a conclusion without stating assumptions that could invalidate it.

The control question is: if this result were unstable, what wrong choice would I make? Without a concrete answer, the link between analysis and action is missing.
