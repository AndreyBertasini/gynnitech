# Final project: a complete mini analytics stack

A final project in analytics engineering is not just a technical showcase but a disciplined practice of making reliable decisions from uncertain data. This mini analytics stack connects raw data, staging models, marts, tests, documentation, and concrete outputs for real stakeholders, aiming to reduce uncertainty and improve business choices.

## Real problem

In the StyleShop context, a fashion e-commerce with data from Shopify, Google Analytics 4, and Facebook Ads, the challenge is turning raw data into useful, tested information to support marketing and product decisions. Building models is not enough: every element must answer a business question, guard against risks, and guide concrete action.

## Conceptual model

To tackle this problem, the conceptual model unfolds in four phases:

| Phase     | What to clarify                                  | Expected output            |
|-----------|-------------------------------------------------|----------------------------|
| Question  | Which real choice needs improvement?            | Decision to make           |
| Measure   | Which observable signal represents the problem?| Metric or source data      |
| Control   | Which baseline makes the result interpretable? | Credible comparison       |
| Action    | What changes after the analysis?                 | Next operational step      |

This framework keeps focus on the discipline of decision-making under uncertainty, avoiding aimless analysis.

## Rigorous formalization

To make the project reproducible and open to critique, each unit of work (source, model, test, mart, metric, or exposure) is linked to observable signals like freshness, test coverage, cost, and stakeholder trust. The baseline can be a prior period or comparable group. The expected decision must be explicit, such as publishing a model or activating a test.

| Element        | Required specification                                         |
|----------------|----------------------------------------------------------------|
| Unit of analysis| source, model, test, mart, metric, or exposure                 |
| Main signal    | freshness, lineage, test coverage, model cost, stakeholder trust|
| Baseline       | prior period, comparable group, benchmark, or counterfactual   |
| Decision       | dbt model, semantic layer, contract, test, or release pipeline |
| Risk           | mistaking an available number for sufficient proof             |

This formalization helps avoid common errors like presenting data without context or ignoring risks.

## Example or case study

The StyleShop project starts from orders, customers, and events data, builds clean staging layers, intermediate models with business logic, marts ready for consumption, and uniqueness and freshness tests. Each model has a clear purpose, from data cleaning to the return on ad spend (ROAS) metric.

| Observed evidence                  | Cautious interpretation                           | Recommended action            |
|----------------------------------|--------------------------------------------------|------------------------------|
| The number improves               | Could be real effect or normal variation          | Seek comparison and segmentation|
| One segment changes more than others | The average hides significant differences        | Separate cohorts or use cases     |
| Cost grows with the result       | Impact must be read on margin                      | Estimate trade-offs and sustainability|

This approach shows how data is interpreted cautiously and contextualized.

## Lab / exercise

### Basic level

Write a one-page brief describing the decision to support, primary metric, baseline, main risk, and action if the signal confirms.

### Intermediate level

Build a table with three segments or scenarios, indicating for each what changes, plausible alternative explanations, and controls before recommending action.

### Research-grade level

Prepare a decision memo with hypotheses, required data, exclusion criteria, quality controls, decision threshold, residual risk, and post-decision monitoring plan.

### Recommended datasets and materials

Use dbt, warehouse, CRM data, events, marts, semantic layer, and lineage. If unavailable, create a synthetic dataset with at least 200 rows, a time dimension, a segment dimension, and an outcome metric.

## Common mistake to avoid

The most frequent error is treating the project as a label rather than a disciplined process. This happens when showing charts without decisions, metrics without baselines, or conclusions without critical assumptions. The key question is: if the result were unstable, what wrong choice would I make? Without a concrete answer, the link between analysis and action is missing.

## Quiz or checkpoint

1. Which concrete decision should this project improve?
2. Which unit of analysis makes the problem measurable?
3. Which baseline would you use to avoid naive interpretation?
4. Which common mistake could invalidate the conclusion?
5. What output would you deliver to a non-technical stakeholder?

## Operational summary

This project becomes useful only when it produces clearer decisions and does not add unnecessary complexity. The problem, model, formalization, example, lab, and checkpoint framework helps turn the lesson into verifiable practice. Mastery is reached when you can explain without jargon, apply it to a real case, and defend the recommendation with limits and controls.

## Practice deep dive

Treat this project as a small work test where a metric must become reliable for other teams. Understanding theory is not enough: you need a tested, documented data model with clear ownership. This step makes knowledge transferable by separating context, measure, action, and limit.

### Operational example

Start with a simple question: which choice would improve by applying this lesson? Link a real problem to an observable output. A valid example can be a table with baseline and segments, a verification query, an experiment design, or a concise memo. Quality depends on traceability of reasoning: readers must understand why you chose that metric, which alternative you discarded, and what evidence would change your mind.

### Work checkpoint

- Write the decision to improve using an action verb: allocate, stop, fix, launch, measure, prioritize, or investigate.
- Define the main signal and at least one guardrail to prevent locally good but globally bad choices.
- Add a baseline to interpret the signal.
- Explicitly state the most probable risk before the recommendation.
- Deliver an output that a reviewer can open and critique: dashboard, query, schema, memo, experiment, or checklist.

### Mastery summary

You have truly mastered the project when you can explain the concept without jargon, apply it to a realistic case, and defend the recommendation including limits and controls. If any of these are missing, revisit the conceptual model and reduce the ambition of the example: better a small rigorous test than a large unverifiable project.
