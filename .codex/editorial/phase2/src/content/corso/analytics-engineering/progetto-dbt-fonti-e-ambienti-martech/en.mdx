## Real-world problem

In analytics engineering, the core challenge is turning raw data into reliable, tested, and documented models that business teams can trust. Without a clear structure, every new metric risks becoming an isolated, hard-to-maintain query. The discipline of making decisions under uncertainty demands a rigorous approach to dbt project design that makes sources, transformations, and dependencies explicit.

## Conceptual model

To tackle this, the conceptual model breaks down into four phases:

| Phase    | What to clarify                               | Output                 |
|----------|----------------------------------------------|------------------------|
| Question | Which real decision needs improvement?       | Decision to make       |
| Measure  | What observable signal represents the problem? | Metric or source data  |
| Control  | What baseline makes the result interpretable? | Credible comparison    |
| Action   | What changes after the analysis?              | Next operational step  |

This simple framework keeps focus on concrete decisions, preventing analysis from becoming an end in itself.

## Rigorous formalization

To make this concrete, define the unit of work and signals to monitor:

| Element          | Required specification                                          |
|------------------|----------------------------------------------------------------|
| Unit of analysis | source, model, test, mart, metric, or exposure                  |
| Main signal      | freshness, lineage, test coverage, model cost, stakeholder trust |
| Baseline         | prior period, comparable group, benchmark, or counterfactual scenario |
| Decision         | dbt model, semantic layer, contract, test, or release pipeline |
| Risk             | Mistaking an available number for sufficient evidence          |

Formalization must ensure reproducibility and allow assumptions to be challenged.

## Example or case study

Imagine a dbt project integrating Stripe, HubSpot, and event tracking data. The initial structure includes:

- YAML source definitions for each system
- Staging models to clean and standardize data
- Consistent naming and separate folders for staging, intermediate, and marts
- Separate dev and prod environments

This setup avoids confusion and eases adding new metrics or segments.

| Observed evidence           | Careful interpretation                   | Recommended action                |
|----------------------------|-----------------------------------------|---------------------------------|
| The number improves         | Could be real effect or normal variation | Seek comparison and segment     |
| One segment changes more    | Aggregate average hides a difference    | Separate cohorts or use cases   |
| Cost rises with result      | Impact must be read on margin            | Estimate trade-offs and sustainability |

## Lab / exercise

### Basic level

Write a one-page brief for a dbt project: define the decision to support, primary metric, baseline, main risk, and action if the signal confirms.

### Intermediate level

Build a table with three segments or periods. For each, indicate what changes, a plausible alternative explanation, and which control you'd use before recommending action.

### Research-grade level

Prepare a detailed decision memo: hypotheses, required data, exclusion criteria, quality controls, decision thresholds, residual risk, and monitoring plan post-decision.

### Recommended datasets and materials

Use a dbt environment with CRM data, events, marts, and semantic layer. If unavailable, create a synthetic dataset with at least 200 rows, a time dimension, a segment dimension, and an outcome metric.

## Common mistake to avoid

The most frequent error is treating "dbt fundamentals and project structure" as an empty label - showing charts without decisions, metrics without baselines, or conclusions without stating which assumptions might invalidate them. The key question is: if the result were unstable, what wrong decision would I make? Without an answer, the link between analysis and action is missing.

A dbt project's structure is not just technical detail but a discipline for making decisions under uncertainty. Applying the problem framework, formalization, examples, exercises, and checkpoints helps turn knowledge into verifiable practice.

## dbt fundamentals and project structure

A well-structured dbt project forms the foundation for solid data-driven decisions. Typical structure includes:

```
my_dbt_project/
├── dbt_project.yml          ← main configuration
├── packages.yml             ← external dependencies
├── profiles.yml             ← warehouse connections
├── models/
│   ├── staging/             ← cleaned raw data
│   ├── intermediate/        ← business transformations
│   └── marts/               ← business consumption models
├── seeds/                   ← static CSV data
├── snapshots/               ← data versioning
├── tests/                   ← SQL tests
├── macros/                  ← reusable functions
├── analyses/                ← ad-hoc queries
└── docs/                    ← optional documentation
```

The `dbt_project.yml` file defines global configurations, including model materializations:

- **View**: lightweight, non-persistent models
- **Table**: materialized models, faster reads
- **Incremental**: partial updates for large tables
- **Ephemeral**: inline CTEs, never materialized

Jinja functions `source()` and `ref()` manage data sources and model dependencies, enabling automatic lineage, ordered execution, and freshness tests.

The workflow centers on four key commands:

- `dbt run`: runs models
- `dbt test`: runs tests
- `dbt docs generate`: generates documentation and lineage
- `dbt build`: combines run, test, seed, and snapshot

An advanced CI command is `dbt build --select state:modified+ --defer --state ./target/`, building only modified models and their descendants.

A real case shows how in eight weeks a data team adopted dbt to integrate operational and financial data, improving quality and timeliness of decisions.

Jinja makes dbt a programming language, allowing loops, conditions, and variables for parametric models and environment-specific logic.

## Quality control

Before trusting a dbt model, check completeness, duplicates, timezones, changed definitions, and excluded segments. Many errors stem from source data not representing the intended behavior.

## Practice deep dive

To consolidate skills, treat dbt structure as a small project where a metric must become reliable for other teams. Produce a tested, documented model with clear ownership, separating context, measure, action, and limits.

### Operational example

Start with a simple question: which decision would improve if you applied this lesson well? Build a three-line example: context, data/model used, and decision after risk checks. Quality is measured by reasoning traceability, not technical complexity.

### Work checkpoint

- Define the decision to improve with an action verb
- Identify main signal and at least one guardrail
- Add a baseline to interpret the signal
- State the most probable risk
- Deliver an output that a reviewer can open and critique

### Mastery summary

You have mastered the lesson when you can explain it without jargon, apply it to a realistic case, and defend a recommendation including limits and controls. If any element is missing, revisit the conceptual model and reduce the example's ambition.
