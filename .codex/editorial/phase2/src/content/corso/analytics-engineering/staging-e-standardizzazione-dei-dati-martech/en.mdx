# Tests, contracts, and trust in models

## Real-world problem

In analytics engineering, turning raw data into reliable models is a constant challenge. Often, a metric changes not because the business changed but due to a technical detail like a renamed field in a source. The lesson is clear: without tests, contracts, and trust in models, decisions risk being based on corrupted or incomplete data.

The goal is to turn data, assumptions, and checks into a process that supports concrete choices. If in the end you cannot say which decision changes, which data you observe, and which error you want to avoid, you have not yet applied the lesson.

## Conceptual model

Building technical trust requires a simple but effective model:

| Phase | What to clarify | Output |
|---|---|---|
| Question | Which real choice needs improvement? | Decision to make |
| Measure | Which observable signal represents the problem? | Metric or source data |
| Check | Which baseline makes the result interpretable? | Credible comparison |
| Action | What changes after the analysis? | Next operational step |

This framework guides every technical check toward real impact.

## Rigorous formalization

To make the process reproducible and open to critique, define:

- Unit of analysis: source, model, test, mart, metric, or exposure
- Main signal: freshness, lineage, test coverage, model cost, stakeholder trust
- Baseline: prior period, comparable group, benchmark, or counterfactual scenario
- Decision: dbt model, semantic layer, contract, test, or release pipeline
- Risk: mistaking an available number for sufficient proof

Formalization is solid when another analyst can reproduce the logic and reach the same decision.

## The dbt testing pyramid

dbt offers a layered testing strategy to protect the warehouse:

| Level | Test type | Coverage | Failure impact |
|---------|--------------|-----------|----------------|
| 1  -  Fundamental | `unique`, `not_null` on primary key | Every model | Blocks PR |
| 2  -  Business | `accepted_values`, `relationships` | Every critical column | Blocks PR |
| 3  -  Volume | Expected row count range | Key models | Warning |
| 4  -  Statistical quality | Mean, standard deviation, distribution | Core metrics | Alert |

Built-in tests cover most common cases and block serious errors. Singular tests allow specific SQL checks that must return zero rows to pass. Custom tests in Jinja are reusable and support a mature testing strategy.

## Data contracts: the next level

A data contract formalizes the agreement between data producer and consumer, defining schema, semantics, quality guarantees, and freshness SLA. dbt 1.5 introduces model contracts that verify types and constraints at build time, shifting validation from "hope data is correct" to "data is guaranteed correct or build fails."

## Real case: disaster without contracts

A European e-commerce saw a 31% revenue drop on dashboards because a payment provider updated a field type from string to number. Without contracts, the issue was found after days of manual investigation. After implementing model contracts, a similar issue was caught in minutes and fixed quickly.

## Progressive implementation strategy

No need to test everything at once. Recommended approach:

1. Week 1: `not_null` and `unique` on every model's primary key
2. Week 2: `accepted_values` on critical columns, `relationships` on foreign keys
3. Month 2: singular tests for critical business rules
4. Month 3: model contracts on staging models from external sources
5. Quarter 2+: reusable custom tests and statistical quality tests

CI/CD must run tests automatically and block PRs on failure; otherwise, tests are just documentation.

## Quality control

Before relying on tests and contracts, always check completeness, duplicates, timezones, changed definitions, and excluded segments. Many analyses fail because data measures something different than assumed.

## Segment interpretation

Aggregate averages can hide important differences. Segment by channel, cohort, plan, country, device, and user maturity. Opposite trends in segments mean the average can mislead and cause wrong decisions.

## Operational decision

Every analysis must end with a concrete choice: continue, stop, iterate, invest, remove, or deepen. If tests, contracts, and trust in models do not change a decision, the link between metric and action is missing.

## Example or case study

A marketing source stops sending `campaign_id` for some rows, but the attribution mart still produces plausible numbers. This shows why not-null, accepted values, and relationship tests must fail early, before dashboards show misleading data.

| Observed evidence | Cautious interpretation | Recommended action |
|---|---|---|
| Number improves | Could be real effect or normal variation | Seek comparison and segmentation |
| One segment changes more | Average hides differences | Separate cohorts or use cases |
| Cost grows with result | Impact must be read on margin | Estimate trade-offs and sustainability |

## Lab / exercise

### Basic level

Write a one-page summary with decision to support, primary metric, baseline, main risk, and action if signal confirmed.

### Intermediate level

Build a table with three segments, periods, or scenarios. For each, indicate what changes, plausible alternative explanation, and check before recommending action.

### Research-grade level

Prepare a decision memo: hypotheses, required data, exclusion criteria, quality checks, decision threshold, residual risk, and monitoring plan.

### Recommended datasets and materials

Use dbt, warehouse, CRM sources, events, marts, semantic layer, and lineage. If no real data, create a synthetic dataset with at least 200 rows, time dimension, segment dimension, and outcome metric.

## Common mistake to avoid

Treating tests, contracts, and trust in models as a label instead of a process. Happens when showing a chart without decision, a metric without baseline, or a conclusion without stating which assumption might invalidate it.

The control question is: if this result were unstable, which wrong choice would I make? If the answer is not concrete, the link between analysis and action is missing.

## Quiz or checkpoint

1. Which concrete decision should this lesson improve?
2. Which unit of analysis makes the problem measurable?
3. Which baseline would you use to avoid naive interpretation?
4. Which common mistake could change the conclusion?
5. What output would you deliver to a non-technical stakeholder?

## Operational summary

Tests, contracts, and trust in models become useful only when they lead to clearer decisions, not just terminology. The problem, model, formalization, example, lab, and checkpoint framework turns the lesson into verifiable practice.
