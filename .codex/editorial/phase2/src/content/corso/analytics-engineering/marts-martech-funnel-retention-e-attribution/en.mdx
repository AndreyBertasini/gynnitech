# Snapshots and Slowly Changing Dimensions

When a customer changes segment, subscription plan, CRM status, or account owner over time, looking only at the current state loses the history that explained past decisions. Snapshots and slowly changing dimensions (SCDs) are not mere modeling details - they determine whether you can reconstruct the correct context of a metric over time.

## Real-world problem

In analytics engineering, the challenge is turning raw data into tested, documented, and reusable business models. Without handling slow changes properly, decisions risk being based on data that do not reflect the historical context. If you cannot specify which decision changes, what data you observe, and which error to avoid, the lesson has not yet become applied skill.

## Conceptual model

| Phase    | What to clarify                              | Output                  |
|----------|---------------------------------------------|-------------------------|
| Question | Which real choice needs improvement?        | Decision to make        |
| Measure  | Which observable signal represents the problem? | Metric or source data   |
| Control  | Which baseline makes the result interpretable? | Credible comparison    |
| Action   | What changes after analysis?                  | Next operational step   |

This simple model keeps focus on decision and practical value.

## Rigorous formalization

To analyze slow changes, define:

| Element        | Required specification                                  |
|----------------|---------------------------------------------------------|
| Unit of analysis | source, model, test, mart, metric, or exposure          |
| Main signal    | freshness, lineage, test coverage, model cost, stakeholder trust |
| Baseline       | prior period, comparable group, benchmark, or counterfactual scenario |
| Decision       | dbt model, semantic layer, contract, test, or release pipeline |
| Risk           | Mistaking an available number for sufficient proof      |

Formalization is solid when another analyst can reproduce logic and reach the same decision.

## What are Slowly Changing Dimensions

An SCD is a dimension whose attributes change over time, and you need to know the value at each historical moment. Current state is not enough - you must answer questions like "what was customer X's subscription plan on March 15, 2023?"

Common types:

| Type    | Strategy                          | Use case                        | Example                        |
|---------|---------------------------------|--------------------------------|-------------------------------|
| Type 1  | Overwrite                       | When old value is no longer needed | Fixing a typo in a name       |
| Type 2  | New row with validity dates     | When full history is needed    | Subscription plan changes     |
| Type 3  | Previous and current value columns | When only immediate prior change matters | Previous vs current legal address |

Type 2 is most common and powerful, adding validity date columns:

| customer_id | plan       | valid_from | valid_to   | is_current |
|-------------|------------|------------|------------|------------|
| C001        | free       | 2023-01-10 | 2023-06-15 | false      |
| C001        | pro        | 2023-06-15 | 2023-12-01 | false      |
| C001        | enterprise | 2023-12-01 | NULL       | true       |

This lets you filter by time period, e.g.: 

> WHERE '2023-08-01' BETWEEN valid_from AND COALESCE(valid_to, '2099-12-31')

## dbt snapshots: automating Type 2

dbt provides a snapshot module automating versioning. You define the strategy and dbt applies it each run.

Example snapshot:

- Unique key: `customer_id`
- Strategy: `timestamp` using `updated_at` column

Each `dbt snapshot` run:

1. Reads source table
2. Compares each row to saved snapshot
3. Inserts new row if `customer_id` is new with `valid_from = now`, `valid_to = NULL`
4. If `updated_at` changed, closes previous row and inserts new one
5. Otherwise, ignores

Alternative strategies:

- `strategy: timestamp`: relies on last modified timestamp
- `strategy: check`: compares specified columns and triggers snapshot if any change

## Real case: how Monzo manages history

Monzo, UK digital bank with 8 million customers, uses dbt snapshots to track every change in account status, pricing plan, and personal data with exact dates. Without snapshots, their logic would require thousands of lines of code and months of work; with dbt, just a few dozen lines and weeks.

An insight: customers upgrading from `standard` to `plus` within 30 days have 43% higher LTV than those waiting 90 days, prompting onboarding redesign.

## Common snapshot mistakes

- Non-immutable `unique_key`: always use system-generated IDs, not mutable fields like email
- Unreliable `updated_at`: prefer `strategy: check` with specific columns
- Querying snapshots without temporal filters: always use validity ranges for historical analysis
- Snapshot frequency too low: if data changes multiple times daily, daily snapshots lose info

### Basic level

Write a one-page summary: decision supported, primary metric, baseline, main risk, and action if signal confirmed.

### Intermediate level

Build a table with three segments or periods, indicating what changes, plausible alternative explanations, and controls before acting.

### Research-grade level

Prepare a decision memo with hypotheses, required data, exclusion criteria, quality checks, decision threshold, residual risk, and monitoring plan.

### Recommended datasets and materials

Use dbt, warehouse, CRM sources, events, marts, semantic layer, and lineage. If no real data, create a synthetic dataset with at least 200 rows, a time dimension, segment dimension, and outcome metric.

## Typical mistake to avoid

Using snapshots and slow change management as a label without process. Happens when there's no decision, baseline, or link between analysis and action.

Key question: if this result was unstable, what wrong choice would I make? If you cannot answer, the connection between analysis and decision is missing.
