# Git workflow, code review, and technical collaboration

When multiple people modify models that feed critical dashboards, the Git workflow becomes integral to data quality. Git workflow, code review, and technical collaboration embed pull requests, reviews, naming conventions, and ownership into the daily work of an analytics engineer.

## Real-world problem

In analytics engineering, the challenge is turning raw data into tested, documented, and reusable models for the business. It is not just about writing SQL code but ensuring every change is traceable, verifiable, and leads to more reliable decisions. If you cannot specify which decision changes, which data you observe, and which error you want to avoid, the process has not yet become applied expertise.

## Conceptual model

| Phase | What to clarify | Output |
|---|---|---|
| Question | Which real choice should improve? | Decision to make |
| Measure | Which observable signal represents the problem? | Metric or source data |
| Control | Which baseline makes the result interpretable? | Credible comparison |
| Action | What changes after the analysis? | Next operational step |

This simple model helps keep the focus: every technical activity should strengthen at least one of these points.

## Rigorous formalization

To analyze Git workflow, code review, and technical collaboration, first define the unit of work: source, model, test, mart, metric, or exposure. Link this unit to an observable metric such as freshness, lineage, test coverage, model cost, or stakeholder trust. Then declare the expected decision: dbt model, semantic layer, contract, test, or release pipeline.

| Element | Required specification |
|---|---|
| Unit of analysis | source, model, test, mart, metric, or exposure |
| Main signal | freshness, lineage, test coverage, model cost, stakeholder trust |
| Baseline | previous period, comparable group, benchmark, or counterfactual scenario |
| Decision | dbt model, semantic layer, contract, test, or release pipeline |
| Risk | mistaking an available number for sufficient proof |

Formalization is solid when another analyst can reproduce the logic, critique assumptions, and reach the same decision from the same data.

## Example or case study

A pull request changes the definition of `is_active_customer` impacting three marts and two executive dashboards. This case shows why code review must consider lineage, ownership, tests, and communication of changes - not just whether the model compiles.

| Observed evidence | Careful interpretation | Recommended action |
|---|---|---|
| Number improves | Could be real effect or normal variation | Seek comparison and segmentation |
| One segment changes more than others | Aggregated average hides differences | Separate cohorts or use cases |
| Cost rises with result | Impact must be read on margin | Estimate trade-offs and sustainability |

## Git workflow for dbt projects

dbt is code. The branching model that works for software also works for data. The recommended pattern is trunk-based development with feature branches:

main ──────────────────────────────────────────────► (production)
  │
  ├── feature/new-mrr-model ──► PR ──► review ──► merge
  │
  ├── fix/campaign-cost-bug ──► PR ──► review ──► merge
  │
  └── staging ──► (automatic deploy to test env)

Key rules:

1. Never commit directly to main; every change must go through branch and pull request.
2. Each PR runs `dbt build` on a separate schema created by CI/CD to isolate changes.
3. PR can be merged only if the build passes and at least one reviewer approves.
4. Merging to main triggers deployment to production or staging.

## Code review for data models: what to check

Code review for dbt models prioritizes differently than application code:

1. Are tests present and sufficient? At least `not_null` on the primary key.
2. Is business logic in the correct layer? Avoid complex business rules in staging models.
3. Is naming clear and consistent with conventions?
4. Is there YAML documentation with descriptions and tests on critical columns?
5. Is the query performant and scalable for production volumes?

Reviewer checklist:

- Tests: not_null and unique on primary key
- Layer: business logic in the correct layer
- Naming: file, model, and columns follow conventions
- Docs: YAML with descriptions
- Performance: scalable queries
- Dependencies: acyclic DAG

## Managing conflicts on dbt models

Conflicts are riskier because Git does not understand SQL. To minimize them:

1. Keep models small and single-responsibility to reduce conflict surface.
2. Use schema separation per developer, with profiles using dedicated schemas to isolate work environments.

Example schema config for developer:

my_project:
  target: dev
  outputs:
    dev:
      schema: "dbt_{{ env_var('USER', 'default') }}"

## Quality control

Before applying git workflow and code review, verify completeness, duplicates, timezones, changed definitions, and excluded segments. Many analyses fail because the starting data does not represent the expected behavior.

## Interpretation by segments

Aggregate averages are only a starting point. Segment by channel, cohort, plan, country, device, and user maturity. Opposing segment trends can make averages misleading and lead to wrong decisions.

## Operational decision

Every analysis must end with a concrete choice: continue, stop, iterate, invest, remove, or deepen. If git workflow and code review do not change a decision, the link between metric and action is missing.

## Common mistake to avoid

Using Git workflow and code review as mere labels rather than processes. This happens when teams show a chart without a decision, a metric without a baseline, or a conclusion without stating which assumptions could invalidate it. The key question is: if this result were unstable, which choice would I get wrong? If the answer is not concrete, the link between analysis and action is missing.
