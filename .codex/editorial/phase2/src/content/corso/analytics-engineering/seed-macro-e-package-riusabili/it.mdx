# Git workflow, code review e collaborazione tecnica

Quando più persone lavorano su modelli che alimentano dashboard critici, il workflow Git diventa parte integrante della qualità del dato. Git workflow, code review e collaborazione tecnica impongono pull request, revisioni, naming e ownership nel lavoro quotidiano dell'analytics engineer.

## Problema reale

Nel campo dell'analytics engineering, il problema da risolvere è trasformare dati grezzi in modelli testati, documentati e riusabili dal business. Non si tratta solo di scrivere codice SQL, ma di garantire che ogni modifica sia tracciabile, verificabile e che porti a decisioni più affidabili. Se non riesci a indicare quale decisione cambia, quale dato osservi e quale errore vuoi evitare, il processo non è ancora diventato competenza applicata.

## Modello concettuale

| Fase | Cosa chiarire | Output |
|---|---|---|
| Domanda | Quale scelta reale deve migliorare? | Decisione da prendere |
| Misura | Quale segnale osservabile rappresenta il problema? | Metrica o dato sorgente |
| Controllo | Quale baseline rende il risultato interpretabile? | Confronto credibile |
| Azione | Che cosa cambia dopo l'analisi? | Prossimo passo operativo |

Questo modello semplice aiuta a mantenere il focus sull'obiettivo: ogni attività tecnica deve rafforzare almeno uno di questi punti.

## Formalizzazione rigorosa

Per rendere Git workflow, code review e collaborazione tecnica analizzabile, definisci prima l'unità di lavoro: source, model, test, mart, metrica o esposizione. Collega questa unità a una metrica osservabile come freshness, lineage, test coverage, costo modello o fiducia stakeholder. Poi dichiara la decisione attesa: modello dbt, semantic layer, contratto, test o pipeline di release.

| Elemento | Specifica richiesta |
|---|---|
| Unità di analisi | source, model, test, mart, metrica o esposizione |
| Segnale principale | freshness, lineage, test coverage, costo modello e fiducia stakeholder |
| Baseline | Periodo precedente, gruppo comparabile, benchmark o scenario controfattuale |
| Decisione | modello dbt, semantic layer, contratto, test o pipeline di release |
| Rischio | Scambiare un numero disponibile per una prova sufficiente |

La formalizzazione è solida quando un altro analista può riprodurre la logica, criticare le assunzioni e ottenere la stessa decisione partendo dagli stessi dati.

## Esempio o caso studio

Una pull request modifica la definizione di `is_active_customer` e impatta tre mart e due dashboard executive. Questo caso mostra perché la code review deve guardare lineage, ownership, test e comunicazione del cambiamento, non solo se il modello compila.

| Evidenza osservata | Lettura prudente | Azione consigliata |
|---|---|---|
| Il numero migliora | Potrebbe essere effetto reale o variazione normale | Cercare confronto e segmentazione |
| Un segmento cambia più degli altri | La media aggregata nasconde una differenza | Separare coorti o casi d'uso |
| Il costo cresce insieme al risultato | L'impatto va letto sul margine | Stimare trade-off e sostenibilità |

## Git workflow per progetti dbt

dbt è codice. Il branching model che funziona per il software funziona anche per i dati. Il pattern consigliato è trunk-based con feature branch:

main ──────────────────────────────────────────────► (produzione)
  │
  ├── feature/new-mrr-model ──► PR ──► review ──► merge
  │
  ├── fix/campaign-cost-bug ──► PR ──► review ──► merge
  │
  └── staging ──► (deploy automatico su env di test)

Regole essenziali:

1. Mai commitare direttamente su main: ogni modifica deve passare da branch e pull request.
2. Ogni PR esegue `dbt build` su uno schema separato creato dal CI/CD per isolare i cambiamenti.
3. La PR può essere mergiata solo se il build è verde e almeno un reviewer ha approvato.
4. Il merge su main triggera il deploy in produzione o staging.

## Code review per modelli dati: cosa guardare

La code review di un modello dbt ha priorità diverse rispetto al codice applicativo:

1. I test sono presenti e sufficienti? Almeno `not_null` sulla primary key.
2. La logica di business è nel layer corretto? Evitare regole di business complesse in modelli staging.
3. Il naming è chiaro e coerente con le convenzioni.
4. C'è documentazione YAML con descrizioni e test su colonne critiche.
5. La query è performante e scalabile sui volumi di produzione.

Checklist per reviewer:

- Test: not_null e unique sulla primary key
- Layer: logica di business nel layer corretto
- Naming: file, modello e colonne seguono convenzioni
- Docs: YAML con descrizioni
- Performance: query scalabile
- Dependencies: DAG aciclico

## Gestione dei conflitti su modelli dbt

I conflitti sono più rischiosi perché Git non interpreta SQL. Per minimizzarli:

1. Modelli piccoli e con responsabilità singola per ridurre la superficie di conflitto.
2. Schema separation per sviluppatore, con profili che usano schemi dedicati per isolare gli ambienti di lavoro.

Esempio di configurazione schema per sviluppatore:

my_project:
  target: dev
  outputs:
    dev:
      schema: "dbt_{{ env_var('USER', 'default') }}"

## Controllo di qualità

Prima di applicare git workflow e code review, verifica completezza, duplicati, timezone, definizioni cambiate e segmenti esclusi. Molte analisi falliscono perché il dato di partenza non rappresenta il comportamento atteso.

## Interpretazione per segmenti

La media aggregata è solo un punto di partenza. Segmenta per canale, coorte, piano, paese, device e maturità utente. Se segmenti si muovono in direzioni opposte, la media può ingannare e portare a decisioni sbagliate.

## Decisione operativa

Ogni analisi deve concludersi con una scelta concreta: continuare, fermare, iterare, investire, rimuovere o approfondire. Se git workflow e code review non cambiano una decisione, manca il collegamento tra metrica e azione.

## Lab / esercizio

### Livello base

Scrivi una scheda sintetica per Git workflow, code review e collaborazione tecnica: decisione da supportare, metrica principale, baseline, rischio e azione prevista.

### Livello intermedio

Costruisci una tabella con tre segmenti o scenari. Per ciascuno indica cosa cambia, quale spiegazione alternativa e quale controllo useresti prima di agire.

### Livello research-grade

Prepara un decision memo con ipotesi, dati richiesti, criteri di esclusione, controlli di qualità, soglia decisionale, rischio residuo e piano di monitoraggio.

### Dataset e materiali consigliati

Usa dbt, warehouse, sorgenti CRM, eventi, marts, semantic layer e lineage. Se non hai dati reali, crea un dataset sintetico con almeno 200 righe, dimensione temporale, segmenti e metrica di outcome.

## Errore tipico da evitare

Usare Git workflow e code review come etichetta anziché processo. Succede quando si mostra un grafico senza decisione, una metrica senza baseline o una conclusione senza indicare quali assunzioni potrebbero invalidarla. La domanda chiave è: se questo risultato fosse instabile, quale scelta sbaglierei? Se la risposta non è concreta, manca il collegamento tra analisi e azione.

## Quiz o checkpoint

1. Quale decisione concreta dovrebbe migliorare questa lezione?
2. Quale unità di analisi rende il problema misurabile?
3. Quale baseline useresti per evitare una lettura ingenua?
4. Quale errore tipico potrebbe cambiare la conclusione?
5. Quale output consegneresti a uno stakeholder non tecnico?

## Riepilogo operativo

Git workflow, code review e collaborazione tecnica diventano utili solo se producono decisioni più chiare e affidabili, non come semplice terminologia. Usa il framework problema, modello, formalizzazione, esempio, lab e checkpoint per trasformare la lezione in pratica verificabile.
