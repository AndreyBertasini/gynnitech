# Reverse ETL and the activation layer

Data warehouses hold reliable segments, but marketing and sales teams only benefit if the data reaches the right operational tools, at the right time, and with valid consent. Reverse ETL and the activation layer shift analytics engineering from producing tables to delivering controlled, actionable audiences and attributes.

## Real-world problem

In analytics engineering, the challenge is turning raw data into tested, documented, and reusable business models. Reverse ETL moves data from the warehouse to operational tools, but without a rigorous process, it risks confusion and poor decisions. The key is ensuring what leaves the warehouse can trigger campaigns, notifications, and workflows in a tested, versioned, and reversible manner.

## Conceptual model

The conceptual model involves four steps:

| Step     | What to clarify                       | Output                  |
|----------|-------------------------------------|-------------------------|
| Question | Which real decision needs improving? | Decision to make        |
| Measure  | What observable signal represents the problem? | Metric or source data   |
| Control  | What baseline makes the result interpretable? | Credible comparison     |
| Action   | What changes after the analysis?    | Next operational step   |

Every technical detail should strengthen at least one of these points.

## Rigorous formalization

To analyze Reverse ETL and the activation layer, first define the unit of work: source, model, test, mart, metric, or exposure. Link this unit to an observable signal such as freshness, lineage, test coverage, model cost, and stakeholder trust. Finally, state the expected decision: dbt model, semantic layer, contract, test, or release pipeline.

| Element          | Required specification                                        |
|------------------|---------------------------------------------------------------|
| Unit of analysis | source, model, test, mart, metric, or exposure                 |
| Main signal      | freshness, lineage, test coverage, model cost, stakeholder trust |
| Baseline         | Previous period, comparable group, benchmark, or counterfactual scenario |
| Decision         | dbt model, semantic layer, contract, test, or release pipeline |
| Risk             | Mistaking an available number for sufficient proof             |

Formalization is solid when another analyst can reproduce the logic, critique assumptions, and reach the same decision from the same data.

## Common mistake to avoid

The most frequent error is treating Reverse ETL and activation layer as a buzzword rather than a process. This happens when teams present a chart without a decision, a metric without a baseline, or a conclusion without stating which assumption could invalidate it. The control question is: if this result were unstable, what wrong choice would I make? Without a concrete answer, the link between analysis and action is missing.

## What is Reverse ETL

Reverse ETL extracts data from the warehouse and loads it into operational tools (CRM, email marketing, advertising, product analytics). It reverses the traditional flow, turning the warehouse from an analytic archive into the operational hub.

Concrete examples:

- Salesforce: sync "customer health score" calculated in dbt for each account
- Braze / Customer.io: send user segments based on recent behavior for targeted email campaigns
- Facebook Ads: create lookalike audiences based on real data
- Zendesk: enrich support tickets with LTV and subscription plan
- Google Sheets: export updated metric tables for ad-hoc reporting

## Integration dbt → Reverse ETL

Standard workflow:

1. dbt builds "activation-ready" models in marts designed for operational tools
2. Hightouch / Census read these models and sync them to destinations
3. Operational tools use the data to personalize experiences and target campaigns

Example dbt pattern for activation models:

```sql
-- models/marts/activation/mrt_activation__churn_risk_users.sql
{{
    config(
        materialized='table',
        schema='activation'
    )
}}

WITH churn_risk AS (
    SELECT
        customer_id,
        email,
        c.salesforce_account_id,
        c.braze_external_id,
        m.total_revenue_12m,
        m.days_since_last_order,
        m.churn_probability,
        m.customer_tier,
        CASE
            WHEN m.churn_probability > 0.7 AND m.customer_tier = 'enterprise'
                THEN 'high_risk_vip'
            WHEN m.churn_probability > 0.5
                THEN 'medium_risk'
            ELSE 'low_risk'
        END AS churn_segment
    FROM {{ ref('int_customer_health') }} m
    JOIN {{ ref('stg_salesforce__accounts') }} c
        ON m.customer_id = c.internal_customer_id
    WHERE m.days_since_last_order > 30
)

SELECT * FROM churn_risk
WHERE churn_segment IN ('high_risk_vip', 'medium_risk')
```

This model produces a clean table with IDs for each tool, enriched metrics, and activation-ready segments. Hightouch or Census sync these into operational tools.

## Real case: how Notion uses Reverse ETL

Notion uses Reverse ETL with Hightouch + dbt to:

1. Calculate product adoption metrics
2. Sync metrics to Salesforce
3. Enable sales reps to see up-to-date data before calls

Insight: accounts with "notion_health_score" > 80 had a 97% renewal rate, under 40 only 23%. This enabled an "early warning list" reducing churn by 12%.

## Data model for the activation layer

| Feature           | Analytics model               | Activation model                      |
|-------------------|------------------------------|-------------------------------------|
| Granularity       | Aggregated (day, country...) | Per operational entity (customer, account, user) |
| Freshness         | T+1 day acceptable           | Ideally T+1 hour                    |
| Columns           | Metrics, dimensions          | Operational IDs + metrics + segments |
| Volume            | Millions of rows             | Tens/hundreds of thousands (only active entities) |
| Consumer          | Analyst, BI tools            | CRM, marketing automation, sales    |

Activation model checklist:

- Contains native IDs for each destination tool
- Metrics calculated with the same logic as analytics models
- Has a `synced_at` column to track freshness
- Filtered to include only active entities
- Enums and segments compatible with destination tools

## Quality control

Before using Reverse ETL and activation layer for decisions, always check completeness, duplicates, timezones, changed definitions, and excluded segments. Many analyses fail because the starting data measures a different behavior than the team believes.

## Segment interpretation

The aggregated average is only a starting point. Segment by channel, cohort, plan, country, device, and user maturity. If two segments move in opposite directions, the average may mislead and cause wrong decisions.

## Operational decision

Every analysis must end with a concrete choice: continue, stop, iterate, invest, remove, or deepen. If Reverse ETL and activation layer don't change a decision, the link between metric and action is still missing.
