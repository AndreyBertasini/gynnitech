# Semantic layer and metric definitions

When terms like "active user," "revenue," or "conversion" are calculated differently across dashboards, the issue is not just technical but governance of decisions. The **semantic layer** and **metric definitions** centralize definitions, granularity, and filters so teams focus on business discussions, not formulas.

## Real-world problem

In analytics engineering, the semantic layer transforms raw data into tested, documented, and reusable business models. This is not isolated theory but a tool to improve concrete choices with explicit assumptions and minimal checks. If you cannot say which decision changes, which data you observe, and which error you want to avoid, the lesson has not become applied skill.

## Conceptual model

| Phase     | What to clarify                         | Output                  |
|-----------|---------------------------------------|-------------------------|
| Question  | Which real choice should improve?     | Decision to make        |
| Measure   | Which observable signal represents the problem? | Metric or source data   |
| Check     | Which baseline makes the result interpretable? | Credible comparison    |
| Action    | What changes after analysis?           | Next operational step   |

This simple model (decision, data, check, action) guides every technical deep dive.

## Rigorous formalization

To analyze semantic layers and metric definitions, first define the unit of work: source, model, test, mart, metric, or exposure. Link it to an observable signal: freshness, lineage, test coverage, model cost, stakeholder trust. Then declare the expected decision: dbt model, semantic layer, contract, test, or release pipeline.

| Element          | Required specification                                  |
|------------------|---------------------------------------------------------|
| Unit of analysis | source, model, test, mart, metric, or exposure          |
| Main signal      | freshness, lineage, test coverage, model cost, stakeholder trust |
| Baseline         | Previous period, comparable group, benchmark, or counterfactual scenario |
| Decision         | dbt model, semantic layer, contract, test, or release pipeline |
| Risk             | Mistaking an available number for sufficient proof      |

Formalization is solid when another analyst can reproduce the logic, critique assumptions, and reach the same decision.

## What is a semantic layer

The semantic layer is an interface between raw or modeled data and consumption tools like BI, AI, or spreadsheets. It defines metrics (what you measure), dimensions (how you group), and join paths (how tables connect). It is not a new table but a shared semantic contract.

Example of a semantic metric definition:

- Metric: "monthly_recurring_revenue"
- Formula: SUM(subscription_amount)
- Where: marts.finance.subscriptions WHERE status = 'active'
- Linkable dimensions: customer_country, plan_type, acquisition_channel
- Time granularities: day, week, month, quarter, year
- Owner: Finance Team
- Update SLA: T+1 hour

Before the semantic layer, each analyst rewrote this differently. Now everyone references `monthly_recurring_revenue` with a single meaning.

## dbt Semantic Layer and MetricFlow

dbt introduced a native semantic layer in 2023 based on MetricFlow, composed of:

1. Semantic Models (YAML)  -  define entities, dimensions, and base measures
2. Metrics (YAML)  -  define metrics derived from measures
3. MetricFlow Server  -  translates requests into optimized SQL

Semantic model example:

semantic_models:
- name: subscriptions
  model: ref('mrt_finance__subscriptions')
  entities:
    - name: subscription
      type: primary
      expr: subscription_id
    - name: customer
      type: foreign
      expr: customer_id
  dimensions:
    - name: plan_type
      type: categorical
      expr: plan
    - name: customer_country
      type: categorical
      expr: country_code
    - name: subscription_started
      type: time
      type_params:
        time_granularity: month
      expr: started_at
  measures:
    - name: monthly_amount
      description: "Monthly subscription amount in EUR"
      agg: sum
      expr: amount_eur
    - name: active_subscriptions
      description: "Count of active subscriptions"
      agg: count
      expr: 1

Derived metrics example:

metrics:
- name: mrr
  description: "Monthly Recurring Revenue"
  label: "MRR"
  type: simple
  type_params:
    measure: monthly_amount
  filter: |
    {{ Dimension('subscription_status') }} = 'active'

- name: arr
  description: "Annualized Run Rate"
  label: "ARR"
  type: derived
  type_params:
    expr: mrr * 12
    metrics:
      - name: mrr

- name: mrr_growth_rate
  description: "MRR growth rate vs same month last year"
  type: ratio
  type_params:
    numerator: mrr - mrr_1y_ago
    denominator: mrr_1y_ago

With these definitions, an analyst can request "MRR by plan_type, last 12 months" without writing SQL. MetricFlow generates the correct query.

## Why metric definitions matter for business

Centralizing metrics prevents three harms:

- Reputational damage: divergent numbers erode trust. After such incidents, rebuilding trust takes on average 4 months (dbt Labs 2023).
- Financial damage: bad decisions cost money. The Microsoft Bing 2012 case is emblematic but smaller-scale errors happen daily.
- Organizational damage: analysts spend 29% of their time reconciling definitions across teams, reducing analysis time.

## Real case: Adevinta's semantic layer

Adevinta, a Norwegian group owning marketplaces like Leboncoin, Subito, and InfoJobs, built a unified semantic layer on dbt for all platforms. The challenge was unifying common metrics despite different data structures.

Standard semantic models for:
- classifieds_listings
- user_profiles
- transactions

Each marketplace maps its data to standard models; metrics are defined once. Thus, "revenue by country, last quarter" is comparable between Subito and Leboncoin despite different payment systems.

Outcome: cross-marketplace report build time dropped from 3 days to 3 hours, and reconciliation errors vanished.

## Quality control

Before using the semantic layer in decisions, check completeness, duplicates, time zones, changed definitions, and excluded segments. Many analyses fail because the data measures a different behavior than expected.

## Segment interpretation

Aggregated averages are only a starting point. Segment by channel, cohort, plan, country, device, and user maturity. If segments move in opposite directions, the average can mislead and cause wrong decisions.

## Operational decision

Every analysis must end with a concrete choice: continue, stop, iterate, invest, remove, or deepen. If semantic layer and metric definitions do not change the decision, the link between metric and action is missing.

## Example or case study

Sales and product both use "active customer," but one counts open contracts and the other events in the last 30 days. The semantic layer declares grain, filters, and owner, preventing the same term from causing divergent decisions.

| Observed evidence       | Cautious interpretation                      | Recommended action            |
|------------------------|----------------------------------------------|------------------------------|
| Number improves        | Could be real effect or normal variation     | Seek comparison and segmentation |
| One segment changes more | Aggregated average hides difference          | Separate cohorts or use cases  |
| Cost grows with result | Impact must be read on margin                 | Estimate trade-offs and sustainability |

### Intermediate level

### Recommended datasets and materials
Use dbt, warehouse, CRM, events, marts, semantic layer, and lineage. If no real data, create a synthetic dataset with at least 200 rows, one time dimension, one segment dimension, and one outcome metric.

## Common mistake to avoid

Using semantic layer and metric definitions as a label rather than a process. Happens when showing a chart without decision, a metric without baseline, or a conclusion without critical assumptions. The control question is: if this result were unstable, which choice would I get wrong? If the answer is vague, the link between analysis and action is missing.
