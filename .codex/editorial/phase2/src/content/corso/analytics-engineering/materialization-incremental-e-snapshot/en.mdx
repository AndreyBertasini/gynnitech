# Materialization, incremental, and snapshot for events and customer state

In analytics engineering, handling real-time events and slowly changing customer states is a daily challenge. Choosing between views, tables, incremental models, and snapshots is not about technical elegance but about balancing freshness, cost, and historical accuracy.

## Real-world problem

How do you transform raw data into reliable, reusable business models without wasting resources or missing important events? This question guides the choice of the right materialization strategy for events and customer state. Knowing what each materialization does is not enough; you must understand which concrete decision you want to improve, which data to observe, and which mistakes to avoid.

## Conceptual model

A simple framework helps:

| Step     | What to clarify                           | Output                 |
|----------|------------------------------------------|------------------------|
| Question | Which real decision needs improvement?  | Decision to make       |
| Measure  | Which signal represents the problem?    | Metric or source data  |
| Check    | Which baseline makes the result interpretable? | Credible comparison    |
| Action   | What changes after analysis?             | Next operational step  |

This keeps focus on what really matters: the decision.

## Rigorous formalization

To make the choice reproducible and debatable, define:

- Unit of analysis: source, model, test, mart, metric, or exposure
- Main signal: freshness, lineage, test coverage, model cost, stakeholder trust
- Baseline: prior period, comparable group, benchmark, or counterfactual
- Expected decision: dbt model, semantic layer, contract, test, or release pipeline
- Risk: mistaking an available number for sufficient evidence

Only then can another analyst replicate the logic and confirm or challenge the decision.

## The four dbt materializations

| Materialization | Behavior                          | When to use                            | Storage | Freshness                   |
|-----------------|---------------------------------|-------------------------------------|---------|-----------------------------|
| View            | SQL view, no data stored         | Staging, lightweight models          | 0       | Always up to date            |
| Table           | Physical table, rebuilt from scratch | Small/medium models with complex logic | High    | Updated at build             |
| Incremental     | Adds only new rows               | Large tables with append-only data  | High    | Updated at build on new rows |
| Ephemeral       | Inline CTE, never materialized  | Lightweight intermediate transforms | 0       | Calculated in consumer query |

Choice depends on model size, update frequency, and rebuild cost.

## Incremental: the most powerful pattern

Incremental models scale dbt to billions of rows without exploding costs. The trick is loading only new or updated data based on a reliable field like `event_time`.

Strategies:

- `append`: add new rows, ideal for immutable data
- `delete+insert`: update existing rows by deleting and reinserting
- `merge`: update and insert, available on Snowflake and BigQuery
- `insert_overwrite`: overwrite partitions, useful for partitioned data

The key syntax is a conditional block filtering data only when running incrementally.

## When NOT to use incremental

Avoid if:

- Model is small (<10M rows), a table is simpler
- Business logic changes often and must be reapplied to all history
- No reliable field exists to filter new rows

## Cost management in data warehouses

Costs depend on compute usage. To optimize:

1. Limit data window in development, e.g., last 30 days
2. Use appropriate warehouses: XS for testing, XL for production
3. Disable unused models to save resources

## Real case: how Zapier cut dbt costs by 60%

Zapier identified the most expensive models and converted them to incremental, drastically reducing costs without losing data. They also added query timeouts and reduced staging retention. This pragmatic approach cut costs from $28,000 to $11,200 monthly.

## Quality checks

Before relying on these techniques, always verify:

- Data completeness
- Duplicates
- Timezones
- Definition changes
- Excluded segments

Many errors stem from data that doesn't represent the expected behavior.

## Segment interpretation

Don't stop at the aggregate average. Segment by channel, cohort, plan, country, device, and user maturity. Opposing trends in segments can make the average misleading and lead to wrong decisions.

## Example or case study

A two-billion-row event table with up to 48-hour delays requires an incremental strategy with recalculation windows and completeness tests. Monitor whether improvements are real or normal fluctuations, segment cohorts, and weigh cost versus benefit.

| Observed evidence           | Cautious interpretation                  | Recommended action             |
|----------------------------|------------------------------------------|-------------------------------|
| Numbers improve             | Could be real effect or normal variation | Seek comparison and segmentation |
| One segment changes more    | Average hides significant differences    | Separate cohorts or use cases  |
| Cost rises with results     | Impact must be read on margin             | Estimate trade-offs and sustainability |

## Lab / exercise

### Basic level

Write a one-page brief describing the decision supported by materialization, incremental, and snapshot, the primary metric, baseline, main risk, and action if the signal confirms.

### Intermediate level

Build a table with three segments or scenarios, indicating for each what changes, a plausible alternative explanation, and a check before recommending action.

### Research-grade level

Prepare a decision memo with hypotheses, required data, exclusion criteria, quality checks, decision threshold, residual risk, and post-decision monitoring plan.

### Recommended datasets and materials

Use dbt, warehouse, CRM sources, events, marts, semantic layer, and lineage. If no real data is available, create a synthetic dataset with at least 200 rows, a time dimension, a segment dimension, and an outcome metric.

## Common mistake to avoid

Do not treat materialization, incremental, and snapshot as mere labels. The risk is showing charts without decisions, metrics without baselines, or conclusions without critical assumptions. The key question is: if this result were unstable, what wrong choice would I make? If you can't answer, the link between analysis and action is missing.

Materialization, incremental, and snapshot become useful only if they help clarify decisions, not just add terminology. Use the problem, model, formalization, example, lab, and checkpoint framework to turn theory into verifiable practice.
