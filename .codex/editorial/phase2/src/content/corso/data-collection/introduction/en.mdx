# Data collection: fundamentals and strategy

A dashboard can look precise but contain useless data if no one decided beforehand which behaviors to observe, at what granularity, and for which decision. Data collection does not start from the tool but from a tracking plan that separates necessary events, critical properties, and noise. This lesson builds that foundation.

## Real-world problem

In data collection and tracking, the challenge is to gather reliable events before dashboards and models amplify hidden errors. This is not abstract theory but improving a concrete choice with data, explicit assumptions, and minimal checks.

Operational goal: understand the analytical problem and decision context; apply examples, metrics, and controls to real cases. If you cannot specify which decision changes, which data you observe, and which error you want to avoid, the lesson is not yet applied competence.

## Conceptual model

| Phase | What to clarify | Output |
|---|---|---|
| Question | Which real choice must improve? | Decision to make |
| Measure | Which observable signal represents the problem? | Metric or source data |
| Control | Which baseline makes the result interpretable? | Credible comparison |
| Action | What changes after the analysis? | Next operational step |

The model is simple: decision, data, control, action. Every technical deep dive should strengthen at least one of these points.

## Rigorous formalization

To analyze data collection, define the unit of work: event, property, user, session, or data source. Link this unit to an observable metric: completeness, duplicates, semantic consistency, case coverage. Finally, declare the expected decision: tracking plan, event contract, QA, and priority correction.

| Element | Required specification |
|---|---|
| Unit of analysis | event, property, user, session, or data source |
| Main signal | completeness, duplicates, semantic consistency, coverage |
| Baseline | prior period, comparable group, benchmark, counterfactual scenario |
| Decision | tracking plan, event contract, QA, priority fix |
| Risk | mistaking an available number for sufficient proof |

Formalization is solid when another analyst can reproduce the logic, critique assumptions, and reach the same decision from the same data.

## Example or case study

A team needs to rebuild marketing dashboards because numbers don't match across CRM, analytics, and warehouse. Before building new reports, they trace data flow from source to final metric and decide which events become shared contracts.

| Observed evidence | Cautious interpretation | Recommended action |
|---|---|---|
| Number improves | Could be real effect or normal variation | Seek comparison and segmentation |
| One segment changes more | Aggregated average hides differences | Separate cohorts or use cases |
| Cost rises with result | Impact must be read on margin | Estimate trade-offs and sustainability |

## Common mistake to avoid

The most common error is treating Data collection: fundamentals and strategy as a label rather than a process. This happens when the team shows a chart without a decision, a metric without a baseline, or a conclusion without stating which assumption might invalidate it.

The control question is: if this result were unstable, which choice would I get wrong? If the answer is not concrete, the link between analysis and action is missing.

## Starting point

Every collected event must have an owner, a clear definition, minimal properties, validation criteria, and intended use. If data does not support a real question, it only adds maintenance without value.

- Context: which technical constraint guides the design?
- Method: which control ensures reliability?
- Application: which trade-off would you explain before production?

## The three pillars of data collection

1. What to collect: events, properties, entities, starting from business requirements, not "track everything".
2. How to collect: client-side (SDK, pixel), server-side (API, webhook), database (CDC, ETL).
3. Quality at source: validation, schema enforcement, deduplication. Dirty upstream data leads to wrong downstream insights.

## Tracking framework

A tracking plan answers:
- Which events? E.g., `page_view`, `add_to_cart`, `purchase`
- Which properties per event? E.g., `page_view` has `page_url`, `referrer`; `purchase` has `order_id`, `amount`, `currency`
- Which entities/users? Unique IDs, static and dynamic properties
- What temporal granularity? Event time vs server time, batching allowed

The tracking plan is a living, versioned document with clear ownership, not a forgotten Excel sheet.

## Client-side vs Server-side tracking

| | Client-side | Server-side |
|---|---|---|
| How it works | SDK in browser/app sends events to collector | Server sends events via API/webhook |
| Advantages | Easy to implement, rich data (DOM, clicks, scroll) | Reliable, not blocked by ad-blockers, full control |
| Disadvantages | Blocked by ad-blockers, missing data, extra latency | Requires more backend development, less visual data |
| Ideal for | Web analytics, heatmaps, A/B testing | Transactions, business-critical events |

Mature architectures use both: client-side for behavioral data, server-side for transactional data, with cross-source reconciliation.

## Operational deep dive

Data collection is part of a larger system of decisions, available data, technical constraints, organizational incentives, and execution quality. The risk is treating it as a definition to memorize; instead, understand the problem it solves, its assumptions, and what happens if they fail.

The first question is not "which metric to calculate?" but: which decision will this analysis inform? Dashboards, queries, or models only add value if they reduce decision uncertainty. If they do not change a choice, they are documentation or analytical theater.

A useful sequence:
1. Define the problem in business terms;
2. Identify the correct unit of analysis: user, account, event, session, order, campaign;
3. Check if data truly measures the phenomenon or just a shadow;
4. Build an interpretable metric;
5. Segment to avoid averages hiding opposite patterns;
6. Turn the result into a verifiable recommendation.

## Real case: Netflix and metric discipline

Netflix builds product decisions around observable behavioral signals: episode completion, search time before playback, early abandonment, weekly return, recommendation effectiveness. Data is decision infrastructure, not decoration.

When Netflix evaluates a change - new recommendation row, different cover image, ranking algorithm - it measures not just immediate clicks but quality signals: does the user really watch? Do they return? Is search time reduced? Is implicit satisfaction increased? This discipline prevents optimizing vanity metrics that look good short-term but harm long-term value.

The same principle applies here: data collection must link to an outcome. If the result does not help choose between two actions, the analysis is incomplete.

## Python example: checking stability and anomalies

A useful metric must be stable enough to guide decisions and sensitive enough to signal real changes. In Python, calculate week-over-week changes and identify anomalies using z-scores based on rolling mean and standard deviation.

This prevents reacting to random fluctuations and highlights changes worth investigating, supporting alerts and weekly reviews.

## Common mistakes to avoid

1. Aggregating data too early, hiding opposing patterns.
2. Ignoring data quality: duplicates, incomplete tracking, inconsistent timezones, definition changes.
3. Confusing correlation with causation: users using a feature convert more does not mean the feature causes conversion.

To reduce risks, every analysis should include explicit metric definition, segment comparison, and verification against prior periods or control groups.

## Summary

Data collection is a decision tool, not a textbook topic. Value arises by linking problem, data, metric, segmentation, and action. Analysis ends not with "the number went up" or "down" but with an operational statement: which decision do we make, with what confidence, and which metric will tell if we were right?
