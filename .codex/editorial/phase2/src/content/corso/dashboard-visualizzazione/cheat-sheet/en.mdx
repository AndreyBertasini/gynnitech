## Real problem

In dashboards and visualization, the real challenge is turning complex data into clear, actionable decision tools. Creating charts or metrics is not enough: every element must support a concrete decision, reducing uncertainty and guiding action. If you cannot specify which decision changes, which data you observe, and which error you want to avoid, you have not yet achieved applied competence.

## Conceptual model

| Phase     | What to clarify                               | Output                   |
|-----------|----------------------------------------------|--------------------------|
| Question  | Which real choice should improve?            | Decision to make         |
| Measure   | Which observable signal represents the problem? | Metric or source data    |
| Control   | Which baseline makes the result interpretable? | Credible comparison     |
| Action    | What changes after the analysis?              | Next operational step    |

This simple model keeps focus: every analysis must connect decision, data, control, and action.

## Rigorous formalization

To analyze a dashboard or visualization, define the unit of work (chart, metric, view, stakeholder, or recurring decision), the main signal (readability, usage frequency, decision time, reduced ambiguity), the baseline for comparison (previous period, comparable group, benchmark, counterfactual scenario), and the expected decision (dashboard, operational view, alert, executive narrative).

| Element         | Required specification                                              |
|-----------------|--------------------------------------------------------------------|
| Unit of analysis | chart, metric, view, stakeholder, or recurring decision            |
| Main signal     | readability, usage frequency, decision time, reduced ambiguity      |
| Baseline        | previous period, comparable group, benchmark, or counterfactual scenario |
| Decision        | dashboard, operational view, alert, or executive narrative         |
| Risk            | Mistaking an available number for sufficient proof                 |

This formalization enables another analyst to reproduce the logic, critique assumptions, and reach the same decision.

## Lab / exercise

### Basic level

Write a one-page dashboard brief: decision to support, primary metric, baseline, main risk, and action if the signal confirms.

### Intermediate level

Build a table with three segments or periods; for each, indicate what changes, a plausible alternative explanation, and a control to use before recommending action.

### Research-grade level

Prepare a decision memo: hypotheses, required data, exclusion criteria, quality controls, decision threshold, residual risk, and post-decision monitoring plan.

### Recommended datasets and materials

Use dashboard datasets, business metrics, stakeholder briefs, mockups, and usage logs. If real data is unavailable, create a synthetic dataset with at least 200 rows, one temporal dimension, one segment dimension, and one outcome metric.

## Common mistake to avoid

The most frequent error is treating the cheat sheet as a label rather than a process. This happens when a chart is shown without a clear decision, a metric without a baseline, or a conclusion without stating which assumptions could invalidate it.

The control question is: if this result were unstable, which choice would I get wrong? If you cannot answer concretely, the link between analysis and action is still missing.

## Quiz or checkpoint

1. Which concrete decision should this analysis improve?
2. Which unit of analysis makes the problem measurable?
3. Which baseline would you use to avoid naive interpretation?
4. Which common mistake could change the conclusion?
5. What output would you deliver to a non-technical stakeholder?

## Summary

The dashboard and visualization cheat sheet is useful only if it leads to clearer decisions, not just more terminology. Use the framework of problem, model, formalization, example, exercise, and checkpoint to turn the lesson into verifiable practice.
