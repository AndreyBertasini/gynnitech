# Multi-agent workflow: analyst, engineer, reviewer, owner

This module tackles a practical challenge in applying agentic AI to data work: preventing analytical tasks from becoming a chain of unverifiable answers. The goal is not to have the model "do analysis" but to design a workflow where questions, data, checks, and decisions remain transparent.

Building on the previous lesson, it adds a more operational layer: `agentic-automl-planning-training-review-e-deploy`. The aim is to increase speed and coverage in data work while preserving responsibility over definitions, thresholds, segments, and recommendations.

## Real problem

In the domain of Agentic AI for Data Analysis, Data Engineering, and AutoML, the multi-agent workflow addresses the challenge of designing a collaboration where each agent has limited, verifiable responsibility. The problem arises when a team wants to speed up data work but cannot distinguish between delegable tasks and non-delegable responsibilities. AI can generate hypotheses, queries, documentation, tests, candidate features, or summaries, but the final decision remains human, especially when it affects budgets, roadmaps, customers, or compliance.

The operational goal is to produce artifacts that others can review: if you cannot specify which decision changes, which data you observe, and which errors you want to avoid, the competence has not yet been applied.

## Conceptual model

The model consists of four layers: task, context, control, and decision.

| Level | What to clarify | Example in data work |
|---|---|---|
| Task | Which part of the work is accelerated? | Query draft, data profile, AutoML checklist, memo |
| Context | What information makes the output useful? | Schema, metric, period, segment, policy |
| Control | How to detect if the output is wrong? | Grain tests, baseline, leakage checks, owner review |
| Decision | What action follows if control passes? | Pipeline fix, experiment, deploy, recommendation |

This model avoids two opposite errors: using AI only as text autocomplete or giving it autonomy over decisions requiring business judgment. Professional skill lies in drawing the boundary.

## Rigorous formalization

To analyze the workflow, define the unit of work: agent role, handoff, artifact, review, decision, or escalation. Link this unit to observable signals such as clear handoffs, resolved conflicts, avoided duplications, artifact quality, and final ownership. The expected decision is to design a multi-agent collaboration with limited, verifiable responsibilities.

| Element | Required specification |
|---|---|
| Unit of analysis | agent role, handoff, artifact, review, decision, or escalation |
| Main signal | clear handoffs, resolved conflicts, avoided duplications, artifact quality, final ownership |
| Baseline | manual process, previous period, comparable group, or current model |
| Decision | multi-agent collaboration with limited, verifiable responsibility |
| Guardrail | privacy, cost, data quality, interpretability, ownership, operational risk |
| Main risk | creating many agents that argue without producing reviewable output |

A mature workflow lets a reviewer reproduce the logic, critique assumptions, and reach the same decision from the same data. If the result depends on untracked conversations, the process is not yet mature.

## Example or case study

An analyst agent formulates hypotheses, an engineer agent evaluates data and lineage, a reviewer critiques the memo, and the business owner decides thresholds and final actions. AI is not the center of work but supports the decision cycle: question, data, control, recommendation, monitoring.

| Observed evidence | Cautious interpretation | Recommended action |
|---|---|---|
| Faster output | Speed only matters if quality and control are maintained | Compare with manual baseline and independent review |
| Plausible explanations | Linguistic plausibility is not empirical proof | Translate each explanation into data or process checks |
| Metric improvement | Possible composition effects, leakage, or seasonality | Segment, verify guardrails, and monitor over time |

A good case study ends with a defensible decision: what to automate, what to keep manual, which metric to monitor, and what condition would stop the process.

## Operational framework

The workflow unfolds in five steps:

| Step | Guiding question | Minimum output |
|---|---|---|
| Decision | Which choice to improve? | Action verb and owner |
| Context | What do we know about the data? | Sources, grain, period, limits |
| AI support | Which part can be accelerated? | Prompt, tool, or checklist |
| Verification | What error could change the conclusion? | Control, guardrail, baseline |
| Handoff | Who decides and by what criteria? | Memo, ticket, model, or dashboard |

This framework applies to exploratory analysis, SQL, data engineering, AutoML, and agentic workflows. No output should be treated as evidence without source, control, and decision.

## Lab / exercise

### Basic level

Write a one-page brief for a multi-agent workflow: decision to support, required inputs, expected output, minimum control, and main risk. Use a simple case such as a conversion change, delayed pipeline, or forecast model evaluation.

### Intermediate level

Create a table with three scenarios: manual workflow, AI-assisted workflow, and highly automated workflow. For each, indicate estimated time, expected quality, operational risk, required control, and final owner.

### Research-grade level

Prepare a reviewable decision memo including hypotheses, required data, exclusion criteria, quality controls, decision threshold, residual risk, and post-decision monitoring plan. Add a section on "what would change the team's mind."

### Recommended datasets and materials

Use RACI analytics, workflow boards, review rubrics, examples of agentic outputs, and escalation policies. If real data is unavailable, create a synthetic dataset with at least 200 rows, temporal dimension, segment dimension, primary metric, and a field representing potential quality errors.

## Common mistake to avoid

The first mistake is treating the multi-agent workflow as a label rather than a process, showing generated output without explaining data, controls, and decisions. The second is confusing individual productivity with organizational reliability. The third is failing to decide upfront which actions are allowed, require approval, or are forbidden.

A practical fix is to write three lines before starting:

| Line | Content |
|---|---|
| Decision | Which concrete choice to improve |
| Evidence | Which data or control supports the choice |
| Stop | Which risk would stop or require review |

If any line is missing, the workflow is not ready. AI can still be useful for exploratory support but not as a stable part of decision-making.

## Quiz or checkpoint

1. Which concrete decision should this workflow improve?
2. Which part can be delegated to AI and which must remain under human ownership?
3. Which baseline would you use to measure if the new process truly improves?
4. Which failure mode could make an apparently correct output dangerous?
5. Which artifact would you deliver to a stakeholder: memo, dashboard, query review, model card, runbook, or checklist?

If you cannot answer specifically, return to the real problem: a generic answer often signals premature automation.

## Operational summary

The multi-agent workflow becomes valuable when it produces a clearer decision, not just new terminology. Use the cycle decision, context, AI support, verification, and handoff to turn the lesson into verifiable practice.

The final rule is simple: the more the workflow uses tools, state, approvals, and traceability, the more it must be observable. An output you cannot reconstruct, review, or stop is not professional automation but uncontrolled speed.
