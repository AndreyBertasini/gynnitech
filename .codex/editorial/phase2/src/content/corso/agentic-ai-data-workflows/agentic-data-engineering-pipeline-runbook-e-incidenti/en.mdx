# Agentic data engineering: pipeline, runbook, and incidents

This lesson tackles a practical challenge: how to apply agentic AI to data workflows without turning analytical work into a chain of unverifiable answers. The goal is not to ask the model to "do analysis," but to design a process where questions, data, checks, and decisions remain transparent and traceable.

Building on the previous lesson `agentic-sql-e-semantic-layer-con-approval`, this adds a more operational layer. The professional promise is straightforward: speed up and broaden data work while retaining ownership over definitions, thresholds, segments, and recommendations.

## Real-world problem

Imagine a weekly review where marketing, product, and data teams must decide what to fix first: funnel, tracking, campaign, model, or pipeline. Without agentic AI, analysts risk wasting hours on repetitive steps; used poorly, AI can deliver convincing but fragile explanations.

The operational challenge is to determine which actions an agent can suggest or perform during data incidents. This is not abstract theory but a method to improve concrete decisions with data, explicit assumptions, and minimal checks.

## Conceptual model

The model has four levels: task, context, control, and decision.

| Level    | What to clarify                              | Example in data work                         |
|----------|---------------------------------------------|---------------------------------------------|
| Task     | Which part of the work is accelerated?      | Query draft, data profile, AutoML checklist, memo |
| Context  | What information makes the output useful?   | Schema, metric, period, segment, policy     |
| Control  | How to detect if the output is wrong?       | Grain test, baseline, leakage, owner review |
| Decision | What action follows if the control holds?   | Pipeline fix, experiment, deploy, recommendation |

This model prevents two opposite mistakes: using AI merely as text autocomplete or granting it autonomy on business-judgment decisions. Professional skill lies in drawing this boundary.

## Rigorous formalization

To analyze agentic data engineering, first define the unit of work: pipeline, alert, runbook, incident ticket, proposed fix, or post-mortem. Link it to observable signals like MTTR, false alarms, runbook coverage, available rollbacks, and post-mortem quality. Finally, specify the expected decision: which operational actions an agent can suggest or perform during data incidents.

| Element         | Required specification                                                      |
|-----------------|----------------------------------------------------------------------------|
| Unit of analysis| pipeline, alert, runbook, incident ticket, proposed fix, or post-mortem     |
| Main signal     | MTTR, false alarms, runbook coverage, available rollbacks, post-mortem quality |
| Baseline        | Manual process, previous period, comparable group, or current model        |
| Decision        | Which operational actions an agent can suggest or perform during data incidents |
| Guardrail       | Privacy, cost, data quality, interpretability, ownership, operational risk  |
| Main risk       | Automating remediation without understanding downstream impact, compliance, and costs |

This formalization is sound when a reviewer can reproduce the logic, critique assumptions, and reach the same decision from the same data. If results depend on untracked conversations, the workflow is immature.

## Example or case study

An order pipeline fails before commercial review. The agent collects logs, identifies a schema change, and proposes a runbook; the data engineer approves the patch and stakeholder communication.

This example shows AI is not the center of work but the decision cycle: question, data, control, recommendation, monitoring. AI reduces friction between these steps, but each remains controllable.

| Observed evidence                 | Cautious interpretation                            | Recommended action                              |
|---------------------------------|---------------------------------------------------|------------------------------------------------|
| Workflow produces output faster  | Speed helps only if quality and control remain intact | Compare with manual baseline and independent review |
| Model offers plausible explanations | Linguistic plausibility is not empirical proof    | Translate each explanation into data or process checks |
| Result improves a metric         | Could be composition effect, leakage, or seasonality | Segment, verify guardrails, and monitor over time |

A good case study ends not with "AI worked" but with a defensible decision: what to automate, what to keep manual, which metric to monitor, and what condition would stop the process.

## Lab / exercise

### Basic level

Write a one-page brief for agentic data engineering: pipeline, runbook, and incidents. Specify the decision to support, required inputs, expected output, minimum control, and main risk. Use a simple case like a conversion change, delayed pipeline, or forecast model evaluation.

### Intermediate level

Create a table with three scenarios: manual workflow, AI-assisted workflow, and more automated workflow. For each, indicate estimated time, expected quality, operational risk, required control, and final owner.

### Research-grade level

Prepare a reviewable decision memo. Include hypotheses, required data, exclusion criteria, quality controls, decision threshold, residual risk, and post-decision monitoring plan. Add a section "what would change the team's mind."

### Recommended datasets and materials

Use orchestrator logs, alerts, lineage, runbooks, SLA dashboards, incident tickets, and rollback policies. If real data is unavailable, create a synthetic dataset with at least 200 rows, a time dimension, a segment dimension, a primary metric, and a field representing a possible quality error.

## Common mistakes to avoid

First, treating agentic data engineering as a label rather than a process. This happens when teams show generated outputs without explaining data, controls, and decisions. Second, confusing individual productivity with organizational reliability. Third, failing to decide upfront which actions are allowed, require approval, or are forbidden.

A practical fix is to write three lines before starting:

| Line      | Content                                      |
|-----------|----------------------------------------------|
| Decision  | Which concrete choice we want to improve     |
| Evidence  | Which data or control supports the choice    |
| Stop      | Which risk would stop us or require review   |

If any line is missing, the workflow is not ready. AI can still help exploratory support but not stable decision-making.

## Quiz or checkpoint

1. Which concrete decision should this lesson improve?
2. Which part of the workflow can be delegated to AI and which must remain under human ownership?
3. What baseline would you use to measure if the new process truly improves?
4. What failure mode could make a seemingly correct output dangerous?
5. What artifact would you deliver to a stakeholder: memo, dashboard, query review, model card, runbook, or checklist?

If you cannot answer specifically, return to the real problem before continuing. Generic answers often signal premature automation.

## Operational summary

Agentic data engineering: pipeline, runbook, and incidents becomes useful when it produces clearer decisions, not just new terminology. Use the cycle decision, context, AI support, verification, and handoff to turn the lesson into verifiable practice.

The final rule is simple: the more the workflow uses tools, state, approvals, and traceability, the more it must be observable. An output you cannot reconstruct, review, or stop is not professional automation; it is just uncontrolled speed.
