# Observability, evals, security, and cost control

This module tackles a practical challenge: how to apply agentic AI to data workflows without turning analytical work into a series of unverifiable answers. The goal is not to ask the model to "do analysis," but to design a process where questions, data, controls, and decisions remain transparent and traceable.

Building on the previous lesson about the multi-agent workflow (`multi-agent-workflow-analyst-engineer-reviewer-owner`), this adds a more operational layer. The aim is to increase speed and coverage in data work while preserving ownership over definitions, thresholds, segments, and recommendations.

## Real-world problem

Imagine a weekly review where marketing, product, and data teams must decide what to fix first: funnel, tracking, campaign, model, or pipeline. Without an agentic approach, analysts risk spending hours on repetitive tasks; with poorly applied agentic AI, they risk delivering explanations that seem convincing but are fragile.

The operational challenge arises when a team wants to speed up data work but cannot distinguish between tasks that can be delegated and responsibilities that cannot. AI can generate hypotheses, queries, documentation, tests, candidate features, or summaries, but decisions remain human when they impact budget, roadmap, customers, compliance, access, or production models.

The goal is to produce an artifact that another professional can review. If you cannot specify which decision changes, which data you observe, and which error you want to avoid, the skill is not yet applied.

## Conceptual model

The model has four levels:

| Level     | What to clarify                             | Example in data work                         |
|-----------|--------------------------------------------|---------------------------------------------|
| Task      | Which part of the work is accelerated?     | Query draft, data profile, AutoML checklist, memo |
| Context   | What information makes the output useful?  | Schema, metric, period, segment, policy     |
| Control   | How to detect if the output is wrong?      | Grain test, baseline, leakage, owner review |
| Decision  | What action follows if control passes?     | Pipeline fix, experiment, deploy, recommendation |

This model avoids two opposite errors: using AI only as text autocomplete or giving it autonomy over decisions requiring business judgment. The skill lies in clearly drawing this boundary.

## Rigorous formalization

To make the workflow observable and evaluable, define the unit of work (trace, eval, cost, policy, failure mode, prompt, or tool call) and link observable signals (success rate, human interventions, cost per run, blocked errors, eval regressions, security incidents). The expected decision is whether an agentic workflow is sufficiently observable and safe for recurring use.

| Element         | Required specification                                                    |
|-----------------|--------------------------------------------------------------------------|
| Unit of analysis | trace, eval, cost, policy, failure mode, prompt, or tool call            |
| Main signal     | success rate, human interventions, cost per run, blocked errors, eval regressions, security incidents |
| Baseline        | Manual process, previous period, comparable group, or current model      |
| Decision        | Decide if the agentic workflow is sufficiently observable and safe for recurring use |
| Guardrail       | Privacy, cost, data quality, interpretability, ownership, operational risk |
| Main risk       | Deploying agents without trace, eval, and cost limits per scenario       |

Formalization is solid when a reviewer can reproduce the logic, critique assumptions, and reach the same decision from the same data. If results depend on untracked conversations, the workflow is immature.

## Example or case study

A reporting agent works well in demos but generates high costs on large datasets. The team introduces per-run budgets, caching, regression evals, and blocks on sensitive tools.

This case shows AI is not the center of work but the decision cycle: question, data, control, recommendation, monitoring. AI helps reduce friction between these steps, but each remains controllable.

| Observed evidence              | Cautious interpretation                             | Recommended action                                |
|------------------------------|----------------------------------------------------|--------------------------------------------------|
| Workflow produces output faster | Speed is only useful if it does not reduce quality or control | Compare with manual baseline and independent review |
| Model proposes plausible explanations | Linguistic plausibility is not empirical proof    | Translate every explanation into data or process control |
| Result improves a metric      | Could be composition effect, leakage, or seasonality | Segment, verify guardrails, and monitor over time |

A good case study ends with a defensible decision: what to automate, what to keep manual, which metric to monitor, and what condition would stop the process.

## Lab / exercise

### Basic level

Write a one-page sheet for **Observability, evals, security, and cost control**: decision to support, required inputs, expected output, minimal control, and main risk. Use a simple case such as a conversion change, delayed pipeline, or forecast model evaluation.

### Intermediate level

Build a table with three scenarios: manual workflow, AI-assisted workflow, and more automated workflow. For each, indicate estimated time, expected quality, operational risk, necessary control, and final owner.

### Research-grade level

Prepare a reviewable decision memo including hypotheses, required data, exclusion criteria, quality controls, decision threshold, residual risk, and post-decision monitoring plan. Add a section on "what would change the team's mind."

### Recommended datasets and materials

Use traces, eval sets, token budgets, incident logs, security policies, regression tests, and cost dashboards. If real data is unavailable, create a synthetic dataset with at least 200 rows, a time dimension, a segment dimension, a primary metric, and a field representing a possible quality error.

## Common mistakes to avoid

The first mistake is treating **Observability, evals, security, and cost control** as a label rather than a process. This happens when teams show generated output without explaining data, controls, and decisions. The second is confusing individual productivity with organizational reliability. The third is not deciding upfront which actions are allowed, which require approval, and which are forbidden.

A practical fix is to write three lines before starting:

| Line     | Content                                    |
|----------|--------------------------------------------|
| Decision | Which concrete choice do we want to improve? |
| Evidence | Which data or control supports the choice? |
| Stop     | Which risk would make us stop or ask for review? |

If any of these are missing, the workflow is not ready. AI can still be useful for exploratory support but not as a stable part of decision-making.

## Quiz or checkpoint

1. Which concrete decision should this lesson improve?
2. Which part of the workflow can be delegated to AI and which must remain under human ownership?
3. Which baseline would you use to measure if the new process truly improves?
4. Which failure mode could make an apparently correct output dangerous?
5. Which artifact would you deliver to a stakeholder: memo, dashboard, query review, model card, runbook, or checklist?

If you cannot answer specifically, return to the real problem before continuing. Generic answers often signal premature automation.

## Operational summary

**Observability, evals, security, and cost control** becomes useful when it produces clearer decisions, not just terminology. Use the cycle of decision, context, AI support, verification, and handoff to turn the lesson into verifiable practice.

The final rule is simple: the more a workflow uses tools, state, approvals, and trace, the more observable it must be. An output you cannot reconstruct, review, or stop is not professional automation; it is uncontrolled speed.
